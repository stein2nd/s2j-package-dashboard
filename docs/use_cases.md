# S2J Package Dashboard - ユースケース仕様

## 概要

本ドキュメントは、S2J Package Dashboard の初期設計における、**ユースケース** を定義します。

本仕様は、アプリケーション層/ドメイン層の設計およびテストケース定義の基準とします。

ユースケースは、ユーザーまたは外部アクターが S2J Package Dashboard を利用して達成したい目的を、アプリケーションの挙動として定義します。

本仕様では、ユースケース (何を達成するか)、UX フロー (どの操作・状態を経由するか)、スクリーン/UI (どう表示するか) を明確に区別します。経路は [`ux_flows_spec.md`](./ux_flows_spec.md)、画面は [`screen_spec.md`](./screen_spec.md) を正本とします。

実装開始前に、実用最小限の製品 (MVP) ユースケースを確定し、各ユースケースについて、メインのフロー/エラーのフロー/オフラインのフローを確定します。

実装後は、ユースケースをアプリケーション/連携/UI テストのシナリオにマッピングします。

## 目的

本仕様の目的は、下記とします。

1. S2J Package Dashboard の主要なユーザー目的を、明確化する
2. アプリケーション層の責務を、明確化する
3. ドメイン・ロジックと UI ロジックを、分離する
4. iOS/iPadOS/Android で共通するアプリケーション挙動を、定義する
5. Kotlin Multiplatform (KMP) 共有ロジックの候補を、明確化する
6. UX フロー/スクリーン/API/ストレージの、仕様との境界を明確化する
7. テスト対象となるビジネス・シナリオを、明確化する

## 非目的

本仕様は、UI レイアウト、色/タイポグラフィ、SwiftUI/Compose 実装、ナビゲーション API、API エンドポイント、データベース・スキーマ、キャッシュの有効期限 (TTL)、Keychain/Keystore 設定を直接定義しません。

## 責務

ユーザーまたは外部アクターが達成したい目的を定義します。正本とするのは、アクター、目的、事前条件、成功条件、失敗の種類です。

## 非責務

操作経路は [`ux_flows_spec.md`](./ux_flows_spec.md)、画面の表示内容は [`screen_spec.md`](./screen_spec.md)、行き先と戻り方は [`navigation_spec.md`](./navigation_spec.md)、共有対象は [`architecture.md`](./architecture.md)、Kotlin Multiplatform (KMP) の HOW は [`kmp_spec.md`](./kmp_spec.md)、遷移の形式は [`state_machine.md`](./state_machine.md)、復元対象は [`application_state.md`](./application_state.md)、横断 UI は [`ui.md`](./ui.md)、Viewport は [`ui-viewport.md`](./ui-viewport.md)、検証の種類は [`testing_spec.md`](./testing_spec.md)、エラー型は [`models_spec.md`](./models_spec.md) を正本とします。

* 統計を確認する

* ローカルデータを管理する

## ユースケースのリレーションシップ

ユースケースは、他のユースケースを含めたり、拡張できます。

たとえば:
* [UC-05](#uc-05-パッケージ詳細を表示する) は [UC-23](#uc-23-キャッシュを更新する) と [UC-09](#uc-09-パッケージを更新する) を含み得る
* [UC-12](#uc-12-統計をリフレッシュする) は [UC-14](#uc-14-統計スナップショットを保存する) と [UC-23](#uc-23-キャッシュを更新する) を含み得る
* [UC-16](#uc-16-packagist-認証を設定する) は [UC-20](#uc-20-認証ステータスを確認する) を含み得る

ただし、含める/拡張するの関係は、実装上の関数コールの関係を意味しません。

## ユースケースと UX フローの関係

ユースケースは目的、UX フローは具体的な利用経路を表します。同じユースケースに対して、複数の UX フローが存在してかまいません。経路の正本は [`ux_flows_spec.md`](./ux_flows_spec.md) とします。

たとえば、[UC-05](#uc-05-パッケージ詳細を表示する) は、ダッシュボードから、検索から、ディープリンクから、それぞれ異なる経路で達成できます。

## ユースケースとスクリーンの関係

1スクリーンが複数のユースケースを提供してもかまいません。

たとえば、パッケージ詳細は、下記を提供し得ます。

* 表示 ([UC-05](#uc-05-パッケージ詳細を表示する))
* お気に入りの追加/削除 ([UC-06](#uc-06-お気に入りを追加する) / [UC-07](#uc-07-お気に入りを削除する))
* リポジトリを開く ([UC-08](#uc-08-リポジトリを開く))
* 更新 ([UC-09](#uc-09-パッケージを更新する))
* 統計表示/更新 ([UC-10](#uc-10-統計を表示する) / [UC-12](#uc-12-統計をリフレッシュする))

画面の構成は [`screen_spec.md`](./screen_spec.md) を正本とします。

逆に、1ユースケースが複数スクリーンにまたがってもかまいません。

たとえば、認証は、設定→認証→システム認証 UI →設定…と複数スクリーンにまたがり得ます。

画面と経路は [`screen_spec.md`](./screen_spec.md) / [`navigation_spec.md`](./navigation_spec.md) / [`authentication_spec.md`](./authentication_spec.md) を正本とします。

## ユースケースと API の関係

エンドポイントは [`api-packagist.md`](./api-packagist.md) / [`api-github.md`](./api-github.md) を正本とします。
本仕様は、「ユースケースがエンドポイントに直接依存せず、リポジトリ/プロバイダ抽象を介する」ことのみを定めます。

## ユースケースとストレージの関係

ユースケースは、ストレージの実装に直接依存しません。永続化 HOW は [`storage_spec.md`](./storage_spec.md) / [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md) を正本とします。
本仕様は、「ユースケースから見たストレージを、リポジトリ・インターフェースとして抽象化する」ことのみを定めます。

## ユースケースと Kotlin Multiplatform (KMP)

共有対象と優先順位は [`architecture.md`](./architecture.md)、HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とします。
本仕様は、「ユースケースの目的/成功条件が、プラットフォーム UI に依存しない」ことのみを定めます。

### 候補

共有候補の一覧は [`architecture.md`](./architecture.md) の共有ロジック対象を正本とします。

## プラットフォーム固有のユースケース

ナビゲーション / ディープリンク / 画面の向き / About Window 等の HOW は [`navigation_spec.md`](./navigation_spec.md) / [`ui-viewport.md`](./ui-viewport.md) / [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md) を正本とします。
本仕様は、「それらの目的の意味論を共通化できる場合に、共有対象としてよい」ことのみを定めます。

## ユースケース状態モデル

遷移の形式は [`state_machine.md`](./state_machine.md) を正本とします。
本仕様は、「ユースケース実行を、アイドル / 実行中 / 成功 / 失敗 / キャンセル として扱い、オフライン時は、ローカルデータを結果として返してよい」ことのみを定めます。

## ユースケースの結果

ユースケースの結果は、UI 表示自体を返しません。ドメイン/アプリケーション・モデル、または `Result<T, ApplicationError>` を返します。SwiftUI.View / Composable / NavigationStack / アラート / シート / Toast を返してはなりません。

## エラーのモデル

エラー型は [`models_spec.md`](./models_spec.md)、境界の分類は [`architecture.md`](./architecture.md) を正本とします。
本仕様は、「ユースケースが `ApplicationError` を返し、プロバイダ固有の例外を UI に直接公開しない」ことのみを定めます。

## 冪等 (べきとう) 性

可能なユースケースは、冪等 (べきとう) に設計します。

たとえば、お気に入りの追加:

`お気に入りの追加` を二回実行しても `お気に入り = true` という一つの状態になることを基本とします。スナップショットの重複排除は [`domain_rules.md`](./domain_rules.md) を正本とします。

## 並行処理

同一ユースケースが短時間に複数回実行された場合の挙動を定義します。

たとえば `リフレッシュ`:

`リフレッシュ`、`リフレッシュ`、`リフレッシュ` が同時実行される場合、`リクエスト 1`、`リクエスト 2`、`リクエスト 3` を無制限に、プロバイダに送信してはなりません。

必要に応じて、下記を採用します。

* 重複排除
* リクエスト結合
* キャンセル
* 最後のリクエストが勝つ

具体的なキャッシュ/リクエストの方針は [`cache_spec.md`](./cache_spec.md) を信頼できる情報源 (SoT) とします。

## アクセシビリティ

アクセシビリティは [`ui.md`](./ui.md) を正本とします。
本仕様は、「主要ユースケースの目的が、アクセシビリティ操作でも達成できる」ことのみを定めます。

## アダプティブ UI

Viewport /「リスト・詳細」は [`ui-viewport.md`](./ui-viewport.md) / [`navigation_spec.md`](./navigation_spec.md) を正本とします。
本仕様は、「ユースケースの目的が Viewport サイズに依存しない」ことのみを定めます。

## 状態復元

復元対象は [`application_state.md`](./application_state.md) を正本とします。
本仕様は、「中断したユースケース・コンテキスト (例: パッケージ/期間) を、可能な範囲で、再開し、古いリモートデータを `最新` として扱わない」ことのみを定めます。

## UC-01: ダッシュボードを表示する

### 目的

ユーザーが、S2J Package Dashboard の現在の状態を把握すること。

### 前提条件

* アプリケーションが起動している
* ローカルデータを利用可能

### 成功

お気に入り/統計サマリーの現状が把握できます。管理対象の取得は [UC-02](#uc-02-管理対象のパッケージを取得する) です。ローカルがなければ、初回取得として扱えます。オフラインなら、ローカル表示として扱えます。

操作経路は [`ux_flows_spec.md` アプリケーション起動のフロー](./ux_flows_spec.md#アプリケーション起動のフロー) / [`ux_flows_spec.md` ダッシュボードのフロー](./ux_flows_spec.md#ダッシュボードのフロー) / [`ux_flows_spec.md` オフラインのフロー](./ux_flows_spec.md#オフラインのフロー) を正本とします。
画面の表示内容は [`screen_spec.md`](./screen_spec.md) を正本とします。

### 代替

* ローカルデータがない: 初回取得として扱う。
* ネットワークが使えない: ローカルを表示し、オフラインであることを誤認させない。

### 関連

* [`ux_flows_spec.md`](./ux_flows_spec.md)
* [`screen_spec.md`](./screen_spec.md)
* [`storage_spec.md`](./storage_spec.md)

## UC-02: 管理対象のパッケージを取得する

### 目的

実装時期は [優先順位-1](#優先順位-1) を正本とします。認証の設定は [UC-16](#uc-16-packagist-認証を設定する) を正本とします。

* 統計期間
* フィルター
* ソート順序
* スプリット・ビューの選択

### 成功

復元対象として定義された状態が、可能な範囲で、戻ります。何を残すかは [`application_state.md`](./application_state.md)、経路は [`ux_flows_spec.md` 状態復元のフロー](./ux_flows_spec.md#状態復元のフロー) を正本とします。

## UC-31: 設定を変更する

### 目的

ユーザーが、アプリケーション・ユーザー設定 (Preference) を、変更すること。

対象例:

* 統計期間
* リフレッシュの方針
* ユーザー設定 (Preference) の表示
* ソート順序
* 外観

### 成功

妥当な設定が永続化され、即座に適用されます。設定変更によってアプリケーション・データを削除しません。設定画面から About を表示できることを確認します。表示内容は [UC-32](#uc-32-about-を表示する) を正本とします。

実装時期は [優先順位-2](#優先順位-2) を正本とします。初期バージョンの最優先ではありません。
経路は [`ux_flows_spec.md` 設定のフロー](./ux_flows_spec.md#設定のフロー) を正本とします。

## UC-32: About を表示する

### 目的

ユーザーが、アプリケーション情報を、確認すること。

### 成功

既存の [S2J About Window](https://github.com/stein2nd/s2j-about-window) で、アプリケーション情報を確認できます。実装詳細は、既存パッケージの仕様に従います。

経路は [`ux_flows_spec.md` About のフロー](./ux_flows_spec.md#about-のフロー) を正本とします。経路は、設定画面から About を開くことだけです。表示できることの確認は [UC-31](#uc-31-設定を変更する) を正本とします。実装時期は [優先順位-2](#優先順位-2) の UC-31に従います。初期バージョンの最優先ではありません。

## UC-33: エラーから復旧する

### 目的

ユーザーが、エラー発生後にアプリケーションを、利用可能な状態に戻すこと。

### エラー・カテゴリー

* ネットワーク・エラー
* 認証エラー
* レート制限
* プロバイダ・エラー
* データ・エラー
* 永続化エラー

### 成功

失敗理由が分かり、次のいずれかで復旧できます。リトライ/ローカルデータの使用/再認証/設定のオープン/Back。

経路は [`ux_flows_spec.md` エラー・リカバリーのフロー](./ux_flows_spec.md#エラーリカバリーのフロー)、横断表示は [`ui.md`](./ui.md) を正本とします。

## UC-34: データ・エクスポートを実行する

### 目的

ユーザーが、ローカルデータまたは統計を、外部ファイルとして保存すること。

### 初期範囲

実用最小限の製品 (MVP) では、必須としません。

### 成功 (将来)

対象データを選び、クレデンシャル (資格情報) を含めないファイルを、システム共有 UI/ Save で保存できます。

## UC-35: データ・インポートを実行する

### 目的

エクスポート済みのアプリケーション・データを、インポートすること。

### 初期範囲

実用最小限の製品 (MVP) では、必須としません。

### 成功 (将来)

ファイルを検証、プレビューした後で、インポートします。不正なファイルによって、既存データを破壊しません。
