# S2J Package Dashboard - リリース仕様

## 概要

本ドキュメントは、S2J Package Dashboard の初期設計における、リリース方針を定義します。リリース 条件の正本です。

## 目的

本仕様は、リリースに関する基本方針、バージョニング、リリース候補 (RC)、検証、配布、リリース後の確認およびロールバックの方針を定義します。リリース条件の正本です。

## 非目的

本仕様は、CI ジョブの詳細手順、日常の PR 検証、アプリケーション機能自体を定義しません。

## 責務

何をもってリリースとするか、バージョン番号、品質ゲート、配布、ホットフィックス/ロールバックを定義します。

## 非責務

CI/CD パイプラインは [`cicd.md`](./cicd.md) を正本とします。

## リリースの原則

S2J Package Dashboard のリリースは、下記の原則に従います。

1. `main` は、常にリリース可能な状態を維持する。
2. リリースされるバージョンは、Git タグによって一意に識別する。
3. リリース前に、CI 品質ゲートを通過する。
4. リリース成果物は、検証済みのコミットから生成する。
5. リリース・バージョンとソースコード・コミットの対応関係を追跡可能にする。
6. クレデンシャル (資格情報)、署名鍵、API Token 等の Secret を Git リポジトリに保存しない。
7. プラットフォーム固有な配布処理は、共通リリースの方針と分離する。
8. リリース後に最低限のスモーク・テストを実施する。
9. 課題が発生した場合に、影響範囲を限定してロールバックまたはホットフィックスを実施できる状態を維持する。

## バージョン管理

### バージョン管理の方針

アプリケーション・バージョンは、セマンティックなバージョン管理を基本とします。

`MAJOR.MINOR.PATCH`

例:

* `1.0.0`
* `1.1.0`
* `1.1.1`
* `2.0.0`

Git タグは、下記の形式とします。

`vMAJOR.MINOR.PATCH`

例:

* `v1.0.0`
* `v1.1.0`
* `v1.1.1`

GitHub でも、セマンティックなバージョン管理にもとづく、リリース・タグが推奨されています。

(参考: [Releasing and maintaining actions - GitHub Docs](https://docs.github.com/en/actions/how-tos/create-and-publish-actions/release-and-maintain-actions))

### MAJOR バージョン

下記の場合に、MAJOR バージョンをカウントアップします。

* 既存ユーザーに影響する、重大な仕様変更
* 既存設定・データとの互換性を維持できない、変更
* 公開 API/データモデル/永続化モデルの、破壊的変更
* 移行が必要となる、重大な変更

例:

`1.5.3 → 2.0.0`

### MINOR バージョン

下記の場合に、MINOR バージョンをカウントアップ します。

* 後方互換性を維持した、新機能
* 新しいスクリーン
* 新しい統計
* 新しいパッケージ管理機能
* 新しいプラットフォームのサポート

例:

`1.2.3 → 1.3.0`

### PATCH バージョン

下記の場合に、PATCH バージョンをカウントアップします。

* バグ修正
* セキュリティ修正
* UI/UX の軽微な修正
* パフォーマンスの改善
* ドキュメントの修正のみではなく、アプリケーション挙動に影響する、軽微な変更

例:

`1.2.3 → 1.2.4`

## プレリリース版

リリース候補 (RC) 等のプレリリース版には、プレリリース識別子を使用できます。プレリリースは、本番リリースと区別します。

例:

* `1.0.0-alpha.1`
* `1.0.0-beta.1`
* `1.0.0-rc.1`

Git タグ:

* `v1.0.0-alpha.1`
* `v1.0.0-beta.1`
* `v1.0.0-rc.1`

## リリース・チャネル

下記は、リリースを、チャネルに分類したものです。

| チャネル | 目的 |
| --- | --- |
| 開発 | 開発中の検証 |
| 内部 | 開発者・関係者による検証 |
| ベータ | 外部を含む事前検証 |
| リリース候補 (RC) | 本番 リリース 候補 |
| 本番 | 一般ユーザー向け正式版 |

## リリース候補 (RC)

### 目的

リリース候補 (RC) は、本番リリース候補として、十分な検証を完了したビルドとします。

原則として、RC は、単なるベータ・ビルドではなく、下記を満たします。

* 機能実装の完了
* バージョンの確定
* ドキュメントの更新済み
* CHANGELOG の更新済み
* 既知 Issue の確認済み

必須のテスト・スイートは [`testing_spec.md` リリース候補 (RC) テスト](./testing_spec.md#リリース候補-rc-テスト) を正本とします。
RC ビルドは、本番ビルドと同じシステム設定 (Configuration) を使用します。

### リリース候補 (RC) タグ

既存の RC タグを書き換えません。

RC には、下記の形式を使用します。

`v1.0.0-rc.1`

RC に重大な課題が発見された場合は、修正版を新しい RC とします。

* `v1.0.0-rc.1`
* `v1.0.0-rc.2`
* `v1.0.0-rc.3`

* [ ] PR が、必要な範囲でマージ済みである

### CI

* [ ] CI が、成功している
* [ ] ユニットテストが、成功している
* [ ] 結合テストが、成功している
* [ ] 静的解析が、成功している
* [ ] ドキュメント・チェックが、成功している
* [ ] セキュリティ・チェックが、成功している

### ドキュメント

* [ ] [`CHANGELOG.md`](../CHANGELOG.md) が、更新されている
* [ ] [`README.md`](../README.md) の「バージョン依存の情報」が、更新されている
* [ ] `./docs/` の関連仕様が、更新されている
* [ ] `./docs_mod/` の実装管理が、必要に応じて、更新されている
* [ ] リリースノートを作成できる状態である

### バージョン

* [ ] アプリケーション・バージョンが、確定している
* [ ] Git タグが、未使用である
* [ ] iOS/iPadOS のバージョン/ビルド番号が、整合している
* [ ] Android のバージョン・コード/バージョン名が、必要に応じて、更新されている

## バージョン更新

リリース・バージョンを確定した後、アプリケーションのバージョン 情報を更新します。

バージョン情報を複数の箇所で管理する場合、それぞれが同一リリース・バージョンを指すことを確認します。

例:

`MARKETING_VERSION = 1.0.0`

ビルド番号は、アプリケーション・バージョンとは独立して、管理します。ビルド番号は、同一プラットフォーム内で、重複させません。

* Version: 1.0.0
* ビルド: 100

## Git タグ

リリース・バージョンを確定したら、対応する Git タグを作成します。

`v1.0.0`

タグは、リリース対象コミットに直接対応させます。

`main` 上のリリース・コミットに `v1.0.0` を付けます。

リリース・タグ作成後、そのタグが指すコミットを変更しません。

リリースに対応する GitHub Release は、可能な限り、不変なリリース成果物として扱います。

* バージョン
* リリース日
* 概要
* 追加機能
* 変更点
* 修正点
* セキュリティ
* 既知の Issue
* 対応プラットフォーム
* ビルド情報
* ソースコードのコミット

## iOS/iPadOS リリース

### ビルド

iOS/iPadOS ビルドは、CI/CD により、再現可能な形で生成します。

基本的な流れは、下記とします。

* Git タグを起点に、CI でビルド/テスト/アーカイブ/検証し、App Store Connect にアップロード

CI ジョブの順序は [`cicd.md` リリース・パイプライン](./cicd.md#リリースパイプライン) を正本とします。
本節は、「iOS/iPadOS 成果物の提出先が App Store Connect である」ことのみを定めます。

### TestFlight

本番リリース前に、必要に応じて、TestFlight を利用します。

TestFlight では、内部テスター/外部テスターを使い分けます。

Apple の App Store Connect では、TestFlight にビルドをアップロードし、テスターに配布して検証できます。外部テスターに対しては、Apple による事前審査 (ベータ・アプリケーション・レビュー) が必要となる場合があります。

(参考: [TestFlight overview - Test a beta version - App Store Connect - Help - Apple Developer](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview))

TestFlight 検証項目:

* [ ] アプリケーション起動
* [ ] パッケージリスト
* [ ] パッケージ詳細
* [ ] 検索 (実装時期は [`use_cases.md` 優先順位-1](./use_cases.md#優先順位-1) の UC-04)
* [ ] リフレッシュ
* [ ] 統計
* [ ] GitHub 連携 (実装時期は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) の UC-17)
* [ ] 認証 (Packagist は [`use_cases.md` 優先順位-1](./use_cases.md#優先順位-1) の UC-16。GitHub 認証以降は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) の UC-17〜 UC-20)
* [ ] オフライン/キャッシュ
* [ ] ナビゲーション
* [ ] iPhone
* [ ] iPad
* [ ] 画面回転
* [ ] アクセシビリティ

## App Store リリース

本番リリースの iOS/iPadOS ビルドは、App Store Connect から、Apple による事前審査 (アプリケーション・レビュー) に提出します。

基本的な流れは、下記の通りです。

* TestFlight →リリース候補 (RC) 検証→ App Store Connect →アプリケーション・レビュー→承認→リリース→本番検証

Apple の公式リリースのフローでも、TestFlight によるベータ検証後、最終ビルドをアプリケーション・レビューに提出して、App Store で公開する流れが基本となります。

(参考: [Distributing your app for beta testing and releases | Apple Developer Documentation](https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases))

## Android リリース

Android は、今後のターゲットです。時期は [`overview.md`](./overview.md) を正本とします。開発に着手したあと、[Google Play Console](https://developer.android.com/distribute/console) を利用します。

テストは、Android 版の開発に着手したタイミングで、iOS/iPad トラックと Android トラックに分けます。

Android トラックの流れは、下記です。

* Git タグを起点に、CI でビルド/テストし、成果物を Android App バンドル (AAB) として、内部テスト、クローズド・テスト/オープン・テストを経て、本番

CI ジョブの順序は [`cicd.md` リリース・パイプライン](./cicd.md#リリースパイプライン) を正本とします。
本節は、「着手後の Android トラックが、Google Play の提出形式とストア上のテスト・トラックに従う」ことのみを定めます。

Google Play では、AAB を基本的な公開形式として使用します。

(参考: [Inspect app versions on the Latest releases and bundles page - Play Console Help](https://support.google.com/googleplay/android-developer/answer/9844279?hl=en))

テスト・トラックは、必要に応じて、下記を使用します。

* 内部テスト
* クローズド・テスト
* オープン・テスト
* 本番

Google Play Console は、これらのテスト・トラックと本番をリリース単位で管理できます。

(参考: [Prepare and roll out a release - Play Console Help](https://support.google.com/googleplay/android-developer/answer/9859348/prepare-and-roll-out-a-release?hl=en-GB))

* S2J Package Dashboard v1.2.0

## リリース・インシデント

本番リリース後に、重大な課題が確認された場合、Issue の深刻度を判定します。致命的/高の課題については、通常のリリース・サイクルを待たずに、ホットフィックス・リリースを検討します。

| 深刻度 | 説明 | アクション |
| --- | --- | --- |
| 致命的 | 起動不能・重大なデータ破壊・重大なセキュリティ Issue | リリース停止/ホットフィックス |
| 高 | 主要機能が利用不能 | ホットフィックス検討 |
| 中程度 | 一部機能に課題 | 次回リリースまたはホットフィックス |
| 低 | 軽微な UI/UX Issue | 次回リリース |

## ホットフィックス

ホットフィックスは、本番バージョンに対する緊急修正版とします。

ホットフィックスでも、通常の CI 品質ゲートを省略しません。

ただし、致命的インシデントの場合は、必要最小限の検証に絞った緊急リリース・プロセスを使用できます。

緊急リリース後は、通常の CI/テスト/ドキュメントを追補して、状態を正規化します。

例: `1.2.0` に対するホットフィックスは、`1.2.1`

## ロールバック

ロールバックは、下記の場合に検討します。

* 致命的クラッシュ
* アプリケーション起動の失敗
* 致命的セキュリティ Issue
* 重大なデータの破損
* 重大な API の互換性の失敗

モバイル・アプリケーションのストア・リリースは、Web サービスのように即時に、全ユーザーを旧バージョンに戻せるとは限りません。

そのため、基本戦略は、下記とします。

* インシデント→リリース停止→可能な範囲で、サーバー側挙動をオフ→ホットフィックス→緊急リリース

サーバー側機能フラグ等で制御可能な機能については、リリース・ロールバックよりも、機能オフを優先できます。

## リリース成果物

リリース成果物は、リリース・バージョンとソースコード・コミットを追跡可能な状態で保存します。成果物の生成元を、後から特定できないビルドを本番リリースに使用しません。

最低限、下記を記録します。

* アプリケーション・バージョン
* ビルド番号
* Git タグ
* Git コミット SHA
* ビルド日
* プラットフォーム
* CI ワークフローの実行

例:

* Version: 1.0.0
* Build: 100
* Tag: v1.0.0
* Commit: <SHA>
* Platform: iOS

## 再現性

可能な限り、同一ソースコード・コミットから、同一リリース成果物を再生成できる状態を維持します。CI では `latest` に依存しすぎず、本番リリースに使用するツールチェーンを明示的に管理します。

そのために、下記を管理します。

* Xcode バージョン
* Swift バージョン
* Swift パッケージの依存関係バージョン
* Android SDK バージョン
* Kotlin バージョン
* Gradle バージョン
* Gradle の依存関係バージョン
* ビルドシステム設定 (Configuration)
* CI ランナーのイメージ

## Secrets と署名

リリースに必要なクレデンシャル (資格情報) /署名素材は、リポジトリに保存しません。

Secrets は、GitHub アクション Secrets/環境 Secrets 等の安全な Secret ストアを利用します。

本番リリースでは、可能な限り、専用環境を使用し、リリース承認を必要とします。

対象:

* Apple 署名証明書
* Apple プロビジョニング情報
* App Store Connect クレデンシャル (資格情報)
* App Store Connect API キー
* Google Play サービスのアカウント・クレデンシャル (資格情報)
* Android 署名鍵
* Packagist API Token
* GitHub Token

## リリース承認

本番リリースは、自動ビルドと自動リリースを、必ずしも同一処理としません。

推奨フロー:

* タグ→ CI →ビルド→テスト→成果物→リリース候補 (RC) →手動承認→本番配布

CI ジョブの順序は [`cicd.md`](./cicd.md) を正本とします。
本節は、「CI 成功だけで、本番リリースを自動実行しない」ことのみを定めます。

## 実用最小限の製品 (MVP) リリースの方針

対象機能は [`use_cases.md`](./use_cases.md) の MVP ユースケースを正本とします。
本節は、「リリースに必要な成果物とゲート」を定義します。

機能一覧は再掲しません。

実用最小限の製品 (MVP) では、リリース自動化を過度に複雑化せず、[リリース承認](#リリース承認) の手動承認を基本形とします。

### 必須

* セマンティックのバージョン管理
* Git タグ
* GitHub Release
* CI 品質ゲート
* CHANGELOG
* iOS/iPadOS TestFlight
* iOS/iPadOS 本番リリース
* デバイスのスモーク・テスト
* リリース・チェックリスト
* 本番での事後チェック

### 将来

* Android 本番リリース
* ストアへの自動提出
* リリースノートの自動生成
* 自動ロールバック
* 機能フラグ
* SBOM
* 成果物の認証

## 最終公開の方針

S2J Package Dashboard のリリースは、**「検証済みのソースコード・コミットを、明確なバージョンとして固定し、再現可能な成果物を生成し、プラットフォーム固有な配布経路を経て、本番に公開する」** ことを基本とします。

リリースの成功条件は、単にビルドが成功することではなく、ソースコード/バージョン/CI/テスト/成果物が、リリース準備完了として追跡可能であり、その後、配布とリリース後検証までたどれることとします。
