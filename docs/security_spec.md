# S2J Package Dashboard - セキュリティ・権限・プライバシー仕様

## 概要

本ドキュメントは、S2J Package Dashboard の初期設計における、セキュリティ/権限/プライバシーを定義します。

外部 API、OS セキュリティ・モデル、Kotlin Multiplatform (KMP)、サードパーティ製 SDK、クラウド同期等の変更に応じて、更新します。

セキュリティ上重大な変更については、ADR およびセキュリティ・レビューを実施します。

## 目的

本ドキュメントでは、セキュリティ、権限およびプライバシーに関する仕様を定義します。ユーザーデータ保護、安全な通信、最小権限、個人情報の最小化、オフライン/バックアップ時のセキュリティ、プラットフォーム間の方針一貫を目的とします。

## 非目的

本仕様は、認証自体の詳細、特定 OS API の呼び出し手順、サードパーティ SDK の導入を目的としません。

## 責務

セキュリティ原則、権限、プライバシー、ログに Secret を出さないこと、安全な失敗を正本とします。

## 非責務

認証/クレデンシャル (資格情報) は [`authentication_spec.md`](./authentication_spec.md) を正本とします。
API 固有のセキュリティは各 API 仕様、ストレージ実装差分は [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md)、共有対象は [`architecture.md`](./architecture.md)、Kotlin Multiplatform (KMP) の HOW は [`kmp_spec.md`](./kmp_spec.md)、検証の種類は [`testing_spec.md`](./testing_spec.md)、リリース 可否は [`release.md`](./release.md) を参照します。

## セキュリティ原則

S2J Package Dashboard では、下記を基本原則とします。

1. 最小権限の原則
2. データの最小化
3. 「デフォルトで、Secure」
4. 「デフォルトで、プライバシー保護」
5. 「匿名」ファースト
6. 「ローカル」ファースト
7. クレデンシャル (資格情報) の分離
8. Secure ストレージ
9. 明示的な同意
10. 安全な失敗

## セキュリティ境界

アプリケーション全体を下記の境界に分離します。層の依存方向は [`architecture.md`](./architecture.md) を正本とします。
本仕様は、「クレデンシャル (資格情報) 境界 (Secure ストレージ) を通常のインフラストラクチャー (Packagist / GitHub / ストレージ) から分離する」ことのみを定めます。

クレデンシャルは、通常のアプリケーション・データと分離します。

## 脅威モデル

主要な脅威アクターは、下記の通りです。すべての脅威を完全に防止することを目的とせず、アプリケーションのリスクを合理的に低減します。

* ネットワーク攻撃者 / 不正アプリケーション / 不正ユーザー / 盗難デバイス / 侵害されたデバイス / リバース・エンジニアリング / サプライチェーン攻撃者 / 偶発的な開示

## 保護対象アセット

保護対象: Packagist / GitHub クレデンシャル (資格情報)、アカウント・メタデータ、お気に入りのパッケージ、統計スナップショット、ユーザー設定 (Preference)、キャッシュ済み API データ、アプリケーション システム設定 (Configuration)、ソースコード/署名アセット。

特に API Token / アクセス Token / リフレッシュ Token / 認証 Secret をハイ・センシティブとして扱います。分類は [`authentication_spec.md`](./authentication_spec.md) を正本とします。

## データの分類

下記は、アプリケーション・データを分類したものです。

### 公開

外部サービスから公開されている情報。

* パッケージ名
* パッケージ説明
* パッケージ・バージョン
* GitHub スター数
* GitHub フォーク数
* 公開リリース
* 公開ダウンロード統計

### 内部

ユーザー固有だが、クレデンシャル (資格情報) 自体ではない情報。

* 「お気に入り」
* ユーザー設定 (Preference)
* 統計スナップショット
* キャッシュ
* 表示設定

### 機密

認証/クレデンシャル (資格情報) に関連する情報。

* API Token
* アクセス Token
* リフレッシュ Token
* 認証 Secret

## データの最小化

アプリケーションは、目的達成に必要なデータだけを取得・保存します。

たとえば、下記が API レスポンスに含まれていても、ダッシュボードに不要であればドメイン・モデルに取り込みません。

* ユーザー名
* メール・アドレス
* プロファイル情報

## 利用目的の限定

取得したデータは、取得時に定めた目的以外に利用しません。広告 / ユーザー・プロファイリングに利用しません。

例: GitHub トラフィックを統計可視化に使用する

## 「匿名」ファースト

公開情報の取得については認証を要求しません。不要なクレデンシャル (資格情報) 付与の禁止は [`authentication_spec.md`](./authentication_spec.md) を正本とします。
本仕様は、「匿名ファーストが脅威低減 (Token 露出面の縮小) である」ことのみを定めます。

## 外部サービスデータ

外部サービスから取得したデータについて、下記を、それぞれのソース情報として保持します。異なるプロバイダから取得したデータを、ユーザー情報として勝手に統合しません。

* Packagist データ
* GitHub データ

## クレデンシャル (資格情報) の分離

クレデンシャル (資格情報) をアプリケーション・データから分離する方針は [`authentication_spec.md`](./authentication_spec.md) を正本とします。
本仕様は、「分離が破れた場合の脅威 (ログ、バックアップ、権限)」を扱います。

## Secure ストレージ

クレデンシャル (資格情報) はプラットフォームが提供する Secure ストレージを利用します。何を置いてよいかは [`authentication_spec.md`](./authentication_spec.md)、Keychain の HOW は [`ios_spec.md`](./ios_spec.md)、Keystore の HOW は [`android_spec.md`](./android_spec.md) を正本とします。

## Kotlin Multiplatform (KMP) セキュリティ境界

KMP 移行後も、プラットフォーム固有の Secure ストレージを共通コードに直接持ち込みません。配置は [`kmp_spec.md`](./kmp_spec.md) を正本とします。

## パスワード方針

パスワードを保存しないことは [`authentication_spec.md`](./authentication_spec.md) を正本とします。
本仕様は、「パスワードがデータベース / UserDefaults / SharedPreferences / ファイルに残らない」ことのみを定めます。

## Token の方針

Token について下記を禁止します。

* ソースコードへの埋め込み
* リポジトリへのコミット
* アプリケーション・バンドルへの固定値埋め込み
* 通常ログへの出力
* アナリティクスへの送信
* クラッシュ・レポートへの送信
* スクリーンショットへの表示
* クリップボードへの自動保存

## Token の表示

生の Token を UI に出しません。必要な場合はマスクします。全文を再表示する機能は提供しません。UI に出してよい状態の一覧は [`authentication_spec.md`](./authentication_spec.md) を正本とします。

## ネットワーク・セキュリティ

外部 API との通信には HTTPS を必須とします。`http://` は拒否し、`https://` は許可します。本番環境で HTTP 通信にフォールバックしません。

## TLS

TLS 証明書検証を無効化しません。開発環境で例外を設ける場合、本番ビルドに含めません。

禁止:

* すべての証明書を信頼
* 証明書検証をオフ
* TLS エラーを無視

## API ホスト規制

クレデンシャル (資格情報) を送信するホストを限定します。GitHub クレデンシャル (資格情報) を Packagist ホストに送信しません。

例: Packagist クレデンシャルは Packagist API、GitHub クレデンシャルは GitHub API。

## 認可ヘッダー

認可ヘッダーをロギングしません。HTTP デバッグロガーを使用する場合も、クレデンシャル (資格情報) を Redact します。

例:

`Authorization: Bearer <redacted>`

## URL クレデンシャル (資格情報) の方針

クレデンシャル (資格情報) を URL に含めません。原則として、HTTP 認可ヘッダー等を利用します。プロバイダ固有の仕様については各 API 仕様を正本とします。

禁止:

`https://example.com/api?token=SECRET`

## HTTP リダイレクト

クレデンシャル (資格情報) 付きリクエストが、意図しないホストにリダイレクトされた場合に、クレデンシャルを送信しません。

リダイレクト時には、オリジナル・ホストからリダイレクト・ホストに移る前に、クレデンシャル範囲をチェックします。

## キャッシュ・セキュリティ

API レスポンスをキャッシュする場合、クレデンシャル (資格情報) を含むレスポンスを通常キャッシュに保存しません。

キャッシュには必要な公開/アプリケーション・データのみを保存します。

## デリケートな対応

認可済み API レスポンスに個人情報やクレデンシャル (資格情報) 関連データが含まれる場合、必要な情報だけをドメイン・モデルにマッピングします。

不要なレスポンス全体を永続保存しません。

## アプリケーション・ストレージ

アプリケーション・ストレージには、下記を保存可能とします。クレデンシャル (資格情報) は、除外します。

* お気に入り
* パッケージのメタデータ・キャッシュ
* GitHub リポジトリ・キャッシュ
* 統計スナップショット
* ユーザー設定 (Preference)
* UI ユーザー設定 (Preference)

## 「統計」プライバシー

統計スナップショットには、必要な統計値のみを保存します。不要なユーザー ID を一緒に保存しません。

例:

* `repository`
* `metric`
* `value`
* `capturedAt`
* `source`

## 「お気に入り」プライバシー

お気に入りはユーザー設定 (Preference) として扱います。お気に入り情報を外部サービスに送信しません。初期バージョンではサーバーに送信しません。

## 「ローカル」ファースト・プライバシー

初期バージョンでは、ユーザー固有データを S2J Package Dashboard 独自サーバーに送信しないことを基本とします。ユーザーデータは、デバイス上に置きます。

## アカウント登録は必須ではない

S2J 独自アカウントを必須としないことは [`authentication_spec.md`](./authentication_spec.md) を正本とします。
本仕様は、「インストール→起動だけで公開データを使えることが、プライバシー方針である」ことのみを定めます。

## 権限の最小化

OS 権限は、必要になった場合のみ要求します。権限が不要な機能ではリクエストしません。

## 権限一覧

初期バージョンでは、可能な限り、追加 OS 権限を必要としない設計を目指します。不要な権限を要求しません。

想定:

* ネットワーク: 必須
* 通知: 任意/将来予定
* 写真 / 連絡先 / 位置情報 / Bluetooth / マイク / カメラ: 必須ではない

## ネットワーク権限

ネットワーク通信は本アプリケーションの主要機能です。

Packagist/GitHub API に HTTPS 通信します。

ネットワーク障害時にも、ローカル・キャッシュが存在する場合は、可能な範囲で、オフライン表示します。

## 通知

通知機能を実装する場合、ユーザーによる明示的なオプトインを基本とします。

たとえば、下記を将来実装する場合も、通知権限をアプリケーション起動時に無条件要求しません。

* パッケージ更新の通知
* セキュリティ告知の通知

## バックグラウンド処理

バックグラウンド処理を利用する場合、下記の目的に限定します。バックグラウンド処理で取得するデータは、フォアグラウンド処理と同じプライバシー方針に従います。

* 統計スナップショット
* パッケージ更新のチェック
* セキュリティ告知のチェック

## バックグラウンド・クレデンシャル (資格情報)

バックグラウンド処理でクレデンシャル (資格情報) を使用する場合でも、クレデンシャルをバックグラウンド・タスクの引数、永続化ジョブ・データ、ログ等に保存しない。

クレデンシャルは実行時に Secure ストレージから取得します。

## アプリケーションのライフサイクル

アプリケーションがバックグラウンドに移行した場合、機密 UI データを、可能な限り、保護します。

特に App Switcher スナップショット等に、下記が表示されないようにします。プラットフォーム固有の対策は、プラットフォーム仕様で定義します。

* Token
* 非公開リポジトリ
* アカウント情報

## クリップボード

アプリケーションからクレデンシャル (資格情報) をクリップボードに自動コピーしません。

お気に入り/パッケージ名等の、ユーザーが明示的にコピーした公開/内部データについては、通常のクリップボード方針に従います。

## 共有シート

共有機能を提供する場合、クレデンシャル (資格情報) や機密データを共有対象に含めません。たとえばパッケージ共有では、下記を共有可能とします。Token を含む URL を生成しません。

* パッケージ名
* パッケージ URL
* リポジトリ URL

## スクリーンショット

通常の UI にクレデンシャル (資格情報) を表示しません。

また、認可済みユーザーデータを表示するスクリーンについて、必要に応じて、スクリーンショット/画面キャプチャーへの対策を検討します。

プラットフォーム固有の仕様は、下記で定義します。

* [`ios_spec.md`](./ios_spec.md)
* [`android_spec.md`](./android_spec.md)

## ロギング

ログには下記を出力しません。

*  パスワード
* API Token
* アクセス Token
* リフレッシュ Token
* 認可ヘッダー
* 非公開キー
* クライアント Secret

## 本番ロギング

本番ビルドでは、デバッグ目的の詳細 HTTP ロギングを無効化します。

必要な診断情報のみをロギングします。

## エラーメッセージ

ユーザー向けエラーメッセージに、下記を含めません。

* アクセス Token
* 認可ヘッダー
* 内部 URL
* 非公開リポジトリ・データ

## クラッシュ報告

クラッシュ報告を導入する場合、機密データを送信しません。最低限、下記を除外します。

* クレデンシャル (資格情報)
* Token
* 非公開リポジトリ・コンテンツ
* ユーザー 個人情報

## アナリティクス

アナリティクスを導入する場合、「デフォルトで、プライバシー保護」とします。アナリティクス導入時には、収集項目を別途明示します。

送信してよい情報:

* スクリーン・ビュー
* 機能 の使い方
* パフォーマンス指標
* クラッシュ・フリーの状態

送信しない情報:

* Token
* パスワード
* メール・アドレス
* 非公開リポジトリ名
* 「お気に入り」パッケージリスト
* Raw API レスポンス

## ユーザー識別

初期バージョンでは、S2J Package Dashboard 独自のユーザー ID を発行しません。

外部サービスのアカウント ID を利用する場合も、必要な目的に限定します。

## サードパーティ製 SDK

サードパーティ製 SDK を追加する場合、セキュリティ/プライバシー・レビューを実施します。目的が不明確な SDK を導入しません。

確認項目:

* データ・コレクション
* データ送信
* 権限
* 追跡
* クラッシュ報告
* アナリティクス
* ネットワーク・アクセス
* サードパーティ・サーバー

## 依存関係セキュリティ

外部の依存関係について、下記を確認します。依存関係の更新時には、既知のセキュリティ脆弱性を確認します。

* ソース
* バージョン
* ライセンス
* セキュリティ告知
* メンテナンス・ステータス

## サプライチェーン・セキュリティ

依存関係/ビルドツールについて、可能な限り、バージョンを Pin または再現可能な状態にします。

CI で依存関係を取得する場合、信頼できるレジストリ/ソースのみを利用します。

## ビルドのセキュリティ

リリース・ビルドでは、下記を含めません。開発システム設定 (Configuration) と 本番システム設定を分離します。

* デバッグ・ロギング
* テスト・クレデンシャル (資格情報)
* 開発エンドポイント
* デバッグ・フラグ

## ソースコード中の Secret

下記をソースコードにコミットしません。

* API Token
* 非公開キー
* パスワード
* クライアント Secret
* 署名クレデンシャル (資格情報)

## CI Secret

CI で Secret が必要な場合は、CI プロバイダの Secret ストアを利用します。

Secret は、下記にコミットしません。

* リポジトリ
* ワークフロー・ファイル
* .plist
* .json
* .env

## Secret スキャン

リポジトリで Secret スキャンの有効化を推奨します。

誤コミットが発生した場合、検出→無効化→ローテーション→クリーンアップを実施します。

Git 履歴から文字列を削除するだけでは、クレデンシャル (資格情報) が有効なまま残る可能性があるため、無効化/ローテーションを優先します。

## コード署名

リリース・ビルドは、プラットフォームのコード署名を利用します。署名クレデンシャル (資格情報) をソース・リポジトリに保存しません。

* iOS/iPadOS: Apple コード署名
* Android: Android アプリケーション署名

## リバース・エンジニアリング

モバイル・アプリケーションは、完全に Secret を隠蔽できる環境ではないことを前提とします。

そのため、下記をネイティブ・アプリケーションに埋め込みません。

* API Secret
* クライアント Secret
* 非公開キー

## 公開クライアント原則

iOS/iPadOS/Android アプリケーションを完全に信頼されたクライアントとはみなしません。

アプリケーション・バンドルに含まれる情報は、最終的に解析可能であることを前提とします。

## クライアント Secret

OAuth 等でクライアント Secret が必要な場合、ネイティブ・アプリケーションに埋め込みません。

必要な場合は、バックエンドを介したフロー、またはプロバイダがネイティブ・アプリケーション向けに提供する、適切な認証フローを利用します。

認証方式については、[`authentication_spec.md`](./authentication_spec.md) を参照します。

## データのエクスポート

将来、データのエクスポート機能を提供する場合、エクスポート対象を明示します。クレデンシャル (資格情報) はエクスポートしません。

エクスポート対象例: お気に入り / 統計 / ユーザー設定 (Preference)。

## バックアップ

通常のアプリケーション・バックアップにはクレデンシャル (資格情報) を含めません。デバイス移行時にクレデンシャルが復元されない場合は、再認証をリカバリー手段とします。

お気に入り / 統計 / ユーザー設定 (Preference) / キャッシュはバックアップしてかまいません。クレデンシャルは Secure ストレージ方針に従います。

## 復元

復元されたアプリケーション・データを、信頼できるクレデンシャル (資格情報) として扱いません。復元されたデータベースにクレデンシャル参照があっても、Secure ストレージに実体があることを確認します。

## デバイス紛失

デバイスを紛失した場合、アプリケーション・データが漏洩するリスクを低減します。

クレデンシャル (資格情報) はプラットフォーム Secure ストレージを利用します。

ユーザーは、必要に応じて、Packagist/GitHub 側から Token を取り消しできます。

## クレデンシャル (資格情報) 無効化

クレデンシャル無効化については、[`authentication_spec.md`](./authentication_spec.md) の仕様に従います。

セキュリティ仕様では、侵害の疑い検出→取り消し→ローテーション→再認証という、リカバリー方針を定義します。

## 不正アクセス

不正アクセスを検出した場合、下記を区別します。アプリケーション全体を停止せず、影響範囲を限定します。

* 認証障害
* 認可障害
* ネットワーク障害
* プロバイダ障害

## 部分的な障害

外部サービスのセキュリティ障害によって、別サービスの公開データを利用不能にしません。

例: GitHub 認証が失敗でも、Packagist 公開データはまだ利用可能とする。

## プライバシー境界

初期バージョンでは、S2J Package Dashboard 独自バックエンドを介在させません。

プライバシー上の境界: お気に入り / 統計 / ユーザー設定 (Preference) / クレデンシャル (資格情報) は ユーザー・デバイス上に置き、外部へは Packagist/GitHub に HTTPS のみとします。

## クレデンシャル (資格情報) バックエンドなし

初期バージョンでは、S2J Package Dashboard 独自バックエンドにクレデンシャルを送信・保存しません。

* Packagist Token X S2J サーバー
* GitHub Token X S2J サーバー

## ユーザー・トラッキングなし

初期バージョンでは、ユーザーのアプリケーション利用行動を個人単位で追跡しません。

特に、下記をユーザー識別情報と結び付けて外部に送信しません。

* 閲覧済みパッケージ
* お気に入りパッケージ
* GitHub アカウント
* Packagist アカウント

## プライバシー開示

App Store/Google Play 等で公開する場合、実際のデータ・コレクションについて、各プラットフォームのプライバシー開示に正確に反映します。

仕様と実際のデータ・コレクションが一致することを必須とします。

## プライバシー方針

外部プライバシー方針を提供する場合、最低限、下記を明示します。

* 収集するデータ
* 収集しないデータ
* データの用途
* データの保存場所
* サードパーティ・サービス
* データ共有
* データの保持
* データの削除
* クレデンシャル (資格情報) の取扱い
* 連絡先情報

## データの保持

アプリケーション・データについて、不要になったキャッシュを無期限に保持しません。いつ Stale になるか (有効期限) と、いつ削除するか (淘汰、クリア、ログアウト時のユーザー固有キャッシュ) は [`cache_spec.md`](./cache_spec.md) を正本とします。
本仕様は、「Stale になったことだけを理由に、キャッシュを削除しない」ことのみを定めます。

統計スナップショットについては、「長期傾向の表示という目的に必要な期間」を定義します。

## データの削除

ユーザーがサービスとの接続を解除した場合、クレデンシャル (資格情報) を削除します。削除手順は [`authentication_spec.md`](./authentication_spec.md) の接続解除を正本とします。
本仕様は、「アプリケーション・データをクレデンシャルと独立した保持方針とする」ことのみを定めます。

## データの完全リセット

将来的に、設定に「すべてのアプリケーション・データをリセット」を提供する場合、下記を明示的に分類して削除します。クレデンシャル (資格情報) は Secure ストレージから削除します。

* お気に入り
* 統計
* キャッシュ
* ユーザー設定 (Preference)
* クレデンシャル

## 認証境界

認証の HOW は [`authentication_spec.md`](./authentication_spec.md)、本仕様はアプリケーションとデータの保護を正本とします。
認証仕様をセキュリティ仕様に重複記載しません。

## 権限境界

OS 権限と外部 API 権限を区別します。OS 権限は iOS/Android ケイパビリティ、API 権限は Packagist/GitHub ケイパビリティ とします。たとえば GitHub トラフィック権限は、iOS の OS 権限ではありません。

## プラットフォーム・セキュリティ

Keychain / Keystore の HOW は [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md) を正本とします。
本仕様は、「OS のサンドボックス/コード署名/権限モデルを利用し、独自の同等機構を実装しない」ことのみを定めます。

## Kotlin Multiplatform (KMP) セキュリティ

KMP の HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とします。
本仕様は、「セキュリティ方針を共通仕様として維持し、Secure ストレージ実装をプラットフォームに置く」ことのみを定めます。

## セキュリティ・テスト

検証の種類は [`testing_spec.md`](./testing_spec.md) を正本とします。
本仕様は、「OWASP MASVS を参考基準とする」ことのみを定めます。

OWASP MASVS は、モバイル・アプリケーションのストレージ、暗号化、認証、ネットワーク、プラットフォーム、コード、レジリエンス、プライバシー等を対象とします。

(参考: [OWASP MASVS - OWASP Mobile Application Security](https://mas.owasp.org/MASVS/))

## セキュリティ・テスト・カテゴリー

検証対象の種類は [`testing_spec.md` セキュリティ・テスト](./testing_spec.md#セキュリティテスト) を正本とします。
本仕様は、「ログ/バックアップ/漏洩面を、脅威面として扱う」ことのみを定めます。

## Secure ストレージ・テスト

保存 HOW の検証は [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md)、検証の種類は [`testing_spec.md`](./testing_spec.md) を正本とします。
本仕様は、「通常ストレージにクレデンシャル (資格情報) が残らない」ことのみを定めます。

## ネットワーク・テスト

検証の種類は [`testing_spec.md`](./testing_spec.md) を正本とします。
本仕様は、「本番で HTTPS 以外に フォールバックしない」ことのみを定めます。

## クレデンシャル (資格情報) 漏洩テスト

脅威面 (ログ / クラッシュ / アナリティクス / スクリーンショット) は本仕様、検証の種類は [`testing_spec.md`](./testing_spec.md) を正本とします。

## プライバシー・テスト

プライバシー方針は本仕様、検証の種類は [`testing_spec.md`](./testing_spec.md) を正本とします。

## 依存関係セキュリティ・テスト

検証の種類は [`testing_spec.md`](./testing_spec.md) を正本とします。
本仕様は、「既知脆弱性をリリース前に確認する」ことのみを定めます。

## リリース・セキュリティ・チェックリスト

リリース 可否は [`release.md`](./release.md) を正本とします。
本仕様は、「デバッグ・ログ / テスト用 Secret / 不要権限が本番に残らない」ことのみを定めます。

## インシデント対応

クレデンシャル (資格情報) 漏洩等のセキュリティ・インシデントが発生した場合: 検出→隔離→クレデンシャル無効化→ローテーション→影響評価→是正措置→検証。

## 侵害されたクレデンシャル (資格情報)

クレデンシャル (資格情報) が漏洩した可能性がある場合、アプリケーション内での削除だけではセキュリティ・インシデントが解決したとはみなしません。

下記をそろえて実施することを基本とします。

* ローカル・デリート
* プロバイダ取り消し
* クレデンシャル・ローテーション

## セキュリティ・ドキュメント

セキュリティ上、重要な設計判断は ADR に記録します。

例:

* ADR-SEC-001: Packagist パスワードを保存しない
* ADR-SEC-002: GitHub トラフィック取得時のみ 認証
* ADR-SEC-003: クレデンシャル (資格情報) を独自バックエンドに保存しない
* ADR-SEC-004: 統計スナップショットとクレデンシャル (資格情報) を分離する

## セキュリティ・レビュー質問

変更時には最低限、下記を確認します。

1. 新しい機密データを扱うか
2. 新しい権限が必要か
3. クレデンシャル (資格情報) を扱うか
4. 新しい外部サービスに送信するか
5. ローカル・ストレージに何を保存するか
6. バックアップ対象になるか
7. ログ に出る可能性があるか
8. アナリティクスに送信されるか
9. Kotlin Multiplatform (KMP) 共有ロジックに持ち込むべきか
10. プラットフォーム固有のセキュリティ機構が必要か

## セキュリティ要件

本アプリケーションは、最低限、下記を満たします。

* SEC-001: クレデンシャル (資格情報) を平文ストレージに保存しない。
* SEC-002: パスワードを保存しない。
* SEC-003: HTTPS 以外でクレデンシャル (資格情報) を送信しない。
* SEC-004: 認可ヘッダーをログに出力しない。
* SEC-005: 不要な OS 権限を要求しない。
* SEC-006: 不要な個人情報を収集しない。
* SEC-007: クレデンシャル (資格情報) とアプリケーション・データを分離する。
* SEC-008: 公開 API 利用時に不要な認証を要求しない。
* SEC-009: サードパーティ製 SDK 追加時にセキュリティ・レビューを実施する。
* SEC-010: リリース・ビルドにテスト・クレデンシャル (資格情報) を含めない。
* SEC-011: クレデンシャル (資格情報) を独自バックエンドに保存しない。
* SEC-012: セキュリティ・インシデント発生時にクレデンシャル (資格情報) 無効化を可能とする。

## セキュリティ要件のトレーサビリティ

セキュリティ要件は、実装およびテストと対応付けます。

例: SEC-001→ `SecureCredentialStore` → `SecureStorageTests`。SEC-003→ HTTPS API クライアント → `NetworkSecurityTests`。SEC-005→ 権限 システム設定 (Configuration) → `PermissionReview`。

## セキュリティ標準

本アプリケーションでは、OWASP モバイル・アプリケーションのセキュリティ検証標準 (MASVS) をモバイル・セキュリティのリファレンス標準とします。

MASVS は iOS/Android を含むモバイル・アプリケーションを対象としており、消費者/法人双方の配布シナリオを想定しています。

(参考: [About the Standard - OWASP Mobile Application Security](https://mas.owasp.org/MASVS/02-Frontispiece/))

ただし、MASVS のすべてのコントロールの無条件実装を意味しません。

S2J Package Dashboard の脅威モデルおよびリスクに応じて、適用範囲を決定します。

## セキュリティ/プライバシー優先度

セキュリティと UX が競合する場合、クレデンシャル (資格情報)、個人情報および外部アカウントを保護することを優先します。ただし、ユーザー操作を過度に複雑化しません。

基本方針は、下記を同時に満たすこととします。

* Secure
* 利便性
* 最小限
