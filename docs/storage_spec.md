# S2J Package Dashboard - ローカル・ストレージ/スナップショット仕様

## 概要

本ドキュメントは、S2J Package Dashboard の初期設計における、ローカル永続化および履歴スナップショットを定義します。キャッシュ方針は [`cache_spec.md`](./cache_spec.md) を正本とします。

iOS/iPadOS 実装、Android 実装、Kotlin Multiplatform (KMP) 移行、ストレージ・フレームワークの選定、クラウド同期導入等に応じて、更新します。

## 目的

本ドキュメントでは、ローカル永続化、統計スナップショット、移行、バックアップ/復元 およびデータのライフサイクルを定義します。永続化と履歴のスナップショットの正本です。

## 非目的

本仕様は、クラウド・バックエンド、クラウド同期プロトコル、SwiftUI/Compose UI、チャートのレンダリングを詳細に定義しません。

## 責務

端末内の永続化、スナップショットの保持/移行/削除、オフライン時の永続データ参照、スキーマのライフサイクルを定義します。

## 非責務

キャッシュ方針は [`cache_spec.md`](./cache_spec.md)、型は [`models_spec.md`](./models_spec.md)、スナップショットの不変条件は [`domain_rules.md`](./domain_rules.md)、認証フローとクレデンシャル (資格情報) フォーマット は [`authentication_spec.md`](./authentication_spec.md)、API エンドポイントは各 API 仕様を正本とします。
集約の意味 (Sum / Last / ユニーク) は [`statistics_spec.md`](./statistics_spec.md) を正本とします。
SwiftData / Room 等の実装差分は [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md)、復元可能な UI の状態は [`application_state.md`](./application_state.md)、共有対象は [`architecture.md`](./architecture.md)、Kotlin Multiplatform (KMP) の HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とします。

## 基本方針

ローカル・ストレージについて、下記を基本原則とします。

1. 「ローカル」ファースト
2. API レスポンスをそのまま永続化しない
3. ドメイン・モデルと永続化モデルを分離する
4. キャッシュと履歴スナップショットを分離する。キャッシュ方針は [`cache_spec.md`](./cache_spec.md) を正本とする
5. クレデンシャル (資格情報) とアプリケーション・データを分離する
6. 原則として、履歴スナップショットは、不変とする。不変条件は [`domain_rules.md`](./domain_rules.md) を正本とする
7. ストレージ失敗でアプリケーション・データ全体を破壊しない
8. スキーマ移行を明示的に管理する
9. オフライン・リードを可能とする
10. クラウド・ストレージを必須依存にしない

## ストレージ・アーキテクチャー

層の置き場所は [`architecture.md`](./architecture.md) を正本とします。
本仕様は、「ストレージの抽象化をリポジトリの下に置き、アプリケーション・ロジックが具体的なストレージ・フレームワークに直接依存しない」ことのみを定めます。

## ストレージ・カテゴリー

ローカル・ストレージでは、下記を区別します。クレデンシャル (資格情報) は別ストレージとします。

* ユーザーデータ (お気に入り / 管理パッケージ)
* パッケージ・データ (パッケージ / リポジトリ・メタデータ)
* キャッシュ (再取得可能なカレント・データ。有効期間は [`cache_spec.md`](./cache_spec.md))
* 履歴スナップショット
* メタデータ (スキーマ・バージョン等)

## クレデンシャル (資格情報) ストレージ

ローカル・データベースに、クレデンシャルを保存しません。禁止対象と Secure ストレージ必須は [`authentication_spec.md`](./authentication_spec.md) を正本とします。
Keychain / Keystore の実装は [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md) とします。

## パッケージ・ストレージ

永続フィールドは `## PackageRecord` を正本とします。
ドメイン型は [`models_spec.md`](./models_spec.md) を正本とします。

## 管理対象パッケージ

ユーザーがメンテナンス対象として扱うパッケージは、ローカル・ストレージに保持します。Packagist API から自動取得したパッケージ一覧と、ローカル・ユーザー設定 (Preference) を混同しません。

* `管理対象 = true`

## お気に入りパッケージ

お気に入りパッケージは、ユーザーのローカル・ユーザー設定 (Preference) として保持します。お気に入りの状態自体は Packagist/GitHub のリモートデータではありません。

* `お気に入り = true`

## パッケージ ID

パッケージ ID は、プロバイダ固有の URL ではなく、ドメイン上で安定した識別子を使用します。

Packagist パッケージの場合、`vendor/package` を 正規パッケージ識別子として扱います。

## リポジトリ ID

GitHub リポジトリは、`owner/repository` を正規リポジトリ識別子として扱います。

リポジトリ URL を主キーとして直接使用しません。

## パッケージ/リポジトリのリレーションシップ

パッケージと GitHub リポジトリは、1対1とは限りません。1パッケージが複数リポジトリ参照を持ち得ます。

## 永続対象とキャッシュの境界

再取得可能なカレント・データはキャッシュとして扱います。区別の意味は [`cache_spec.md`](./cache_spec.md) を正本とします。
本仕様の対象は、ユーザー所有の永続データおよび履歴スナップショットです。キャッシュを削除してもスナップショットは削除しません。

## スナップショット

統計スナップショットは、ある時点で取得した統計を記録します。型は [`models_spec.md`](./models_spec.md)、意味は [`statistics_spec.md`](./statistics_spec.md) を正本とします。
永続フィールドは [StatisticsSnapshotRecord](#statisticssnapshotrecord) を正本とします。

## スナップショットの目的

下記は、スナップショットの主目的です。

* 履歴傾向
* 成長計算
* パッケージの比較
* 長期統計
* GitHub トラフィックの保持期間の補完

## スナップショット書き込み規則

スナップショットの不変条件 (不変性、アイデンティティ、重複排除、欠測の扱い) は [`domain_rules.md`](./domain_rules.md) を正本とします。
永続化では、確定済み行を更新しません。同一 `(package, provider, capturedDay)` は挿入しません。

## スナップショット・タイムスタンプ

スナップショットには、`capturedAt` を保存します。

これは S2J Package Dashboard が統計を取得した時点を表します。

## タイムスタンプ標準

永続化では UTC を基本とします。ユーザー向け表示時のみ、現地時間に変換します。

* `capturedAt = Instant/UTC`

## 日次スナップショット

可視化の粒度は [`statistics_spec.md` スナップショットの粒度](./statistics_spec.md#スナップショットの粒度) を正本とします。
本仕様は、「永続化の基本単位を、日次行とする」ことのみを定めます。

## スナップショットの重複排除

重複排除の規則は [`domain_rules.md`](./domain_rules.md) を正本とします。
永続化では、同一日の後勝ちを、ユニーク制約または同等の書き込み規則で実現します。

## 失敗したスナップショット

失敗時に偽の0値行を書かないことは [`domain_rules.md`](./domain_rules.md) を正本とします。
永続化層は失敗した取得に対して、スナップショット行を生成しません。

## 部分スナップショット

プロバイダ単位で、部分的にスナップショットを保存可能とします。片方のプロバイダが利用不能でも、取得できた側の行を残します。欠測側を0で埋めないことは [`domain_rules.md`](./domain_rules.md) を正本とします。

## 指標の可用性

可用性の値と0の区別は [`domain_rules.md`](./domain_rules.md) を正本とします。
永続化では、指標ごとに可用性を保存できること。

## GitHub トラフィック・スナップショット

14日ウィンドウを超える組み立て HOW は [`api-github.md`](./api-github.md) の「長期統計」を正本とします。
本仕様は、「取得できたトラフィックを、日次スナップショット行として永続する」ことのみを定めます。

## トラフィック過去データ

インストール前の履歴を推測しないことは [`statistics_spec.md`](./statistics_spec.md) を正本とします。
本仕様は、「最初のスナップショット行より前の日付を、永続化に補完しない」ことのみを定めます。

## スナップショット保持期限

初期バージョンでは、スナップショットに固定的な短期の保持期限を設定しません。

ユーザーが削除するまで、可能な範囲で、過去データを保持します。

将来的に、ストレージ最適化が必要となった場合、保持の方針を追加可能とします。

## ストレージのクォータ

スナップショット増加によるストレージ消費を考慮します。

アプリケーションは、必要に応じて、下記を確認可能とします。

* 使用中のストレージ
* スナップショット数
* 最古のスナップショット

## ストレージ最適化

長期運用でスナップショット数が増えた場合、日次行の月次集約を検討します。ただし、Raw 日次データを削除する場合は、「精度の損失」を明示します。

## 集計スナップショット

集計データには、下記を保持可能とします。

* `aggregationType`
* `aggregationPeriod`

例:

* `aggregationType` = monthly
* `aggregationPeriod` = 2026-08

## 集約ルール

指標ごとの集約意味 (Sum / Last / ユニーク を加算しない等) は [`statistics_spec.md`](./statistics_spec.md) を正本とします。
本仕様は、「集約結果を `aggregationType` / `aggregationPeriod` として永続する」ことのみを定めます。

## Raw vs 派生

永続化では、「Raw 指標」と「派生指標」を区別します。

* Raw: 出典 = Packagist/GitHub
* 派生: 出典 = S2J Package Dashboard

## 派生指標の永続化

派生指標は、必要性がない限り永続化せず、Raw スナップショットから再計算可能とします。

ただし、下記の場合は、永続化を許容します。

* 計算コストが高い
* 長期保存する必要がある
* 計算バージョンを固定する必要がある

## 計算バージョン

派生データを保存する場合、`calculationVersion` を保持します。

計算ルール変更時に、旧データとの互換性を維持します。

## スナップショット・スキーマ・バージョン

スナップショットには、`schemaVersion` を持たせます。

アプリケーション・バージョンとは分離します。

## 永続化モデル

「ドメイン≠永続」は [`models_spec.md`](./models_spec.md) を正本とします。
本仕様は、「永続化マッパー経由で、ローカル・データベースに書き、スキーマ変更がドメイン型に直接影響しない」ことのみを定めます。

## ストレージ・リポジトリ

アプリケーションからは、リポジトリ・インターフェースを利用します。

例:

* `PackageRepository`
* `StatisticsRepository`
* `SnapshotRepository`
* `CacheRepository`

## リポジトリ境界

* ドメイン層: `interface SnapshotRepository`
* インフラストラクチャ層: `SwiftDataSnapshotRepository`

または将来的に、`SQLDelightSnapshotRepository` を実装します。

## プラットフォームの独立性

ドメイン層は、下記に直接依存しません。

* SwiftData
* CoreData
* SQLite API
* SQLDelight API
* Android Room
* Jetpack Compose
* SwiftUI

## Kotlin Multiplatform (KMP) 移行

共有対象と優先順位は [`architecture.md`](./architecture.md)、HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とします。
本仕様は、「ストレージ・インターフェースを、移行時に再利用する」ことのみを定めます。

## Kotlin Multiplatform (KMP) 互換の永続化

KMP 移行後の候補として、SQLite/SQLDelight 等を利用可能とします。SQLDelight は、SQL スキーマから型安全な Kotlin API を生成でき、SQLite を Android/iOS/Multiplatform で利用できます。

(参考: [Getting Started - SQLDelight](https://sqldelight.github.io/sqldelight/2.0.0/multiplatform_sqlite/))

ただし、初期 iOS 実装において特定の KMP 永続化フレームワークを必須としません。

## SwiftData

iOS/iPadOS の SwiftData 実装は [`ios_spec.md`](./ios_spec.md) を正本とします。
本仕様は、「初期 iOS で SwiftData を永続化実装として採用し得る」「ドメインが SwiftData に依存しない」ことのみを定めます。

## SwiftData 境界

ドメイン・モデルに SwiftData の永続化アノテーションを直接持ち込みません。実装差分は [`ios_spec.md`](./ios_spec.md) を正本とします。

## データベース・スキーマ

永続化スキーマは、下記の概念を持ちます。

* `PackageRecord`
* `RepositoryRecord`
* `FavoriteRecord`
* `StatisticsSnapshotRecord`
* `MetricRecord`
* `CacheRecord`
* `StorageMetadata`

## PackageRecord

概念: `id` / `name` / `description` / `repositoryID` / `maintained` / `favorite` / `source` / `createdAt` / `updatedAt`。

ドメイン型の正本は [`models_spec.md`](./models_spec.md) とします。
本仕様は「永続化行の列」だけを定めます。

## RepositoryRecord

概念: `id` / `provider` / `owner` / `name` / `url` / `archived` / `defaultBranch` / `updatedAt`。

ドメイン型の正本は [`models_spec.md`](./models_spec.md) とします。

## StatisticsSnapshotRecord

概念: `id` / `packageID` / `source` / `capturedAt` / `schemaVersion` / `availability`。

スナップショット不変条件は [`domain_rules.md`](./domain_rules.md) を正本とします。

## MetricRecord

概念: `id` / `snapshotID` / `name` / `value` / `unit` / `period` / `availability` / `derived`。

指標の意味は [`statistics_spec.md`](./statistics_spec.md) を正本とします。

## スナップショット ID

スナップショット ID は `packageID` + `source` + `calendarDay` を基本構成とします。

同一指標を複数保存する必要がある場合は、指標 ID を追加します。

## 主キー

永続化内部の主キーには、ストレージ固有識別子を使用可能とします。

ドメイン ID とデータベース主キーを、必ずしも一致させません。

## 外部キー

概念的には、`PackageRecord` 一つに対して `StatisticsSnapshotRecord` が複数、各スナップショット一つに対して `MetricRecord` が複数、とします。

パッケージ削除時のスナップショット処理については、明示的な削除の方針を使用します。

## パッケージの削除

ユーザーがパッケージをローカル・ダッシュボードから削除した場合、下記を削除します。現在キャッシュの削除方針は [`cache_spec.md`](./cache_spec.md) に従います。履歴スナップショットについては、ユーザーの意図を確認せずに自動削除しません。

* お気に入り
* 管理
* 現在 キャッシュ

## ダッシュボードから削除

「ダッシュボードから削除」と「過去データを完全削除」を分離します。非表示にしても、履歴スナップショットは保持し得ます。

## 過去データの削除

ユーザーが明示的に過去データの削除を要求した場合のみ、対象スナップショットを削除します。

## すべてのローカルデータの削除

「すべてのローカルデータを削除」機能を提供する場合、下記を削除します。クレデンシャル (資格情報) については、クレデンシャル (資格情報) ストレージの方針に従います。

* パッケージ
* お気に入り
* 管理
* キャッシュ
* スナップショット
* メタデータ

## クレデンシャル (資格情報) 分離

ローカル・データベースの全削除処理とクレデンシャル削除処理を分離します。クレデンシャル削除は別途明示します。方針は [`authentication_spec.md`](./authentication_spec.md) を正本とします。

## 移行

永続化スキーマ変更時には、移行を実施します。既存データを、可能な限り、保持します。

## 移行の原則

移行は、下記であることを目指します。

* 再現可能
* 検証可能
* アトミック
* 復旧可能

## 移行失敗

移行に失敗した場合、既存データを破壊した状態でアプリケーションを起動しません。リカバリー / ロールバックを検討します。

## 移行のテスト

移行のテストでは、下記を検証します。代表的な本番データを、フィクスチャとして保持します。

* `v1 → v2`
* `v2 → v3`
* ...

## 後方互換性

新バージョンでは、旧バージョンの永続化データを、可能な限り、読み込めるようにします。

## 前方互換性

旧アプリケーションが、新アプリケーションによって作成された、永続化スキーマを読み込めることは保証しません。

旧バージョンでのデータ使用が必要な場合は、エクスポート/バックアップを利用します。

## トランザクション

複数レコードを同時更新する場合、トランザクション境界を明示します。途中状態をユーザーに成功データとして表示しません。

例: `PackageRecord` 更新 とスナップショット Insert を同一コミットにする。

## アトミック・スナップショット

スナップショット保存は、可能な限り、`SnapshotRecord` と `MetricRecords` を同一コミットにします。途中で失敗した場合、不完全スナップショットを残しません。

## 破損スナップショット

スナップショットが破損している場合、そのスナップショットだけを「利用不能」として扱えるようにします。データベース全体をエラーにしません。

## 整合性チェック

必要に応じて、下記を利用して整合性を検証可能とします。初期バージョンでは Checksum を必須としません。

* `schemaVersion`
* `metricCount`
* `checksum`

## バックアップ

ローカル・ストレージは、OS/デバイス・バックアップによって、バックアップ可能な永続化方式を優先します。

iOS/iPadOS では、採用する永続化フレームワークのバックアップ/復元挙動を、実機で検証します。

## デバイス移行

機種変更時は OS バックアップ/移行による、ローカルデータ復元を基本とします。アプリケーション独自のサーバー移行を必須にしません。

## バックアップ整合性

バックアップ後に、下記を検証可能とします。

* パッケージ数
* お気に入り数
* 管理パッケージ数
* スナップショット数
* 最古スナップショット
* 最新スナップショット

## バックアップ vs クレデンシャル (資格情報)

バックアップ対象データとクレデンシャルを分離します。

クレデンシャルは、プラットフォーム Secure ストレージのバックアップ/復元の方針に従います。

アプリケーション・データベースにクレデンシャルをコピーしません。

## クラウド同期

クラウド同期は、初期バージョンでは必須としません。

将来的に、iCloud/CloudKit 等を利用する場合も、ローカル永続化をソースとして設計可能とします。

SwiftData の `ModelContainer` は、CloudKit エンタイトルメントを設定した場合、永続化データの複数デバイス間同期を扱えます。

(参考: [ModelContainer | Apple Developer Documentation](https://developer.apple.com/documentation/swiftdata/modelcontainer))

ただし、クラウド同期を採用するかどうかは別仕様として決定します。

## 外部サーバー

初期バージョンでは、下記の理由から、統計スナップショット保存のためだけに外部サーバーを導入しません。

* 運営費用
* プライバシー
* セキュリティ
* 可用性
* サーバー・メンテナンス
* 認証基盤

## デバイス横断型同期

複数端末間でのデータ共有は、初期バージョンでは必須機能としません。iPhone/iPad / Android はそれぞれローカル・ストレージを正とします。

## 将来のデバイス横断型同期

将来導入する場合の同期対象は、下記から選択します。原則として、クレデンシャル (資格情報) は、同期対象外とします。

* お気に入り
* 管理対象
* パッケージ・メタデータ
* スナップショット

## コンフリクト解決

デバイス横断型同期を将来導入する場合、コンフリクト解決を定義します。

例:

* お気に入り
* デバイス A = true
* デバイス B = false

上記について、下記の方針を採用します。初期バージョンでは不要です。

* Last Writer Wins
* タイムスタンプ
* ユーザー解決

## ストレージ暗号化

機密データを含む永続化については、プラットフォームが提供するデータ保護/暗号化を優先利用します。

クレデンシャル (資格情報) はデータベースに保存せず、Secure ストレージを利用します。

## スナップショット機密性

原則として、統計スナップショットには、クレデンシャル (資格情報) を含めません。また、不要な個人情報を保存しません。

## API レスポンス・ストレージ

「データ転送オブジェクト (DTO) ≠ドメイン」は [`models_spec.md`](./models_spec.md) を正本とします。
本仕様は、「API レスポンス全文をデータベースに保存せず、必要なフィールドだけを永続化する」ことのみを定めます。

## 不明 API フィールド

プロバイダ API に未知フィールドが追加されても、アプリケーション永続化スキーマを自動的に拡張しません。必要なフィールドのみ、明示的にマッピングします。

## API バージョン

永続化スキーマ・バージョンとプロバイダ API バージョンを混同しません。下記は、別管理します。

* `storageSchemaVersion`
* `providerAPIVersion`

## スナップショット無効化

キャッシュ無効化ではスナップショットを削除しません。キャッシュの無効化は [`cache_spec.md`](./cache_spec.md) を正本とします。

* キャッシュ → 無効化可能
* スナップショット → 履歴レコード

## リフレッシュ失敗

リフレッシュに失敗しても、既存のスナップショットを削除しません。キャッシュを残すかどうかは [`cache_spec.md`](./cache_spec.md) に従います。

## オフライン起動

オフライン状態でアプリケーションを起動した場合、永続化したユーザーデータおよび履歴スナップショットを優先して利用します。カレント・データの Stale 表示は [`cache_spec.md`](./cache_spec.md) に従います。

API 利用不能を理由に、ダッシュボード全体を表示不能にしません。

## 「空」の状態

「空」の見え方は [`ui.md`](./ui.md) を正本とします。
本仕様は、「初回起動等でローカルデータがないことを、正常状態 (`ローカルデータ なし`) として扱う」ことのみを定めます。

## 最初の起動

最初の起動では、ローカル・ストレージが「空」であることを前提とします。パッケージ・データをハードコーディングして永続化に初期投入しません。

## ストレージのリセット

デバッグ/開発環境では、ローカル・ストレージのリセットを可能とします。

本番環境では、ユーザーが誤操作しにくい UI とします。

## デバッグデータ

デバッグ用データは、本番永続化に混入させません。

## テスト・ストレージ

ユニットテストでは、可能な限り、インメモリ・ストレージを利用します。

本番データベースをテストから直接操作しません。

SwiftData は、インメモリ等のストレージ・システム設定 (Configuration) を設定可能であるため、テスト用永続化を分離できます。

(参考: [ModelContainer | Apple Developer Documentation](https://developer.apple.com/documentation/swiftdata/modelcontainer))

* 読取

* スナップショット・クエリー
* スナップショットの重複排除

## スナップショット・テスト

最低限、下記をテストします。

* スナップショットの作成
* スナップショットの読取
* スナップショットの重複
* スナップショットの欠落
* 部分スナップショット
* 無効スナップショット
* 履歴クエリー

## ストレージ失敗のテスト

* ディスク容量不足
* データベース・エラー
* 移行失敗
* 破損レコード
* トランザクション失敗
* 権限失敗

## ディスク容量不足

ストレージ容量不足時にも、既存過去データを、可能な限り、保持します。新規スナップショット保存に失敗しても、既存履歴を破棄しません。

## 並行アクセス

複数タスクから同時に永続化にアクセスする場合、ストレージ・フレームワークが提供する並行処理モデルに従います。

ドメイン層からデータベース・スレッドセーフ性を直接制御しません。

## バックグラウンドのアクセス

バックグラウンド・リフレッシュからローカル・ストレージにアクセスする場合も、フォアグラウンド UI との競合を避けます。

## 書き込みの方針

統計取得時の順序は、フェッチ API →検証→マップ→永続化→更新 UI を基本とします。無効 データを先に永続化に保存しません。

## 検証

永続化前に最低限、下記を検証します。

* パッケージ識別子
* 指標名
* 数値
* タイムスタンプ
* ソース
* 単位
* 可用性

## 数値検証

統計値について、下記を保存しません。

* NaN
* 無限大
* 負の個数

## タイムスタンプ検証

スナップショット・タイムスタンプについて、明らかに「未来のタイムスタンプ」等を無条件に過去データとして保存しません。

プロバイダ固有のタイムスタンプ定義を考慮します。

## ストレージ・メタデータ

ストレージ全体について、下記を保持可能とします。

* `schemaVersion`
* `createdAt`
* `lastMigrationAt`
* `lastIntegrityCheckAt`

## アプリケーション・バージョン

アプリケーション・バージョンはストレージ・メタデータに、必要に応じて、記録します。ただし、下記を同一視しません。

* `applicationVersion`
* `schemaVersion`

## ストレージ診断

デバッグ画面等では、下記を確認可能とします。本番 UI への公開は別途検討します。

* データベース・サイズ、パッケージ数、スナップショット数、キャッシュ数、最古スナップショット、最新スナップショット

## エクスポート

将来的に、ローカルデータのエクスポートを提供する場合、下記のように対象を明示します。クレデンシャル (資格情報) はエクスポートしません。

* パッケージ / お気に入り / スナップショット / メタデータ

## インポート

インポート時の順序は、検証→スキーマ移行→コンフリクト解決→トランザクション→コミットとします。

## インポート失敗

インポート途中で失敗した場合、部分的なデータを本番ストレージに残しません。

## JSON エクスポート

JSON エクスポートを提供する場合、ドメイン・エクスポート・スキーマを定義します。

内部永続化スキーマをそのままエクスポート・フォーマットとして公開しません。

## CSV エクスポート

統計について、CSV エクスポートを提供する場合、下記を基本カラムとします。

* `package`
* `source`
* `metric`
* `date`
* `value`
* `unit`

## データの移植性

ユーザーが蓄積した履歴統計を、アプリケーション・バージョンやプラットフォーム変更によって失わないことを目指します。

## プラットフォームの移行

「iOS → iPadOS」等の同一プラットフォーム間移行では、OS/デバイス移行による永続化移行を基本とします。

## プラットフォーム横断型の移行

「iOS → Android」では、OS バックアップだけに依存しません。将来的に、エクスポート→ポータブル・フォーマット→インポートによる移行を可能とします。

## ポータブル・スナップショット・フォーマット

永続フィールドは [StatisticsSnapshotRecord](#statisticssnapshotrecord) を正本とします。
本仕様は、「論理スキーマを、プラットフォーム固有のデータベース・スキーマから独立させる」ことのみを定めます。

## Kotlin Multiplatform (KMP) 移行戦略

共有に移す順序は [`architecture.md`](./architecture.md) を正本とします。
本仕様は、「ドメイン・モデル / リポジトリ / 永続化を段階的に移行可能な構造とする」ことのみを定めます。

## ストレージ・アダプタ

Kotlin Multiplatform (KMP) の HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とします。
本仕様は、「`SnapshotRepository` を iOS / Android アダプタ経由で実装し、将来共有 SQL に移行可能とする」ことのみを定めます。

## UI の依存関係なし

ストレージ層は、下記に依存しません。

* SwiftUI
* Jetpack Compose

## ネットワークの依存関係なし

層境界は [`architecture.md`](./architecture.md) を正本とします。
本仕様は、「ストレージ層が Packagist API クライアント / GitHub API クライアントに直接依存しない」ことのみを定めます。

## ソース・メタデータ

永続化された統計には、下記のように必ず出典を保持します。

* source = Packagist
* source = GitHub
* source = 派生

## プロバイダ・データの保持期限

プロバイダ側の保持期間と S2J 側の保持期限を混同しません。プロバイダ・ウィンドウの意味は [`api-github.md`](./api-github.md) / [`statistics_spec.md`](./statistics_spec.md) を正本とします。
本仕様は、「S2J の保持期限をプロバイダの保持期間と同一視しない」ことのみを定めます。

## 履歴の真実

S2J スナップショットは、「S2J Package Dashboard がその時点で取得したプロバイダ・データ」を記録します。

プロバイダ側の履歴データベース自体ではありません。

## スナップショットの来歴

永続フィールドは [StatisticsSnapshotRecord](#statisticssnapshotrecord) を正本とします。
本仕様は、「必要に応じて、`source` / `capturedAt` / `providerAPI` / `schemaVersion` で 来歴を追跡可能とする」ことのみを定めます。

## 現在データのリフレッシュ

現在データのリフレッシュでは、スナップショットを必ず作成する必要はありません。カレント・データの更新は [`cache_spec.md`](./cache_spec.md) に従います。

履歴スナップショットを作成するのは、スナップショット方針に該当する場合とします。

## スナップショット・スケジュール

初期バージョンでは、スナップショット取得を日次単位とします。

GitHub トラフィックのスナップショットは、初期バージョンに含めます。取得は認証成功時に限ります。認証の設定の実装時期は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) の UC-17を正本とします。いつ取得するかは [`api-github.md` トラフィック・スナップショット・スケジュール](./api-github.md#トラフィックスナップショットスケジュール) を正本とします。

時計どおりの定期ジョブによる自動取得は、初期バージョンの対象外とします。

## バックグラウンド・スナップショット方針

GitHub トラフィックで、バックグラウンド更新が許可されている場合の取得は、[`api-github.md` トラフィック・スナップショット・スケジュール](./api-github.md#トラフィックスナップショットスケジュール) を正本とします。その場合も、`Maximum: 1スナップショット/パッケージ/日` を基本とします。過剰な API リクエストを避けます。

## 手動スナップショット

デバッグ/上級ユーザー向けに、手動スナップショットを許可する場合も、日次の重複排除の方針を維持します。

## ストレージのライフサイクル

キャッシュの有効期間は [`cache_spec.md`](./cache_spec.md)、日次行は [日次スナップショット](#日次スナップショット)、削除は [ダッシュボードから削除](#ダッシュボードから削除) / [すべてのローカルデータの削除](#すべてのローカルデータの削除) を正本とします。
本仕様は、「API 取得成功後に、現在→ (必要なら) 日次スナップショット→任意の集約に進み、ユーザー削除で終わる」ことのみを定めます。

## データ削除のライフサイクル

ダッシュボードからの非表示は [ダッシュボードから削除](#ダッシュボードから削除)、明示的な完全削除は [すべてのローカルデータの削除](#すべてのローカルデータの削除) を正本とします。
本仕様は、「削除でキャッシュを消し、スナップショットは保持し得る」「完全削除ではパッケージ / キャッシュ / スナップショット / メタデータを対象とする」ことだけを再掲します。

## プライバシー削除

ユーザーがローカルデータ削除を要求した場合、対象データを復元不能な形で削除します。

OS バックアップ等に存在するデータについては、プラットフォームのバックアップ方針に従います。

## セキュリティ境界

クレデンシャル (資格情報) の分離は [`authentication_spec.md`](./authentication_spec.md) / [`security_spec.md`](./security_spec.md) を正本とします。
本仕様は、「公開統計をローカル・データベースに置き、クレデンシャルをスナップショットに混在させない」ことのみを定めます。

## ログ記録

Token/クレデンシャル (資格情報) をログに出さないことは [`security_spec.md`](./security_spec.md) を正本とします。
本仕様は、「統計値の診断を必要最小限にする」ことのみを定めます。

## クラッシュ・リカバリー

アプリケーション・クラッシュ中にストレージ書き込みが発生した場合も、可能な限り、アトミック・コミットを利用します。

再起動後に、不完全トランザクションをアプリケーションが通常データとして扱いません。

## 破損リカバリー

データベース破損が検出された場合、検出→復元可能なデータの保全→復元/リビルドを検討します。キャッシュは再構築可能とし、履歴スナップショットの保全を優先します。キャッシュのリビルド は [`cache_spec.md`](./cache_spec.md) を正本とします。

## リビルド戦略

ローカル・データベース全体を再構築する場合、ポータブル/エクスポートされたデータを検証した後で、リビルドを利用可能とします。

## パフォーマンス

ストレージ・クエリーは、UI スレッド/メインスレッドを不必要にブロックしません。

大量スナップショットを取得する場合は、ページネーション/日付範囲フィルター等を利用します。

## スナップショット・クエリー

履歴チャートでは、必要な期間だけスナップショットを取得します。選択できる期間は [`screen_spec.md`](./screen_spec.md)、期間の意味は [`statistics_spec.md`](./statistics_spec.md) を正本とします。
全履歴を毎回メモリにロードしません。

## インデックス

下記の検索条件について、必要に応じて、インデックスを設けます。特に、`packageID + capturedAt` を履歴クエリーの、主要インデックス候補とします。

* `packageID`
* `capturedAt`
* `source`
* `metricName`

## ストレージ・サイズの監視

スナップショット数が増加した場合、ストレージ使用量を監視可能とします。

必要に応じて、ユーザーに、「ストレージの使用量が増加している」等を通知可能とします。

## 初期バージョン・ストレージ方針

基本方針は [基本方針](#基本方針) を正本とします。
v1固有の制約は、永続化 / キャッシュ / スナップショットをローカルに限り、外部サーバーとクラウド同期を必須としないこととします。

## 初期 iOS 実装

iOS/iPadOS の永続化実装は [`ios_spec.md`](./ios_spec.md) を正本とします。
本仕様は、「ドメイン / リポジトリ・インターフェース / ユースケースを SwiftData に依存させない」ことのみを定めます。

## Android 実装

Android の 永続化実装は [`android_spec.md`](./android_spec.md) を正本とします。
本仕様は、「iOS と独立して実装を選べる」「共有ドメインからプラットフォーム・ストレージに依存する」ことのみを定めます。

## Kotlin Multiplatform (KMP) 互換アーキテクチャー

境界は [`architecture.md`](./architecture.md) を正本とします。
共有永続化の候補は [Kotlin Multiplatform (KMP) 互換の永続化](#kotlin-multiplatform-kmp-互換の永続化) を正本とします。
本仕様は、「ドメイン / リポジトリ・インターフェースをプラットフォーム・ストレージから独立させる」ことのみを定めます。

## ストレージの抽象化例

具体的な API 定義は、実装時に決定します。

概念:

```text
interface SnapshotRepository {
    suspend fun save( snapshot: StatisticsSnapshot )
    suspend fun find( packageID: PackageID, from: Instant, to: Instant ): List<StatisticsSnapshot>
    suspend fun delete( packageID: PackageID )
}
```

## ドメイン/永続化のマッピング

「ドメイン≠永続」は [`models_spec.md`](./models_spec.md) を正本とします。
本仕様は、「`SnapshotPersistenceMapper` 等で `StatisticsSnapshot` と `StatisticsSnapshotRecord` を双方向に写す」ことのみを定めます。

## ストレージ・エラー

ドメイン・エラー / `ApplicationError` は [`models_spec.md`](./models_spec.md) を正本とします。
本仕様は、「SQLite / CoreData / SwiftData 等の例外を `StorageError` に写像し、ドメインにそのまま漏出させない」ことのみを定めます。アプリケーション層に出す場合は `PersistenceFailed` とします。

## エラー・カテゴリー

`StorageError` は、少なくとも、下記を区別します。

* `ReadFailure`
* `WriteFailure`
* `MigrationFailure`
* `Corruption`
* `QuotaExceeded`
* `Unknown`

## リトライ

ストレージへの書き込み失敗について、盲目的に再試行しません。

トランザクション失敗等、リトライ可能性が明確な場合のみ、再試行します。

## 一貫性

アプリケーション起動後は、下記の参照整合性を、可能な限り、維持します。

* パッケージ
* お気に入り
* 管理
* スナップショット
* キャッシュ

## 孤立レコード

孤立スナップショット等を定期的に検出可能とします。

たとえば、`Snapshot.packageID` に対応するパッケージがない場合、下記の方針に従って処理します。

* 復元
* 保持
* 削除

## 履歴の孤立

パッケージ・レコードが削除されても、履歴スナップショットを保持する場合があります。

そのため、`PackageRecord` と履歴スナップショットを必ずカスケード削除しません。

## 孤立の表示

パッケージ・レコードが存在しないスナップショットは、通常のダッシュボードには表示しません。

デバッグ/リカバリー用途では、存在を確認可能とします。

## ストレージの一貫性チェック

必要に応じて、下記を検査します。

* パッケージ数
* スナップショット数
* 孤立数
* 無効指標数

## 修復

一貫性チェックで課題を検出した場合、自動修復は慎重に行います。

過去データを、推測によって、修正しません。

## データ損失の原則

ストレージ修復では、「不明なデータを推測して修復するより、壊れているデータとして保持する」ことを優先します。

## ユーザー可視ストレージのステータス

通常、ユーザーには、ストレージ内部実装を意識させません。

ただし、下記の場合は、通知可能とします。

* 移行が必須
* ストレージ・エラー
* ストレージがほぼ満杯
* データ・リカバリーが必須

## テスト・フィクスチャ

移行のテスト用に、各スキーマ・バージョンのフィクスチャを保持します。

```text
fixtures/
├── storage-v1/
├── storage-v2/
└── storage-v3/
```

## バージョニング

ストレージ・スキーマ・バージョンは、アプリケーション・リリース・バージョンとは独立して、セマンティックに管理します。

例:

* アプリケーション: v1.4.0
