# S2J Package Dashboard - テスト仕様

## 概要

本ドキュメントは、S2J Package Dashboard の初期設計における、テスト戦略、テストレベル、テスト対象、テストデータ、実行環境およびリリース前後に実施する、検証内容を定義します。

## 目的

本仕様は、品質を継続的に保証するためのテスト戦略、テストのレベル、テスト対象、テストデータ、実行環境およびリリース前後に実施する、検証内容を定義します。

## 非目的

本仕様は、CI ワークフローの YAML、ランナー構成、リリース可否の判断自体を定義しません。自動生成される生のテスト出力を本仕様に埋め込みません。

## 責務

何を、なぜ、どのレベルでテストするかを正本とします。

## 非責務

CI 上の実行方法は [`cicd.md`](./cicd.md)、リリース前後の品質ゲートは [`release.md`](./release.md)、生のテスト結果は [`test-results.md`](../docs_mod/test-results.md) とします。
Viewport/基準端末は [`ui-viewport.md`](./ui-viewport.md)、横断 UI 挙動は [`ui.md`](./ui.md)、復元対象は [`application_state.md`](./application_state.md)、遷移の形式は [`state_machine.md`](./state_machine.md) を正本とします。
機能の正本は、各専門仕様とします。

## テスト原則

S2J Package Dashboard のテストは、下記の原則に従います。

1. ビジネス・ルールを、最優先でテストする。
2. 純粋ロジックは、可能な限り、高速なユニットテストで検証する。
3. 状態遷移は、網羅的に検証する。
4. 外部 API に依存するテストと、依存しないテストを、明確に分離する。
5. ネットワーク/ストレージ/キャッシュは、テスト用ダミー/スタブ/モック等によって制御可能にする。
6. UI テストは、ユーザー挙動を中心に検証し、実装詳細に依存しない。
7. スナップショット・テストは、補助的に使用し、主要なビジネスロジックの検証には使用しない。
8. プラットフォーム固有な UI とプラットフォーム非依存なロジックを、別々に検証する。
9. テストは、決定論的であることを優先する。
10. CI で継続的に実行可能であることを、テストの設計条件とする。

## テスト・ピラミッド

基本的なテスト・ピラミッドは、下記とします。

件数は、ユニット > 結合 > UI/E2E > 手動とします。

UI テストや E2E テストだけで、アプリケーション・ロジックの品質を保証しません。

## テストのレベル

下記は、テストのレベルを分類したものです。

| レベル | ターゲット | Main 目的 |
| --- | --- | --- |
| ユニット | ドメイン / アプリケーション / 状態 | ロジックの正確性 |
| コンポーネント | UI コンポーネント | コンポーネントの挙動 |
| 結合 | リポジトリ / API / ストレージ / キャッシュ | 境界の正確性 |
| UI | スクリーン / ナビゲーション | ユーザー・インタラクション |
| E2E | アプリケーションのフロー | ユーザーの目的 |
| パフォーマンス | 重要な操作 | パフォーマンスのリグレッション |
| セキュリティ | クレデンシャル (資格情報) / データのハンドリング | セキュリティのリグレッション |
| 手動 | 実機 / ストア ビルド | リリースの検証 |

## テストの命名

テスト名は、「何を検証するか」が明確になるようにします。テスト名だけで、目的を理解できることを原則とします。

基本形式: `subject_condition_expectedResult`
または: `given_condition_when_action_then_result`

例:

* `emptyPackageName_isRejected`
* `validPackageName_isAccepted`
* `refreshRequested_startsLoading`
* `packageLoaded_updatesState`
* `networkFailure_preservesExistingData`

## Given / When / Then

挙動テストでは、下記の構造を基本とします。

* Given: 初期状態
* When: イベント/アクション
* Then: 期待される状態/結果

例:

* Given:
    * パッケージが読み込み完了の状態
* When:
    * `RefreshRequested`
* Then:
    * 更新中の状態になる
    * 既存パッケージ・データは保持される

## ユニットテスト

### 目的

ユニットテストは、外部 I/O に依存しない、小さな単位の動作を検証します。

主な対象:

* ドメイン
* 値オブジェクト
* エンティティ
* 検証
* ビジネス・ルール
* フォーマッター
* マッパー
* レデューサー
* 状態遷移
* エラーの分類
* 統計の算出

### ドメイン・テスト

ドメイン・テストは、ビジネス・ルールを検証します。

例:

* パッケージの識別子
    * Given: `vendor/package`
    * Then: 有効なパッケージ識別子として扱う

* 統計
    * Given: 日別ダウンロード数 / 月別ダウンロード数 /総ダウンロード数
    * Then: 正しい統計モデルが生成される

## 検証テスト

検証は、境界値を含めて検証します。

対象例:

* 空の文字列
* 空白
* 最小長
* 最大長
* 無効な文字
* 無効な URL
* 無効なパッケージ名
* 無効なリポジトリ URL
* 無効な統計値

境界値テストでは、下記を原則とします。

* 最小値 - 1
* 最小値
* 最小値 + 1

* 最大値 - 1
* 最大値
* 最大値 + 1

## 状態機械テスト

遷移の形式は [`state_machine.md`](./state_machine.md) を正本とします。
本節は、「レデューサーを I/O なしで検証する」「下記を重点ケースとする」ことのみを定めます。

* `(State, Event) -> (State, Effect*)` に対して、同一の入力は、同一の出力
* 既存データありのエラー (データが消失しない)
* 既存データありのリフレッシュ (リフレッシュ中に既存データが消失しない)
* 「Stale ≠エラー」(キャッシュあり + Stale 通知をエラーと混同しない)

## エフェクト・テスト

遷移の形式は [`state_machine.md`](./state_machine.md) を正本とします。
本節は、「レデューサー・テストで、ネットワーク・リクエストを実行せず、エフェクト・テストでは、テスト用ダミー・リポジトリ等で、操作を検証する」ことのみを定めます。

## ユースケース・テスト

ユースケースは、ユーザー目的単位で、テストします。ボタン単位のテストではなく、「ユーザー目的」が達成されることを検証します。

例:

* パッケージリストのロード
* パッケージ詳細のロード
* パッケージのリフレッシュ
* パッケージの検索
* 統計のロード
* 統計のリフレッシュ
* お気に入りの追加
* お気に入りの削除
* 認証
* セッションの復元

## リポジトリ・テスト

リポジトリは、ドメイン/アプリケーション層とインフラストラクチャ層の境界として、テストします。

対象:

* `PackageRepository`
* `StatisticsRepository`
* `AuthenticationRepository`
* `SettingsRepository`

### リポジトリ契約

リポジトリ・インターフェースに対して、契約テストを定義します。

たとえば、`loadPackage` について、下記を検証します。

* 成功
* 見つからない
* ネットワーク・エラー
* 認証エラー
* 無効レスポンス
* タイムアウト
* オフライン

## API テスト

API テストは、本番 API に直接依存しません。テストは、テスト用ダミー/スタブ HTTP レスポンスを API クライアントに渡します。

### Packagist

Packagist API クライアントでは、下記を検証します。

* パッケージ JSON 解析
* パッケージ・メタデータのマッピング
* 統計のマッピング
* ダウンロード数のマッピング
* バージョンのマッピング
* メンテナーのマッピング
* 無効な JSON
* 欠落フィールド
* 予期しないフィールド
* HTTP エラー
* タイムアウト
* レート制限関連エラー

### GitHub

GitHub API クライアントでは、下記を検証します。

* リポジトリ 解析
* オーナーのマッピング
* スター数
* フォーク数
* Issue 数
* PR 数
* リポジトリの URL
* トラフィック・データ
* 無効なレスポンス
* 認証エラー
* レート制限
* 権限エラー

## API フィクスチャ

API テストでは、フィクスチャを利用します。

フィクスチャは、実際の API レスポンスをそのまま保存する場合と、テストに必要な最小構造を持つ合成フィクスチャに分けてもかまいません。

フィクスチャに、クレデンシャル (資格情報) / 個人情報を含めません。

推奨構造:

```text
fixtures/
├── packagist/package.json
├── github/repository.json
└── domain/package.json, statistics.json
```

## API 契約テスト

「データ転送オブジェクト (DTO) ≠ドメイン」は [`models_spec.md`](./models_spec.md) を正本とします。
本節は、「外部 API と、期待される契約と、アプリケーション・モデルの互換を、契約テストで保護する」ことのみを定めます。

API 仕様変更時は、アプリケーション・モデル/マッパー/フィクスチャ/API 仕様を同時に見直します。

## ストレージ・テスト

ストレージ・テストは、永続化データと復元可能な状態を分離します。クレデンシャル (資格情報) は、通常のアプリケーション・ストレージに保存しないため、ストレージ・テストの対象から除外します。

対象:

* パッケージ・データ
* お気に入りデータ
* 統計スナップショット
* アプリケーション・ユーザー設定 (Preference)
* 復元可能なナビゲーション状態

## キャッシュ・テスト

キャッシュは、下記の状態を検証します。

* 欠落
* 新鮮
* Stale
* 無効

キャッシュ状態の意味は [`cache_spec.md`](./cache_spec.md) を正本とします。
本節は、「欠落/新鮮/Stale/無効を検証する」ことのみを定めます。

新鮮では、キャッシュ済みデータを返し、Stale かつオンラインでは、リフレッシュ、オフラインでは、キャッシュを維持することを確認します。

## キャッシュの一貫性

同一パッケージについて、下記の優先順位と更新規則が正しいことを検証します。キャッシュ更新中にアプリケーション状態が、不整合にならないことを確認します。

* メモリ・キャッシュ
* 永続化キャッシュ
* リモート API

## 認証テスト

許可状態とライフサイクルは [`authentication_spec.md`](./authentication_spec.md) を正本とします。
Packagist 認証の実装時期は [`use_cases.md` 優先順位-1](./use_cases.md#優先順位-1) の UC-16を正本とします。GitHub 認証以降 (UC-17〜 UC-20) の実装時期は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) を正本とします。初期バージョンの最優先ではありません。
本節は、「未認証→リクエスト済→認証中→認証済みを検証する」「認証中→失敗→未認証を検証する」ことのみを定めます。

クレデンシャル (資格情報) 本体を、テスト・ログに出力しません。

## クレデンシャル (資格情報) ストレージ・テスト

保存 HOW は [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md) を正本とします。
本節は、「保存/ロード/更新/削除/クレデンシャル欠落/クレデンシャル無効/移行を実 Token なしで検証し、本体をテストログに出さない」ことのみを定めます。

## ナビゲーション・テスト

行き先と戻り方は [`navigation_spec.md`](./navigation_spec.md) を正本とします。
本節は、「ナビゲーション・セマンティクスを検証し、ナビゲーション・パスにドメイン・オブジェクト全体を保持せず、識別子等の軽量な値で復元できる」ことのみを定めます。

## 状態復元テスト

復元対象と禁止対象は [`application_state.md`](./application_state.md) を正本とします。
本節は、「再起動後に、復元可能な状態から、安全に初期状態を再構築できることを検証する」ことのみを定めます。

## Android UI テスト

Android 版の開発に着手したあと、Android トラックで Compose UI のテストを使用します。時期は [`overview.md`](./overview.md)、トラックの分割は [`release.md`](./release.md) を正本とします。

Compose テストは、セマンティクスを利用して UI 要素を検索し、アサーション/アクションを実行します。

* Finder → セマンティクス・ノード → アサーション/アクション

Android では、UI テストをスクリーン全体だけでなく、必要に応じて、コンポーネント/Composable 単位でも実施します。

(参考: [Common patterns | Jetpack Compose | Android Developers](https://developer.android.com/develop/ui/compose/testing/common-patterns))

* 英語

* 長文
* 複数形
* 日付 / 数値のフォーマット

## エラー処理テスト

エラーは、アプリケーション・エラーのモデルに変換されることを検証します。複数層が、同一エラーを異なる意味で表示しないこと。

代表的なエラー:

* NetworkUnavailable
* NotFound
* RateLimited
* InvalidResponse
* DecodingFailure
* StorageFailure
* タイムアウト
* 無認可
* 禁止
* 不明

## オフライン・テスト

オフライン・テストは、必須とします。キャッシュ利用は [`cache_spec.md`](./cache_spec.md)、見え方は [`ui.md`](./ui.md) を正本とします。
本節は、「オンラインでデータロード後、オフラインでパッケージを開いても、キャッシュ済みデータと Stale 通知が使え、既存データを破棄しない」ことのみを定めます。

## 並行処理テスト

非同期処理について、下記を検証します。

* 重複リクエスト
* リクエスト・キャンセル
* 順序不整合レスポンス
* 最新リクエスト優先
* Stale レスポンスの無視
* リフレッシュの統合
* 並行パッケージ・リクエスト

例: リクエスト A と B が並行し、レスポンスが B → A の順でも、最新リクエスト優先 / Stale レスポンスの無視になること。

この場合、古いレスポンス A が最新状態を上書きしないことを検証します。

## パフォーマンス・テスト

体感上の遅延禁止は [`ui.md`](./ui.md) を正本とします。
本節は、「測る対象」を定めます。

対象:

* アプリケーション起動
* パッケージリストのレンダリング
* パッケージ詳細のレンダリング
* JSON デコード
* キャッシュ読み込み
* キャッシュ書き込み
* 統計計算
* 検索 / フィルター
* 大量のパッケージリスト

パフォーマンス・リグレッションを検知できるよう、代表的なベンチマークを維持します。

## メモリ・テスト

解放方針は [`cache_spec.md`](./cache_spec.md)、チャート再描画用データを捨てたとしても、履歴を消さないことは [`ui.md`](./ui.md) を正本とします。
本節は、「下記状態で使用量が連続増加しない」ことを検証します。

* 大量パッケージリスト
* 大量統計データセット
* 重複ナビゲーション
* 重複リフレッシュ
* 画面回転
* バックグラウンド/フォアグラウンド

特に、パッケージリスト↔パッケージ詳細の繰り返しで、メモリが継続的に増加しないことを確認します。

## ネットワーク・テスト

ネットワーク・テストでは、下記を再現可能にします。本番 API に対する、無制限のテスト・リクエストを、CI から実行しません。

* ネットワーク速度が遅い
* オフライン
* タイムアウト
* 接続リセット
* HTTP エラー
* レート制限
* 部分レスポンス
* 無効レスポンス

## 実 API テスト

実 API を使用するテストは、通常の CI テスト・スイートと分離し、明示的にトリガーします。ユニット/結合は、外部の依存関係を持ちません。

実 API テストは、下記の場合に限定します。

* 手動実行
* スケジュール済みテスト
* リリース候補 (RC) 検証
* API 契約検証

API レート制限を考慮します。

## テストデータ

テストデータは、下記の原則に従います。テストデータの生成は、Factory/フィクスチャ・ビルダを使用してかまいません。

1. 決定論的
2. 最小限
3. 再利用可能
4. 可読性
5. Secrets なし
6. 個人情報なし
7. 本番クレデンシャル (資格情報) なし

## テストの分離

各テストは、可能な限り、独立させます。必要な状態は、テストごとに明示的に生成します。

テスト間で、下記を共有しません。

* 可変グローバル状態
* 永続化ユーザーデータ
* 認証セッション
* ネットワーク状態
* キャッシュ状態

## テストダブル (代役オブジェクト)

外部依存を制御するため、下記を使用します。モックの過剰利用は、避けます。

* スタブ
* テスト用ダミー
* モック
* Spy
* フィクスチャ

基本方針:

* テスト用ダミー: リポジトリ / ストレージ
* スタブ: API レスポンス
* モック: インタラクション検証が必要な場合
* Spy: コール計数 / 引数検証
* フィクスチャ: 決定論的データ

## テスト可能アーキテクチャー

テスト可能性を、アーキテクチャーの要件とします。

層の依存方向は [`architecture.md`](./architecture.md) を正本とします。
本節は、「ドメイン/アプリケーションが、具体的な API クライアントやストレージの実装に直接依存しないことを、テスト可能性の要件とする」ことのみを定めます。

## リグレッション・テスト

原則として、バグ修正した場合、リグレッション・テストを追加します。流れは、下記とします。

* バグ→根本原因→リグレッション・テスト→修正→ CI

「修正しただけ」で完了せず、同じバグが再発した場合に、CI が検知できる状態を目指します。

## セキュリティ・テスト

漏洩面は [`security_spec.md`](./security_spec.md) を正本とします。
本節は、「ログ記録/フィクスチャ/スナップショット/テスト成果物/ソースコードに Token を残さないことを検証する」ことのみを定めます。

## スナップショット・テスト

スナップショット・テストは、必要に応じて、使用します。ただし、スナップショット・テストを、ビジネスロジック・テストの代替として使用しません。

スナップショットの更新は、意図した UI 変更と同時に行います。

対象例:

* 複合コンポーネント
* タイポグラフィ
* レイアウト
* 空状態
* エラー状態
* ダークモード
* 翻訳

## テスト・タグ

テスト・スイートは、下記のような、タグ/カテゴリーを持たせてもかまいません。CI では、必要に応じて、テスト・カテゴリーを、分離して実行します。

* unit
* integration
* ui
* e2e
* network
* security
* performance
* release

Swift のテストは、テストのグルーピング/タグ付け/パラメータ化等をサポートしているため、テスト・スイートの整理に利用できます。

(参考: [Swift Testing | Apple Developer Documentation](https://developer.apple.com/documentation/testing/))

## リリース後スモーク・テスト

実施必須は [`release.md`](./release.md) を正本とします。

重大な失敗が確認された場合は [`release.md`](./release.md) のインシデント/ホットフィックス・プロセスに従います。

## テスト失敗の方針

テスト失敗を検知した場合、調査した後で、テスト失敗/プロダクト・バグ/環境失敗/フレーク・テストに分類します。

フレーク・テストを「無視してリトライ」するだけの運用は禁止します。フレーク・テストは、Issue として記録し、原因を調査します。

## フレーク・テスト

フレーク・テストとは、同一コード/同一環境に対して、結果が安定しないテストと定義します。フレーク・テストは、リトライだけで CI 合格 として扱いません。

代表例:

* タイミング依存性
* レース・コンディション
* ネットワーク依存性
* 共有状態
* ランダム・データ
* デバイス固有の挙動

## テスト・カバレッジ

カバレッジは、品質の唯一の指標としません。

カバレッジではなく、ビジネス・リスク/状態空間/失敗モード/重要なユーザーのフローにもとづく、リスク・ベースのテスト設計を重視します。

特に下記は、高いテスト・カバレッジを目標とします。

* ドメイン・ルール
* 状態機械
* 統計計算
* 検証
* 認証状態
* キャッシュ・ルール
* エラー処理
* リポジトリ契約

## クリティカル・パス

クリティカル・パスは [リリース後スモークテスト](#リリース後スモークテスト) の操作順を正本とします。
本節は、「そのフローを、リリース候補 (RC) / 本番スモーク・テストで必ず確認する」ことのみを定めます。

## 最終テストの方針

カバレッジ件数ではなく、ドメイン・ルール/アプリケーション挙動/状態遷移/外部境界/ユーザー・インタラクション/リリース品質を、適切なテストのレベルで検証することを基本とします。

プラットフォーム固有の UI とプラットフォーム非依存ロジックを分離してテストし、将来の Kotlin Multiplatform (KMP) / Android でも、ビジネスロジック・テストを再利用できる構造を維持します。
