# S2J Package Dashboard - キャッシュ仕様

## 概要

本ドキュメントは、S2J Package Dashboard の初期設計における、キャッシュを定義します。

プロバイダ API、統計仕様、ストレージ実装、iOS/iPadOS/Android 実装、Kotlin Multiplatform (KMP) 移行等に応じて、更新します。

## 目的

本ドキュメントでは、キャッシュの対象データ、有効期間、鮮度、無効化、リフレッシュ、オフライン利用およびプロバイダ別キャッシュ方針を定義します。キャッシュ方針の正本は本仕様とします。

キャッシュは、「再取得可能なデータを一時的に保持し、ネットワーク・リクエストの削減および UI レスポンスの改善を目的とするデータ」と定義します。

## 非目的

本仕様は、クラウド同期、外部バックエンド、チャートのレンダリング、SwiftUI/Compose レイアウトを詳細に定義しません。

## 責務

有効期限 (TTL) / 鮮度 / Stale / 無効化 / リビルド、オフライン時のカレント・データ利用を定義します。

## 非責務

永続化および履歴スナップショットは [`storage_spec.md`](./storage_spec.md)、統計指標の意味は [`statistics_spec.md`](./statistics_spec.md)、API エンドポイントは各 API 仕様、認証フローとクレデンシャル (資格情報) 保存は [`authentication_spec.md`](./authentication_spec.md)、フォアグラウンド復帰時の既存表示の維持と鮮度の表示文言は [`ui.md`](./ui.md)、共有対象は [`architecture.md`](./architecture.md)、Kotlin Multiplatform (KMP) の HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とします。

## キャッシュの基本原則

キャッシュは、下記を原則とします。

1. キャッシュは「信頼できる情報源 (SoT)」ではない
2. キャッシュは再構築可能である
3. キャッシュ消失によってアプリケーション・データ全体を失わない
4. キャッシュと履歴スナップショットを混同しない
5. キャッシュの鮮度を明示的に管理する
6. Stale キャッシュを、可能な限り、有効利用する
7. キャッシュ失敗で、アプリケーション全体を停止しない
8. クレデンシャル (資格情報) をキャッシュしない
9. プロバイダごとに適切なキャッシュ方針を設定する
10. プラットフォーム固有のキャッシュ API に、ドメイン・ロジックを依存させない

## キャッシュ仕様の概要

基本方針は [キャッシュの基本原則](#キャッシュの基本原則) を正本とします。
v1固有の制約は、キャッシュをローカルに限り、デバイス横断型同期と外部キャッシュ・サーバーを必須としないこととします。

## キャッシュとスナップショット

キャッシュとスナップショットは、明確に分離します。

* キャッシュ: カレント・データを再利用するための一時データ
* スナップショット: 履歴統計として保存するデータ

キャッシュを削除しても、履歴スナップショットは削除しません。スナップショットの不変条件は [`domain_rules.md`](./domain_rules.md)、スキーマ / 保持 / 移行は [`storage_spec.md`](./storage_spec.md) を正本とします。

## キャッシュ vs スナップショット

区別の意味は [キャッシュとスナップショット](#キャッシュとスナップショット) を正本とします。
キャッシュの有効期限 (TTL) は、スナップショットの保持とは無関係です。

## キャッシュと「信頼できる情報源 (SoT)」

現在の統計の「信頼できる情報源 (SoT)」は、プロバイダ側のデータとします。キャッシュはそのコピーであり、プロバイダの代替ではありません。

## キャッシュ・アーキテクチャー

層の置き場所は [`architecture.md`](./architecture.md) を正本とします。
本仕様は、「キャッシュをリポジトリとプロバイダ API の間に置き、アプリケーション・ロジックからキャッシュの存在を必須としない」ことのみを定めます。

## キャッシュ境界

ドメイン層は URLCache / NSCache 等のキャッシュ・フレームワークに依存しません。アクセスは `CacheRepository` 経由とし、プラットフォーム実装はアダプタに置きます。

## キャッシュ・リポジトリ

具体的な API は実装時に定義します。

概念:

`CacheRepository` を利用可能とします。

例:

* `get(key)`
* `put(key, value)`
* `remove(key)`
* `clear()`

## キャッシュ可能データ

初期バージョンでは、下記をキャッシュ対象とします。

* パッケージ・メタデータ
* リポジトリ・メタデータ
* 現在の統計
* プロバイダ・ケイパビリティ

## キャッシュ不能データ

クレデンシャル (資格情報) をキャッシュしないことは [`authentication_spec.md`](./authentication_spec.md) / [`security_spec.md`](./security_spec.md) を正本とします。
本仕様は、「パスワード / Token / 認可ヘッダーをアプリケーション・キャッシュに入れない」ことのみを定めます。

## API レスポンス

「データ転送オブジェクト (DTO) ≠ドメイン」は [`models_spec.md`](./models_spec.md) を正本とします。
本仕様は、「API レスポンス全文を、無条件にアプリケーション・キャッシュに保存せず、検証・ドメイン写像後のキャッシュ可能モデルだけをキャッシュする」ことのみを定めます。

## HTTP キャッシュ vs アプリケーション・キャッシュ

下記を区別します。

* HTTP キャッシュ: HTTP レスポンスのキャッシュ
* アプリケーション・キャッシュ: アプリケーションが意味を理解したカレント・データのキャッシュ

iOS の `URLCache` は、HTTP/HTTPS レスポンスをメモリ/ディスクにキャッシュできるが、アプリケーションのドメイン・キャッシュとは別物として扱います。

(参考: [developer.apple.com](https://developer.apple.com/documentation/foundation/accessing-cached-data?changes=_3))

## `URLCache`

iOS 実装では、`URLCache` を HTTP 層のキャッシュとして利用可能とします。`URLCache` は S2J のカレント・データ・キャッシュと同一視しません。

## `URLCache` パージ

iOS では、ディスク・キャッシュがシステムによってパージされる可能性があります。

したがって、URLCache の存在をアプリケーション・データの永続性保証として利用しません。

(参考: [developer.apple.com](https://developer.apple.com/documentation/foundation/urlcache?changes=_6))

## アプリケーション・キャッシュ

カレント・データについて、必要に応じて、アプリケーション管理型キャッシュを利用します。

例:

* `PackageCurrentCache`
* `StatisticsCurrentCache`
* `RepositoryCurrentCache`

## キャッシュ・キー

キャッシュには、一意なキャッシュ・キーを持たせます。

概念: キャッシュ・キーは、「プロバイダ + リソース + 識別子 + パラメータ」を組み合わせて一意にする。

## パッケージ・キャッシュ・キー

例: `packagist:package:vendor/package`

## リポジトリ・キャッシュ・キー

例: `github:repository:owner/repository`

## 統計キャッシュ・キー

統計については、指標および期間等を考慮します。

例: `packagist:statistics:vendor/package:downloads`

## パラメータ化キャッシュ

API クエリー・パラメータによって結果が変化する場合、キャッシュ・キーにパラメータを含めます。

## キャッシュ・キーの安定性

キャッシュ・キーは、プロバイダ API URL 自体と同一である必要はありません。

ドメイン上で安定したアイデンティティを優先します。

## キャッシュ・エントリ

キャッシュ・エントリは、最低限、`key` / `value` / `fetchedAt` / `expiresAt` / `schemaVersion` を持ちます。

## `fetchedAt`

`fetchedAt` は、「S2J Package Dashboard がプロバイダからデータを正常取得した時点」を表します。

## `expiresAt`

`expiresAt` は、キャッシュが「新鮮」として扱える期限を表します。

## 新鮮

`now < expiresAt` の場合、「新鮮」とします。

## Stale

`now >= expiresAt` の場合、「Stale」とします。これを「期限切れ」とは呼びません。

## Stale キャッシュ

Stale キャッシュは、即時削除しません。

ネットワーク・リクエストが失敗した場合などに、最終確認データとして利用可能とします。

## キャッシュ状態

キャッシュ状態は、下記を基本とします。

* 欠落
* 新鮮
* Stale
* 無効

### 欠落

キャッシュ・エントリが存在しない場合、「欠落」とします。

### 無効

キャッシュ・エントリがスキーマ検証等に失敗した場合、「無効」とします。

### 無効キャッシュ

無効キャッシュは、正常なカレント・データとして UI に渡しません。

必要に応じて、削除して再取得します。

### 鮮度

鮮度は、データ有効性とは異なります。

* 新鮮
* Stale

は、

* 有効
* 無効

とは別概念とします。

## キャッシュの有効性

キャッシュされたデータが、ドメイン・ルール上、有効であることを確認してから利用します。

## キャッシュ検証

キャッシュ読み取り時には、必要に応じて、下記を検証します。

* スキーマ・バージョン
* パッケージ・アイデンティティ
* 指標タイプ
* 単位
* タイムスタンプ
* 可用性

## キャッシュ・スキーマ・バージョン

キャッシュ・エントリには、必要に応じて、スキーマ・バージョン `schemaVersion` を保持します。

アプリケーション・バージョンとは分離します。

## スキーマ不一致

キャッシュ・スキーマが、現在アプリケーションで解釈できない場合、`Invalid` として扱い、必要に応じて、再取得します。

## キャッシュ移行

キャッシュについては、履歴スナップショットほど厳密な移行を要求しません。

再取得可能なキャッシュについては、旧エントリを破棄して再取得することを許可します。

デバイス移行時にキャッシュが失われても、履歴スナップショット/ユーザー設定 (Preference) が保持されていれば正常とします。

## キャッシュの有効期限 (TTL)

キャッシュ TTL は、プロバイダおよび指標の性質に応じて、設定します。

固定 TTL を全データに適用しません。

## プロバイダ固有の有効期限 (TTL)

初期バージョンでは、プロバイダ/リソース単位で TTL を定義可能とします。具体値は、実測結果に応じて、調整します。

上流がキャッシュ期間を公表している場合、クライアント TTL はその期間以下とします。公表期間より長いクライアント TTL は採用しません。短い方、つまり上流の期間に合わせます。

GitHub と Packagist の数値を、一つの TTL にまとめません。リソースごとに判定します。上流が固定 TTL を公表せず、条件付きリクエストを提供する場合は、再検証を鮮度の正本とします。固定の再取得間隔は、上流 TTL ではありません。

例:

* Packagist パッケージ API: 上流はレスポンスを12時間キャッシュします。クライアント TTL は12時間以下とします。正本は [`api-packagist.md`](./api-packagist.md) です
* Packagist Composer メタデータ: 固定 TTL を鮮度の正本にしません。`If-Modified-Since` で再検証します
* Packagist 検索: 短めの TTL
* Packagist API エラー: キャッシュしない、または短めの TTL
* GitHub リポジトリ・メタデータ: 上流に固定 TTL はありません。`ETag` / `Last-Modified` で再検証します。再取得間隔の例は1時間です
* GitHub トラフィック: 鮮度は、上流が公表するキャッシュ期間に合わせます。クライアント TTL はその期間を超えません。14日は保持期間であり、キャッシュ TTL ではありません。上流が固定 TTL を公表しない場合は、再検証を鮮度の正本とします。現在レスポンスはスナップショットとして残します。正本は [`api-github.md`](./api-github.md) です

## 統計の有効期限 (TTL)

統計は、指標の更新頻度に応じて、TTL を決定します。その場合も、上流が公表するキャッシュ期間は超えません。GitHub トラフィックは、更新頻度から TTL を決めません。

## 変化が遅いデータ

パッケージ説明等の、比較的変化が少ないデータ については、長めの有効期限 (TTL) を許容します。長くする場合も、上流が公表するキャッシュ期間は超えません。

## 変化が速いデータ

変化の速いデータでも、クライアント TTL は上流が公表するキャッシュ期間を超えません。GitHub トラフィックに、上流と別に短めの TTL を設けません。鮮度は、[プロバイダ固有の有効期限 (TTL)](#プロバイダ固有の有効期限-ttl) の GitHub トラフィックを正本とします。

## ユーザー・リフレッシュ

ユーザーが明示的にリフレッシュした場合、通常の有効期限 (TTL) を無視して、再取得可能とします。

## 手動リフレッシュ

明示更新は [ユーザー・リフレッシュ](#ユーザーリフレッシュ) を正本とします。

## リフレッシュ失敗

リフレッシュに失敗した場合、既存キャッシュを削除しません。

## リフレッシュ失敗 UI

見え方は [`ui.md`](./ui.md) を正本とします。
本仕様は、「リフレッシュ失敗時に既存キャッシュの鮮度をプレゼンテーション層に渡す」ことのみを定めます。

## キャッシュなし + 失敗

空/エラーの見え方は [`ui.md`](./ui.md) を正本とします。
本仕様は、「キャッシュなし、かつ取得失敗を `データなし + エラー` として扱う」ことのみを定めます。

## 偽0なし

0と欠測の区別は [`domain_rules.md`](./domain_rules.md) を正本とします。
本仕様は、「キャッシュ欠落 / API 失敗を `指標 = 0` に変換しない」ことのみを定めます。

## オフライン・モード

オフライン時には、新鮮キャッシュを優先して利用します。

## オフライン・ Stale

見え方は [`ui.md`](./ui.md) を正本とします。
本仕様は、「オフライン時に新鮮がなければ、Stale キャッシュを利用可能とする」ことのみを定めます。

## オフラインのキャッシュなし

見え方は [`ui.md`](./ui.md) を正本とします。
本仕様は、「キャッシュがないオフラインでは、プロバイダ・データを表示できない」ことのみを定めます。

## オフライン・スナップショット

オフライン状態で、プロバイダ・データを取得していない場合、新しい履歴スナップショットを生成しません。

## スナップショットの作成

スナップショットの生成規則は [`domain_rules.md`](./domain_rules.md) を正本とします。
キャッシュ・ヒットだけを理由に、新規スナップショットを生成しません。

## キャッシュ・ヒット

新鮮キャッシュがある場合、それをカレント・データとして返します。

## キャッシュ・ミス

キャッシュが欠ける場合、プロバイダからフェッチし、成功後にキャッシュを更新します。

## 再検証中の Stale (SWR)

可能な場合、Stale キャッシュを表示しつつ、バックグラウンド・リフレッシュします。見え方は [`ui.md`](./ui.md) を正本とします。
本仕様は、「UI が、Stale を新鮮データと誤認しない」ことのみを定めます。

## バックグラウンド再検証

既存データがあるリフレッシュの見え方は [`ui.md`](./ui.md) を正本とします。
本仕様は、「バックグラウンド再検証で、既存キャッシュを消去してからフェッチしない」ことのみを定めます。

## キャッシュ・スタンピード

同一リソースに対して複数のリクエストが同時発生した場合、同一キャッシュ・エントリへの重複リクエストを、可能な限り、抑制します。

## リクエスト結合

同一リソースへの同時リクエストを、可能な範囲で、単一のプロバイダ・リクエストにまとめます。

## 並行リフレッシュ

同一パッケージのリフレッシュ要求が同時に複数発生した場合、無制限に API リクエストを発行しません。

## キャッシュ・ロック

必要に応じて、キャッシュ・キー単位で、リフレッシュ処理を直列化します。

## キャッシュ書き込み

「データ転送オブジェクト (DTO) ≠ドメイン」は [`models_spec.md`](./models_spec.md) を正本とします。
本仕様は、「ドメイン検証成功後にだけ、キャッシュ書き込みする」ことのみを定めます。

## 失敗したフェッチ

HTTP エラー/デコード・エラー/ドメイン検証エラーの場合、キャッシュを更新しません。

## 部分フェッチ

一部指標のみ取得できた場合、部分キャッシュ・エントリとして保存可能とします。

ただし、欠落指標を0に変換しません。

## 部分キャッシュ

部分キャッシュには、指標単位の可用性を保持します。

* ダウンロード数: 利用可能
* トラフィック: 利用不能

## プロバイダ固有キャッシュ

下記のように、プロバイダごとに、キャッシュ名前空間を分離します。

* `packagist:`
* `github:`

## プロバイダ横断型の衝突

下記を同一キャッシュ・エントリとして扱いません。

* `packagist:package:foo/bar`
* `github:repository:foo/bar`

## 現在のデータモデル

現在のキャッシュは、ドメイン・モデルまたは専用キャッシュ・モデルとして保持します。

## キャッシュ・モデル

永続化モデルとドメイン・モデルの分離は [`models_spec.md`](./models_spec.md) を正本とします。
本仕様は、「キャッシュ・レコードを、マッパー経由でドメイン・モデルに写す」ことのみを定めます。

## キャッシュ・ストレージ

保存 HOW は [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md) を正本とします。
本仕様は、「メモリ / HTTP / ローカル永続化を利用してよいが、ドメイン層から具体的なフレームワークに依存しない」ことのみを定めます。

## メモリ・キャッシュ

メモリ・キャッシュは、高速な現在セッション・キャッシュとして利用します。

アプリケーション終了で消失してもかまいません。

## ディスク・キャッシュ

ディスク・キャッシュは、アプリケーション再起動後にも再利用する必要がある場合に、使用します。

## システム管理型キャッシュ

プラットフォームが管理するキャッシュは、アプリケーションが完全な永続化を保証できません。

## iOS `URLCache` の方針

iOS の HTTP 層では、`URLSessionConfiguration.requestCachePolicy` を利用して、キャッシュ方針を制御可能とします。

Apple ではデフォルトの `useProtocolCachePolicy` が HTTP キャッシュ・コントロール等に従う方針として定義されています。

(参考: [developer.apple.com](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/requestcachepolicy?changes=l_9))

## iOS エフェメラル・セッション

クレデンシャル (資格情報) や機密データを含むリクエストでは、必要に応じて、エフェメラル・セッション等を利用します。

エフェメラル・セッションは、キャッシュ/Cookie/クレデンシャル (資格情報) をディスクに保存しません。

(参考: [developer.apple.com](https://developer.apple.com/documentation/foundation/urlsessionconfiguration))

## 機密 HTTP レスポンス

機密データを含む HTTP レスポンスについては、ディスク・キャッシュに保存しないことを基本とします。

## クレデンシャル (資格情報) を含むリクエスト

認可ヘッダーを含むリクエストについては、HTTP キャッシュによる、データ漏洩を避けます。

必要に応じて、下記の方針を使用します。

* キャッシュなし
* メモリのみ

## 公開統計

Packagist/GitHub の公開統計については、キャッシュを利用可能とします。

## 認可済み統計

認証/認可が必要な統計は、公開キャッシュと同一方針にしません。

## ユーザー固有キャッシュ

ユーザー・アカウントに依存するデータについては、キャッシュ・キーにアカウント・アイデンティティを含めます。

## アカウント切り替え

アカウントが変更された場合、旧アカウントのキャッシュを新アカウントに誤って利用しません。

## ログアウト

ログアウト時には、ユーザー固有キャッシュを削除します。

クレデンシャル (資格情報) 削除方針は [`authentication_spec.md`](./authentication_spec.md) に従います。

## ログアウト後の公開キャッシュ

公開パッケージ・メタデータ等については、ログアウト後も保持可能とします。

ただし、ユーザー固有データと混同しないこと。

## キャッシュの分離

下記を別の名前空間として扱います。

* 公開
* アカウント固有
* クレデンシャル (資格情報) 関連

## キャッシュの暗号化

キャッシュに機密データを保存する必要が生じた場合、プラットフォーム・データ保護等を利用します。

ただし、初期バージョンでは、機密データをキャッシュしないことを優先します。

## キャッシュのログ記録

キャッシュ値自体を本番ログに出力しません。

## キャッシュ指標

デバッグ/診断では、下記を計測可能とします。

* キャッシュ・ヒット
* キャッシュ・ミス
* Stale ヒット
* リフレッシュ
* 淘汰
* 失敗

## キャッシュ・ヒット率

パフォーマンス分析のため、キャッシュ・ヒット率を計測可能とします。

ただし、本番 UI で常時表示する必要はありません。

## キャッシュの遠隔計測

遠隔計測を導入する場合も、パッケージ名やユーザー・アカウント等の、不要な個人情報/機密データを送信しません。

## キャッシュ淘汰

キャッシュ容量を超えた場合、再取得コストが低いデータから、淘汰可能とします。

## 淘汰の優先順位

メモリ・キャッシュでは「古い / 最も最近使われていないもの (LRU)」等の方針を利用可能とします。

## 履歴データの優先順位

淘汰時にも、履歴スナップショットを、キャッシュ淘汰の対象として扱いません。

## キャッシュ容量

キャッシュ容量には、上限を設定可能とします。

## ディスク・プレッシャー

デバイス・ストレージが不足した場合、キャッシュを優先的に削除可能とします。

## データの優先順位

下記は、ストレージ・プレッシャー時の優先順位です。ただし、クレデンシャル (資格情報) はキャッシュ対象外です。

1. クレデンシャル (資格情報)
2. 履歴スナップショット
3. ユーザー設定 (Preference)
4. カレント・データ・キャッシュ
5. 一時データ

## キャッシュ・クリア

ユーザーがキャッシュ・クリア を実行した場合、下記を削除可能とします。

* 現在キャッシュ
* HTTP キャッシュ
* 一時キャッシュ

## キャッシュ・クリアは、履歴を削除しない

キャッシュ・クリアでは、「履歴スナップショット」を削除しません。

## キャッシュ・クリアは、お気に入りを削除しない

キャッシュ・クリアでは、「お気に入り」「管理対象」を削除しません。

## キャッシュ・クリア・フィードバック

キャッシュ・クリア後には、次回アクセス時にプロバイダから再取得されることを明示可能とします。

## 自動無効化

下記の場合、キャッシュを無効化可能とします。

* 有効期限 (TTL)
* 手動リフレッシュ
* アカウント変更
* スキーマ変更
* プロバイダ変更
* データ破損

## パッケージの削除

パッケージをダッシュボードから削除した場合、そのパッケージの現在キャッシュを削除可能とします。

履歴スナップショットは別方針とします。

## リポジトリの変更

パッケージのリポジトリの関連付けが変更された場合、旧リポジトリ・キャッシュを、必要に応じて、無効化します。

## プロバイダ API バージョンの変更

プロバイダ API スキーマ変更によりキャッシュ・データが解釈できなくなった場合、キャッシュを破棄して再取得可能とします。

## キャッシュの有効期限

有効期限は、キャッシュ・エントリ単位で判定可能とします。

## 厳密な有効期限

`expiresAt` による、「厳密な有効期限」を基本とします。

## 弾力的な有効期限

初期バージョンでは、データの鮮度が、利用頻度によって無制限に延長されることを避けるため、単純な「弾力的な有効期限」を基本方針としません。

## 再検証

キャッシュが Stale になった場合、プロバイダに再検証できます。

## HTTP 条件付きリクエスト

プロバイダ/HTTP サーバーが対応する場合、ETag/Last-Modified 等の条件付きリクエストを利用可能とします。

## `304` Not Modified

HTTP `304` 等でデータ変更がないことが確認できた場合、既存キャッシュの `fetchedAt` / 有効期限の方針を更新できます。

## HTTP ヘッダーの方針

HTTP キャッシュ・コントロール等のサーバーの方針を、可能な限り、尊重します。

ただし、アプリケーション・キャッシュ方針がより厳しい場合はアプリケーション方針を優先します。

## サーバーのキャッシュ方針

サーバーのキャッシュ・コントロールを無条件に無視しません。

## アプリケーションの有効期限 (TTL) 

アプリケーションが独自 TTL を設定する場合、サーバーの方針との整合性を考慮します。

## 鮮度表示

鮮度文言は [`ui.md`](./ui.md) を正本とします。
本仕様は、「キャッシュ層が `fetchedAt` をプレゼンテーションに渡せる」ことのみを定めます。

## キャッシュ・ステータスの露出

新鮮/Stale/更新中/利用不能の伝達は [キャッシュ状態と UI](#キャッシュ状態と-ui) を正本とします。

## キャッシュ状態機械

状態の分類は [キャッシュ状態](#キャッシュ状態) を正本とします。
本仕様は、「欠落→フェッチ→新鮮、および、新鮮→ Stale の遷移」だけを定めます。

失敗時は、欠落または Stale を維持します。

## キャッシュ・リフレッシュの状態

既存データがあるリフレッシュの見え方は [`ui.md`](./ui.md) を正本とします。
本仕様は、「リフレッシュ中に、既存データを空白に戻さない」ことのみを定めます。

## リフレッシュのキャンセル

ユーザーが画面を離れた場合、不要なリフレッシュをキャンセル可能とします。

ただし、バックグラウンド・スナップショット・コレクション等とは独立したライフサイクルとします。

## リクエスト・タイムアウト

キャッシュ利用時にも、プロバイダ・リクエストには、適切なタイムアウトを設定します。

## 「キャッシュ」ファースト

通常の UI 表示では、「キャッシュ」ファーストを利用可能とします。

## 「ネットワーク」ファースト

明示的なリフレッシュ等では、「ネットワーク」ファーストを利用可能とします。

## 「キャッシュ」ファーストの方針

新鮮キャッシュがあれば表示します。欠落/Stale のときは、フェッチします。

## 「ネットワーク」ファーストの方針

先にフェッチします。成功時はキャッシュを更新して表示し、失敗時は既存キャッシュがあればそれを使います。

## 方針の選択

ユースケースに応じて、「キャッシュ」ファースト/「ネットワーク」ファースト等を選択します。

## ダッシュボードの方針

ダッシュボード初期表示では、「キャッシュ」ファーストを基本とします。

## パッケージ詳細の方針

パッケージ詳細では、新鮮キャッシュがあれば即時表示し、必要に応じて、バックグラウンド・リフレッシュを行います。

## 手動リフレッシュの方針

手動リフレッシュでは、「ネットワーク」ファーストを基本とします。

## バックグラウンドの方針

バックグラウンド更新では、API リクエスト数と バッテリー消費量を考慮します。

## スナップショット・コレクションの方針

生成の不変条件は [`domain_rules.md`](./domain_rules.md) を正本とします。
キャッシュ層では、キャッシュ・ヒットだけでスナップショットを作成せず、プロバイダ取得の成功を必要とします。

## レート制限

キャッシュは、プロバイダ・レート制限を考慮して設計します。

## レート制限レスポンス

レート制限に到達した場合、無駄なリトライを繰り返しません。

既存キャッシュがあれば、Stale データとして利用します。

## バックオフ

リトライ可能なプロバイダ・エラーについては、指数関数的バックオフ等を利用可能とします。

## リトライ制限

無制限リトライを行いません。

## キャッシュ・スタンピードの防止

同一パッケージについて、複数 UI コンポーネントが、同時にリフレッシュしても、プロバイダ・リクエストを、可能な限り、統合します。

## パッケージリスト + パッケージ詳細

リストと詳細が同じパッケージ・データを要求する場合、同一キャッシュ・エントリを共有可能とします。

## キャッシュの一貫性

キャッシュ更新後、同じキャッシュ・キーを参照するコンシューマーは、可能な限り、同一データを取得します。

## アトミック・キャッシュの更新

複数指標を一括更新する場合、部分書き込みによる不整合を避けます。

## 現在の統計キャッシュ

現在の統計を保存する場合、下記を考慮します。

* パッケージ
* プロバイダ
* 指標
* 期間
* FetchedAt

## カレント・データ vs 履歴データ

現在の統計キャッシュが更新されても、履歴スナップショットを上書きしません。

## スナップショット生成の例

生成の不変条件は [`domain_rules.md`](./domain_rules.md) を正本とします。
本仕様は、「プロバイダ取得成功後に現在キャッシュを更新し、その後スナップショット方針に従って、履歴行を書く」ことのみを定めます。

## キャッシュ失敗

キャッシュ書き込みに失敗しても、プロバイダから取得したカレント・データを UI に表示可能とします。

## キャッシュ読み取り失敗

キャッシュ読み取りに失敗しても、プロバイダ・フェッチにフォールバック可能とします。

## キャッシュ・ストレージ失敗

キャッシュ・ストレージ自体が利用不能でも、ネットワーク・フェッチが可能なら、アプリケーションを継続可能とします。

## 任意最適化としてのキャッシュ

キャッシュは、「アプリケーションの正確性に必須ではないが、パフォーマンス/オフライン・ケイパビリティを改善するもの」として扱います。

## オフラインの依存関係

完全オフラインでカレント・データを表示する場合は、キャッシュが必要となります。

ただし、オフライン表示自体をドメイン・ルールとして必須化しません。

## キャッシュ・パージ

OS/プラットフォームによるキャッシュ・パージを正常な状態として扱います。

## キャッシュ・リビルド

キャッシュ・パージ後は、プロバイダ・フェッチによりリビルドできることを基本とします。キャッシュ破損時は、キャッシュを破棄し、履歴スナップショットは保持します。

## キャッシュ・バックアップ

キャッシュを、バックアップ対象の重要ユーザーデータとして扱いません。

## キャッシュ・エクスポート

通常、キャッシュをユーザー・エクスポート対象としません。

エクスポート対象は、履歴データ/ユーザーデータを優先します。

## キャッシュ・セキュリティ

キャッシュには、下記を含めません。

* パスワード
* Token
* Secret

## キャッシュ・プライバシー

キャッシュに、不要な個人情報を保存しません。

## 公開データ

Packagist/GitHub の公開パッケージ・メタデータや公開統計は、キャッシュ可能とします。

## ユーザー固有データ

ユーザー固有データは、アカウント・アイデンティティを考慮して、キャッシュします。

## アカウントの分離

アカウント A のキャッシュを、アカウント B のセッションから利用しません。

## ログアウトのキャッシュ方針

ログアウト時、アカウント固有キャッシュは削除します。

公開キャッシュは、保持可能とします。

## 認証の状態

認証の状態の変更によって、キャッシュ・データの可用性が変化する場合があります。

## 認可のキャッシュ

認可の結果自体を、長期間キャッシュしません。

必要な場合は、短い有効期限 (TTL) を利用します。

## 権限の取り消し

権限が取り消された場合、該当する認可済みキャッシュを無効化します。

## セキュリティ境界

クレデンシャル (資格情報) の分離は [`authentication_spec.md`](./authentication_spec.md) / [`security_spec.md`](./security_spec.md) を正本とします。
本仕様は、「キャッシュ層をクレデンシャル・ストレージから分離する」ことのみを定めます。

## キャッシュの診断

デバッグ画面では、必要に応じて、下記を表示可能とします。

* キャッシュ・サイズ
* エントリ数
* ヒット数
* ミス数
* Stale 数
* 最後のクリーンアップ

## 本番の診断

本番 UI では、テクニカル・キャッシュ情報を通常ユーザーに公開しません。

## キャッシュ・テスト

最低限、下記をユニットテストします。

* キャッシュ・ヒット
* キャッシュ・ミス
* 新鮮
* Stale
* 無効
* 有効期限
* リフレッシュ
* リフレッシュ失敗
* クリア
* 淘汰

## キャッシュの一貫性テスト

パッケージリストとパッケージ詳細が、同一キャッシュ・エントリを利用しても、不整合が起きないことを確認します。

## 並行アクセスのテスト

同一キャッシュ・キーへの並行読み取り/書き込みをテストします。

## リクエスト結合テスト

同一リソースへの並行フェッチが、不必要に複数リクエストを発生させないことを確認します。

## オフライン・テスト

下記を検証します。

* 新鮮キャッシュ + オフライン
* Stale キャッシュ + オフライン
* キャッシュ + オフラインなし

## レート制限のテスト

プロバイダ・レート制限時に、既存キャッシュとレート制限エラーを同時に扱えることを確認します。

## アカウントの分離のテスト

下記が混同されないことを確認します。

* アカウント A キャッシュ
* アカウント B セッション

## キャッシュ・クリアのテスト

キャッシュ・クリア後に、下記が削除されないことを確認します。

* お気に入り
* 管理対象
* 履歴スナップショット

## スナップショットの分離のテスト

キャッシュ無効化/クリアによって、履歴スナップショットが変更されないことを確認します。

## 移行のテスト

キャッシュ・スキーマ・バージョンが変更された場合、互換なら移行、非互換なら破棄 + 再フェッチできることを確認します。

## パフォーマンス・テスト

下記を測定可能とします。

* コールドスタート
* キャッシュ・ヒット
* キャッシュ・ミス
* 再検証中の Stale (SWR)
* 大量のキャッシュ読み取り
* 大量のキャッシュ・クリア

## メモリ・プレッシャー

メモリ・キャッシュは、メモリ・プレッシャー時に解放可能とします。

ディスク/永続化キャッシュに、必要に応じて、フォールバックします。

## バッテリー

バックグラウンド・リフレッシュでは、過剰なポーリングを行いません。

## ネットワーク効率

キャッシュは、プロバイダ API リクエスト削減を目的とします。

同一データを短時間に繰り返し取得しません。

## データ鮮度 vs ネットワーク・コスト

鮮度を高めるために、無制限に API リクエストを行いません。

## ユーザー・インテントの優先順位

明示的なリフレッシュは、通常の自動キャッシュ方針より優先されます。

## システム制約

バックグラウンド実行、ネットワーク可用性、バッテリー等のプラットフォーム制約を考慮します。

## プラットフォームの独立性

ドメイン・キャッシュ方針は、iOS/iPadOS/Android で同じセマンティクスを持ちます。

## プラットフォーム固有の実装

保存 HOW は [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md) を正本とします。
本仕様は、「HTTP キャッシュ / メモリ / SQLite 系を、プラットフォーム実装としてよい」ことのみを定めます。

## Kotlin Multiplatform (KMP) 境界

共有対象は [`architecture.md`](./architecture.md) を正本とします。
本仕様は、「有効期限 (TTL) / 鮮度 / 無効化 / キャッシュ・キーを共有方針とし、ストレージ実装をアダプタに置く」ことのみを定めます。

## プラットフォーム・キャッシュ・アダプタ

Kotlin Multiplatform (KMP) の HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とします。
本仕様は、「共有キャッシュ方針を `CacheRepository` 経由でプラットフォーム・アダプタに実装する」ことのみを定めます。

## Swift 実装

保存 HOW は [`ios_spec.md`](./ios_spec.md) を正本とします。
本仕様は、「iOS でキャッシュ方針を Swift 実装してよいが、ドメイン・ロジックを SwiftUI / SwiftData / URLCache に依存させない」ことのみを定めます。

## Kotlin Multiplatform (KMP) 移行

共有に移す順序は [`architecture.md`](./architecture.md)、HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とします。
本仕様は、「キャッシュ方針を、共有ロジックに移行可能な構造とする」ことのみを定めます。

## キャッシュ・ルールのバージョン

キャッシュ方針を変更する場合、必要に応じて、`cachePolicyVersion` を更新します。

## 有効期限 (TTL) 変更

TTL 変更によって、履歴スナップショットを変更しません。

## キャッシュ方針の変更

キャッシュ方針変更時は、下記を確認します。

* 有効期限 (TTL)
* 無効化
* ストレージ
* セキュリティ
* API リクエスト頻度
* バッテリー消費

## 履歴のサイレント変更なし

キャッシュ方針変更によって、履歴スナップショットの意味を変更してはなりません。

## キャッシュのライフサイクル

基本ライフサイクル: プロバイダ→フェッチ→ 検証 →キャッシュ→新鮮→ Stale →再検証。
再検証成功なら「新鮮」、失敗なら「Stale」のまま、必要時に淘汰/クリアします。

## キャッシュ状態と UI

新鮮/Stale/更新中/利用不能の見え方は [`ui.md`](./ui.md)、状態分類は [`application_state.md`](./application_state.md) を正本とします。
本仕様は、「キャッシュ層がそれらの状態を、プレゼンテーションに伝達できる」ことのみを定めます。

## カレント・データのプレゼンテーション

値/出典の意味は [`statistics_spec.md`](./statistics_spec.md)、更新日時/鮮度の見え方は [`ui.md`](./ui.md) を正本とします。
本仕様は、「キャッシュ層が、それらをプレゼンテーションに渡せるように保持する」ことのみを定めます。

## 偽の鮮度なし

Stale を新鮮に見せないことは [`ui.md`](./ui.md) を正本とします。
本仕様は、「Stale キャッシュを、現在/新鮮データとして扱わない」ことのみを定めます。

## 偽の可用性なし

0と欠測の区別は [`domain_rules.md`](./domain_rules.md) を正本とします。
本仕様は、「認可失敗を、キャッシュ欠落 = 0にしない」ことのみを定めます。

## キャッシュ派生のスナップショットなし

キャッシュから読み出しただけのデータを、新しいスナップショットとして記録しません。

## キャッシュと履歴精度

履歴スナップショットは、キャッシュの有効期限 (TTL) に左右されません。

スナップショット・コレクションの方針に従って、独立して管理します。

## ストレージ境界

キャッシュは、[storage_spec.md](./storage_spec.md) で定義された、永続化ストレージの補助層として扱います。

## キャッシュの永続化

キャッシュの永続化は、プラットフォーム/実装に応じて、変更可能とします。

## 永続化キャッシュ vs スナップショット

キャッシュとスナップショットの分離は [キャッシュとスナップショット](#キャッシュとスナップショット) を正本とします。
本仕様は、「永続化キャッシュがあっても、履歴スナップショットと同一視しない」ことのみを定めます。

## キャッシュの削除

キャッシュの削除は、通常のユーザーデータ削除とは異なります。

## ユーザー可視の意味

ユーザー向けには、「キャッシュのクリア」を、「次回表示時に、最新データを再取得します。」という意味として扱います。
