# S2J Package Dashboard - UX フロー仕様

## 概要

本ドキュメントは、S2J Package Dashboard の初期設計における、**ユーザー体験のフロー (UX フロー)** を定義します。

UX フローとは、ユーザーが特定の目的を達成するために、下記を定義したものです。

* 経由する画面・状態は、何か
* 実行する操作は、何か
* アプリケーションが、どのように応答するか
* 成功・失敗・中断時に、どの状態に遷移するか

本仕様では、個々の UI の外観や具体的なナビゲーション API は定義しません。

分離は [シナリオ分担](#シナリオ分担) を正本とします。

したがって、本仕様は iOS/iPadOS/Android で共通の UX 意味論を定義し、各プラットフォームにおける具体的な UI 表現は [`navigation_spec.md`](./navigation_spec.md)、[`screen_spec.md`](./screen_spec.md)、[`ui.md`](./ui.md) に委ねます。

## 目的

UX フローは、下記を目的とします。

1. ユーザーが主要な目的を、迷わず達成できること
2. 操作の結果を、ユーザーが予測できること
3. ロード/エラー/空/オフライン等の状態を、明確に扱うこと
4. iPhone/iPad/Android で、同一の目的・意味論を維持すること
5. ナビゲーション UI と UX フローを、分離すること
6. ディープリンク/状態復元を考慮した、フローを定義すること
7. 実装において、期待するユーザー行動を明確にすること

## 非目的

本仕様は、スクリーンの具体レイアウト、色/タイポグラフィ、コンポーネントのビジュアル・デザイン、SwiftUI/Compose の具体実装を目的としません。

## 責務

ユーザーが、どの画面・状態を経由し、何をすると成功/失敗/中断で、どこに行くかを、正本として定義します。

## 非責務

ユースケースの目的は [`use_cases.md`](./use_cases.md)、ナビゲーションは [`navigation_spec.md`](./navigation_spec.md)、画面は [`screen_spec.md`](./screen_spec.md)、横断 UI は [`ui.md`](./ui.md)、復元対象は [`application_state.md`](./application_state.md)、遷移の形式は [`state_machine.md`](./state_machine.md)、向き/ウィンドウは [`ui-viewport.md`](./ui-viewport.md)、検証の種類は [`testing_spec.md`](./testing_spec.md)、共有対象は [`architecture.md`](./architecture.md)、Kotlin Multiplatform (KMP) の HOW は [`kmp_spec.md`](./kmp_spec.md)、API/ストレージ/キャッシュ/クレデンシャル (資格情報) は、各専門仕様を正本とします。

## シナリオ分担

| 問い | 正本 |
| --- | --- |
| 誰が、何を達成するか | [`use_cases.md`](./use_cases.md) |
| どの状態を、どの順で通るか | 本仕様 |
| その画面は、何を出すか | [`screen_spec.md`](./screen_spec.md) |
| 行き先と戻り方 | [`navigation_spec.md`](./navigation_spec.md) |

## UX フローの基本モデル

UX フローは、下記の形式で表現します。

1. ユーザーの目的
2. エントリー・ポイント
3. 初期の状態
4. ユーザー・アクション
5. アプリケーション・レスポンス
6. 次の状態/遷移先
7. 目的達成

エラーや中断が発生する場合は、別のブランチを持ちます。

ユーザー・アクションの結果に応じて:

* 成功→次回の状態
* エラー→エラー状態
* 空→「空」の状態
* キャンセル→前回の状態

## UX フローとナビゲーションの責務分離

UX フローは「どの状態を、どの順で通るか」を定義します。表示構造 (縦積み/スプリット/コンパクト) は [`navigation_spec.md`](./navigation_spec.md) を正本とします。
同じ経路でも、iPhone のプッシュと iPad の2ペインは、ナビゲーション側で変えてかまいません。

## エントリー・ポイント

アプリケーションへの入口は、下記を想定します。初期バージョンでは、通知/外部起動が存在しない場合でも、将来、追加可能な構造とします。

1. アプリケーション起動
2. ダッシュボード
3. パッケージリスト
4. パッケージ詳細
5. 統計
6. 設定
7. ディープリンク
8. 通知/外部起動
9. 状態復元

## アプリケーション起動のフロー

### 初回起動

初回に認証を必須にしないことは [`authentication_spec.md`](./authentication_spec.md) を正本とします。

経路: 起動→ローカル・システム設定 (Configuration) →認証の状態確認→ローカルのパッケージ・データ→ダッシュボード。

### 既存ユーザー

ナビゲーション状態の復元の実装時期は [状態復元のフロー](#状態復元のフロー) を正本とします。
復元対象は [`application_state.md`](./application_state.md)、フォールバック遷移先は [`navigation_spec.md`](./navigation_spec.md) を正本とします。

経路: 起動→状態復元→前回のナビゲーション。

## 初期データ・ロードのフロー

ダッシュボード表示時に、必要なデータが存在しない場合は、プロバイダから取得します。

キャッシュ/ローカルがあれば表示します。なければフェッチして表示します。

取得対象には、下記を含みます。

* Packagist パッケージ・メタデータ
* Packagist ダウンロード統計
* GitHub リポジトリ・メタデータ
* GitHub 統計
* お気に入りのパッケージ情報

管理対象のパッケージ情報は、Packagist アカウントのクレデンシャル (資格情報) を使って取得します。実装時期は [`use_cases.md` 優先順位-1](./use_cases.md#優先順位-1) の UC-02を正本とします。認証の設定は UC-16を正本とします。公開パッケージのメタデータとお気に入りは、認証を要求しません。

## ダッシュボードのフロー

### ダッシュボード表示

ダッシュボードは、ユーザーが現在のパッケージ状況を把握するための起点とします。

ダッシュボードに何を出すかは [`screen_spec.md`](./screen_spec.md)、行き先は [`navigation_spec.md`](./navigation_spec.md) を正本とします。
本フローは、「ダッシュボードを起点に、管理対象/お気に入り/統計/設定に進む経路」だけを定義します。管理対象は、タップや選択の対象とします。取得の実装時期は [`use_cases.md` 優先順位-1](./use_cases.md#優先順位-1) の UC-02を正本とします。Packagist のクレデンシャル (資格情報) 節へ進む時期は UC-16、設定画面の残りへ進む時期は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) の UC-31を正本とします。

## 管理対象のパッケージのフロー

管理対象の取得は、Packagist アカウントのクレデンシャル (資格情報) を使います。実装時期は [`use_cases.md` 優先順位-1](./use_cases.md#優先順位-1) の UC-02を正本とします。認証の設定は UC-16を正本とします。管理対象は、タップや選択の対象とします。

### 管理パッケージの表示

ユーザーが Packagist 上で管理するパッケージを取得し、一覧表示します。

経路: ダッシュボード→管理対象のパッケージ→パッケージリスト。

### パッケージの選択

パッケージを選択すると、パッケージ詳細に進みます。表示内容は [`screen_spec.md`](./screen_spec.md) を正本とします。

## お気に入りのパッケージのフロー

### お気に入りの追加

お気に入りは、管理対象のパッケージとは独立した概念とします。追加と削除は認証を要求しません。実装時期は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) の UC-06と UC-07を正本とします。初期バージョンの最優先ではありません。

ユーザーは、自身がメンテナーではないパッケージを、お気に入りとして登録できます。

1. パッケージ詳細
2. お気に入り追加
3. お気に入りの状態 = アクティブ
4. お気に入りのパッケージに出る

### お気に入りの削除

お気に入りの削除は、パッケージの削除とは異なります。

削除後も、パッケージ自体の情報は、他の参照元から取得可能であれば保持してかまいません。

1. パッケージ詳細
2. お気に入り削除
3. 確認
4. お気に入りの状態 = 非アクティブ

## パッケージ検索のフロー

パッケージ検索の実装時期は [`use_cases.md` 優先順位-1](./use_cases.md#優先順位-1) の UC-04を正本とします。実装するときのフローは、下記とします。

1. パッケージリスト
2. 検索
3. クエリー
4. Packagist 検索
5. 結果
6. 選択
7. パッケージ詳細

### 検索結果が存在しない場合

1. 検索
2. 結果なし
3. 「空」の状態

### ネットワーク・エラー

検索の詳細仕様は [`api-packagist.md`](./api-packagist.md) を信頼できる情報源 (SoT) とします。

1. 検索
2. ネットワーク・エラー
3. エラー状態
4. リトライ

## パッケージ詳細のフロー

パッケージ詳細は、パッケージの情報を集約して表示します。何を出すかは [`screen_spec.md`](./screen_spec.md) を正本とします。
本フローは、「詳細に入り、統計/外部リポジトリ/お気に入りに進む経路」だけを定義します。

外部リポジトリを開く場合は、プラットフォームの標準的な外部 URL 遷移を使用します。

## 統計のフロー

### 統計表示

期間は実装時の UX および取得可能なスナップショット範囲に応じて、調整します。

1. パッケージ詳細
2. 統計
3. 期間の選択
4. チャートの表示

対象となる期間の候補:

* `7 days`
* `30 days`
* `90 days`
* `1 year`
* すべて利用可能

### 統計の出典

統計は、プロバイダごとに出典を区別します。指標の意味は [`statistics_spec.md`](./statistics_spec.md) を正本とします。

## リフレッシュのフロー

パッケージを更新する実装時期は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) の UC-09を正本とします。初期バージョンの最優先ではありません。統計のリフレッシュは UC-12です。

### 手動リフレッシュ

ユーザーが、明示的にリフレッシュを実行した場合:

1. 現在の状態
2. リフレッシュ
3. 更新中
4. 最新データのフェッチ
5. キャッシュ/スナップショットの更新
6. 読込完了

既存データが存在する場合、リフレッシュ中も、可能な限り、既存データを表示します。

読込完了→更新中でも既存データを表示→新規データ。

### リフレッシュ失敗

既存データが存在する場合は、データを完全に消去してエラー・スクリーンに置き換えるのではなく、既存データ + Stale/エラー・インジケータ + リトライ を同時表示する状態を優先します。

更新中→ネットワーク・エラー→ Stale データ。

## オフラインのフロー

ネットワーク接続が利用できない場合でも、ローカルデータが存在する場合は、可能な範囲で、アプリケーションを利用可能とします。

起動→ネットワーク利用不能→ローカルデータ利用可能→キャッシュ済み表示。

ローカルデータが存在しない場合は、下記の通りです。

起動→ネットワーク利用不能→ローカルデータなし→オフライン空/エラー。

ユーザーには、下記を明示します。

* オフライン
* 最終更新
* リトライ

## エラー・リカバリーのフロー

エラーは「終了状態」ではなく、可能な限り、リカバリー・アクションを提供します。エラーの種類に応じて、リカバリー・アクションを変更します。

* リトライ
* キャッシュ・データの使用
* キャンセル / Back

### ネットワーク・エラー

* リトライ
* キャッシュ・データの使用

### 認証・エラー

* 再認証
* 設定を開く

### レート制限

* 待機
* 後でリトライ
* キャッシュ・データの使用

### 無効なパッケージ

* Back
* パッケージの削除

## 認証のフロー

Packagist 認証の設定の実装時期は [`use_cases.md` 優先順位-1](./use_cases.md#優先順位-1) の UC-16を正本とします。GitHub 認証以降 (UC-17〜 UC-20) の実装時期は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) を正本とします。初期バージョンの最優先ではありません。

### 認証必須

実行内容: 認証が必要な操作

1. ユーザー・アクション
2. 認証必須
3. 認証 UI
4. 認可
5. オリジナル・フローに戻る

認証後は、可能な限り、元の操作を継続します。

### 認証失敗

1. 認証
2. 失敗
3. エラー
4. リトライ または キャンセル。

認証情報を無効化している場合は、ユーザーに再認証を促します。

### クレデンシャル (資格情報) の削除

設定から認証情報を削除する場合:

1. 設定
2. 認証
3. クレデンシャルの削除
4. 確認
5. クレデンシャル削除

クレデンシャルの削除によって、ローカルのパッケージ・データやお気に入りデータを自動的に削除してはなりません。

認証情報とアプリケーション・データは、別のライフサイクルを持ちます。

## 設定のフロー

Packagist のクレデンシャル (資格情報) 節へ進む実装時期は [`use_cases.md` 優先順位-1](./use_cases.md#優先順位-1) の UC-16を正本とします。設定画面の残りの実装時期は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) の UC-31を正本とします。初期バージョンの最優先ではありません。
設定の画面構成は [`screen_spec.md`](./screen_spec.md) を正本とします。
本仕様は、「設定が、ダッシュボードの主要データ操作とは別経路である」ことのみを定めます。

## About のフロー

About を表示できることの確認は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) の UC-31を正本とします。表示内容は UC-32を正本とします。初期バージョンの最優先ではありません。
About の表示内容は [`screen_spec.md`](./screen_spec.md)、コンポーネント境界は [`component_spec.md`](./component_spec.md) を正本とします。
本仕様は、「設定から About に進む経路」だけを定めます。

[S2J About Window](https://github.com/stein2nd/s2j-about-window) 自体を S2J Package Dashboard の UX フローに再実装しません。

## ディープリンクのフロー

ディープリンクの実装時期は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) の UC-27を正本とします。パッケージの識別子を外部から指定できる構造とします。

例:

`s2jpackagedashboard://package/vendor/package`

フロー:

1. 経路の解析
2. パッケージの解決
3. パッケージ詳細

パッケージが、ローカルデータに存在しない場合:

1. パッケージの解決
2. パッケージのフェッチ
3. パッケージ詳細

取得に失敗した場合:

1. パッケージが見つからない
2. エラー

ディープリンクの URI スキーマ/ユニバーサル・リンク/Android アプリリンクの具体仕様は [`navigation_spec.md`](./navigation_spec.md) で定義します。

## 状態復元のフロー

ナビゲーション状態の復元の実装時期は [`use_cases.md` 優先順位-2](./use_cases.md#優先順位-2) の UC-26を正本とします。初期バージョンの最優先ではありません。
アプリケーションが中断・再起動された場合、可能な範囲で、ユーザーが最後に見ていた状態を復元します。

対象は [`application_state.md`](./application_state.md) を正本とします。
本フローは、「ナビゲーション状態の復元→ローカルデータの復元→表示→任意リフレッシュ」の順序だけを定めます。

Apple の SwiftUI ナビゲーションでも NavigationPath 等を用いたナビゲーション状態の保持と状態復元が、ナビゲーション・アーキテクチャーの一部として扱われています。

(参考: [Bringing robust navigation structure to your SwiftUI app | Apple Developer Documentation](https://developer.apple.com/documentation/SwiftUI/Bringing-robust-navigation-structure-to-your-swiftui-app))

Android でも、アダプティブ・ナビゲーションでは、ウィンドウサイズの変化を含むシステム設定 (Configuration) 変更に対する連続性が重要であり、選択されたコンテンツ等を保存・復元する設計が想定されています。

(参考: [Build a list-detail layout | Adaptive Apps | Android Developers](https://developer.android.com/develop/adaptive-apps/guides/list-detail))

## 画面の向き変更のフロー

画面の向き変更は、UX フロー上の新しいスクリーン遷移とはみなしません。同じスクリーン/状態を維持したまま、プレゼンテーション・レイアウトのみを変更します。向き/サイズクラスは [`ui-viewport.md`](./ui-viewport.md) を正本とします。
本フローは、「iPad (縦置き) では、パッケージ詳細が、画面の向き変更により、パッケージリスト + パッケージ詳細になっても、ナビゲーションのフローの変更ではなく、アダプティブ・レイアウトの変更として扱う」ことのみを定めます。

## ウィンドウ・リサイズのフロー

iPadOS/Android のウィンドウサイズが変化した場合も、画面の向き変更と同様にスクリーン/UX コンテキストを維持します。サイズクラスと複数ペイン/単一ペインは [`ui-viewport.md`](./ui-viewport.md) を正本とします。
本フローは、「ウィンドウ・リサイズを、新しいスクリーン遷移とみなさない」ことのみを定めます。

Android のアダプティブ・アプリケーションでは、展開ウィンドウで複数ペイン、コンパクト/ミディアムでは単一ペインとする「リスト・詳細」パターンが公式に定義されています。

(参考: [Get started with adaptive apps | Adaptive Apps | Android Developers](https://developer.android.com/develop/adaptive-apps/guides/get-started-with-adaptive-apps?hl=en))

## Back ナビゲーションのフロー

Back 操作は、ユーザーが直前の UX コンテキストに戻るために使用します。行き先と戻り方は [`navigation_spec.md`](./navigation_spec.md) を正本とします。
本フローは、「Back が前の UX コンテキストに戻る」「複数ペインでは、Back が必ずしも前画面を意味しない」ことのみを定めます。

たとえば、展開レイアウトでパッケージリストとパッケージ詳細が同時に表示されている場合、パッケージ詳細の変更は、同一 UX コンテキスト内の選択変更として扱うことができます。

したがって、Back の具体的な挙動は、プラットフォーム・ナビゲーション・モデルに従います。

## キャンセルのフロー

ユーザーが操作をキャンセルした場合は、変更前の状態を、可能な限り、維持します。キャンセルは、破壊的なアクションの確定とは異なります。

対象:

* 認証
* お気に入りの追加
* お気に入りの削除
* 設定の変更
* 検索
* フィルター
* 確認ダイアログ

## 確認のフロー

破壊的または不可逆な操作には、確認を使用します。単純なナビゲーションや、一時的なフィルター変更には、確認を要求しません。

対象例:

* クレデンシャル (資格情報) の削除
* お気に入りの削除
* ローカルデータの削除
* スナップショット・データの削除

基本のフロー:

1. ユーザー・アクション
2. 確認。確認なら実行、キャンセルなら戻る

## データ削除のフロー

ローカルデータを削除する場合:

1. 設定
2. ストレージ
3. ローカルデータの削除
4. 確認
5. 削除
6. 完了

ストレージのリセットも、同じ経路とします。リセットは、初期状態に戻す確認付き操作であり、クレデンシャル (資格情報) を含める場合は、明示します。

削除対象は、アプリケーション・データとクレデンシャルを明確に区別します。クレデンシャルの削除と、ローカルデータの削除を、一つの操作として暗黙に結合しません。対象の正本は [`storage_spec.md`](./storage_spec.md) / [`authentication_spec.md`](./authentication_spec.md) とします。
