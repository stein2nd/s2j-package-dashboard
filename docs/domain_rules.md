# S2J Package Dashboard - ドメイン・ルール仕様

## 概要

本ドキュメントは、S2J Package Dashboard の初期設計における、ドメイン・ルールを定義します。

ドメイン・モデル、統計仕様、API 仕様、ストレージ仕様、Kotlin Multiplatform (KMP) 移行方針等の変更に応じて、更新します。

## 目的

本ドキュメントでは、S2J Package Dashboard におけるドメイン・ルール、ドメイン不変性、ビジネス・ルールおよびドメイン上の状態遷移を定義します。

本仕様は、UI/永続化/API/プラットフォームから独立したドメイン層の仕様です。

## 非目的

本仕様は、HTTP、OAuth、Keychain、永続化スキーマ、UI レイアウト、チャートのレンダリング、色/タイポグラフィ/アニメーションを定義しません。

## 責務

ドメイン上の正しさ (何が妥当か、何を混同してはいけないか、どの遷移が許されるか) を正本として定義します。

## 非責務

型と層境界は [`models_spec.md`](./models_spec.md)、指標の意味と収集は [`statistics_spec.md`](./statistics_spec.md)、スナップショットの永続化は [`storage_spec.md`](./storage_spec.md)、キャッシュ方針は [`cache_spec.md`](./cache_spec.md)、表示文言は [`ui.md`](./ui.md)、層と共有対象は [`architecture.md`](./architecture.md)、Kotlin Multiplatform (KMP) の HOW は [`kmp_spec.md`](./kmp_spec.md)、検証の種類は [`testing_spec.md`](./testing_spec.md)、API の実装は各専門仕様を正本とします。

## ドメインの目的

S2J Package Dashboard は、「Packagist および GitHub 上のパッケージ/リポジトリに関する統計を取得・整理・蓄積し、ユーザーが管理対象およびお気に入りのパッケージの状態を継続的に把握できるようにする」ことを目的とします。

## ドメイン境界

本アプリケーションのドメインは、下記を中心とします。

* パッケージ
* リポジトリ
* 統計
* スナップショット
* お気に入り
* 管理対象

## ドメインに含まれないもの

下記はドメイン・ルール自体ではありません。これらはドメイン外の責務とします。

* SwiftUI ビュー
* Jetpack Compose UI
* SwiftData モデル
* SQLite スキーマ
* Packagist HTTP クライアント
* GitHub HTTP クライアント
* Keychain
* Android Keystore
* ネットワーク接続
* プラットフォーム固有の UI
* アニメーション
* レンダリング

## ユビキタス言語

本アプリケーションでは、下記の用語を統一して使用します。

| 用語 | 定義 |
| --- | --- |
| パッケージ | Packagist 上で識別される Composer Package |
| リポジトリ | パッケージの出典リポジトリ |
| 管理対象のパッケージ | ユーザー自身がメンテナンス対象として扱うパッケージ |
| お気に入りのパッケージ | ユーザーがお気に入りとして登録したパッケージ |
| カレント・データ | プロバイダから取得した現在値 |
| スナップショット | 特定時点で取得した統計の記録 |
| 指標 | 統計を構成する個々の指標 |
| プロバイダ | Packagist/GitHub 等のデータソース |
| 可用性 | 指標を取得可能かどうかを示す状態 |
| Stale | 最新の取得期限を超えたデータ |
| 派生指標 | Raw 指標から計算された指標 |

## ドメイン・ルールの原則

ドメイン・ルールは下記を満たします。

1. プラットフォームに依存しない
2. UI に依存しない
3. 永続化に依存しない
4. API エンドポイントに依存しない
5. クレデンシャル (資格情報) に依存しない
6. 決定論的である
7. テスト可能である
8. ドメイン・オブジェクト自身が守るべきルールは、ドメイン・オブジェクト内で保証する

## ドメイン不変性

ドメイン不変性とは、「ドメイン上、常に成立していなければならない条件」とします。

不変を破ったドメイン・オブジェクトを、正常なドメイン状態として扱いません。

## 無効状態

下記のような状態を、ドメイン上の有効の状態としません。

* パッケージ ID = 空
* 指標値 = NaN
* 指標値 = 無限
* スナップショット・タイムスタンプ = 無効
* 不明指標の単位
* 無効パッケージの識別子

## パッケージ・アイデンティティ

パッケージは、一意なドメイン・アイデンティティを持ちます。

## パッケージの識別子ルール

パッケージの識別子は、`vendor/package` 形式を基本とし、下記を許可しません。ただし、API アダプタが外部表現を、ドメイン識別子に変換することは可能とします。

* `vendor/`
* `package`
* `/vendor/package`
* `https://packagist.org/packages/vendor/package`

## パッケージ・アイデンティティの不変性

パッケージ・アイデンティティは、パッケージの有効期間中に変更しません。

パッケージ名の変更等がプロバイダ側で発生した場合は、別ドメイン・イベント/移行ルールとして扱います。

## リポジトリ・アイデンティティ

GitHub リポジトリは、`owner/repository` を正規識別子とします。

## リポジトリ・プロバイダ

リポジトリには、プロバイダを持たせます。将来的なプロバイダ追加を妨げません。

例: `github`

## パッケージ/リポジトリのリレーションシップ

パッケージとリポジトリの関係は、必ずしも1対1とは限りません。ドメイン・モデルでは、パッケージがリポジトリ・リファレンスを持ちます。

## パッケージは、リポジトリと等しくない

Packagist パッケージと GitHub リポジトリを同一アイデンティティとして扱いません。同じ名前を持つ場合でも、それぞれ独立したドメイン・オブジェクトとします。

## 管理対象のパッケージ

管理対象のパッケージとは、「ユーザーが自身のメンテナンス対象として、ダッシュボードで管理するパッケージ」と定義します。

## 管理対象のパッケージ - Source

管理対象の状態は、プロバイダから取得した統計ではありません。

ユーザー設定 (Preference) /ユーザーの状態として扱います。

## 管理対象のパッケージ - ルール

パッケージは、`管理対象 = true` または `管理対象 = false` のいずれかです。

## お気に入りのパッケージ

お気に入りのパッケージとは、「ユーザーが自分のダッシュボードで継続的に観測したいパッケージ」と定義します。

## お気に入りのパッケージ - ルール

パッケージは、`お気に入り = true` または `お気に入り = false` のいずれかです。

## 管理対象とお気に入り

管理対象とお気に入りは、独立した属性とします。

下記をすべて許可します。

* `管理対象 = true`、`お気に入り = true`
* `管理対象 = true`、`お気に入り = false`
* `管理対象 = false`、`お気に入り = true`
* `管理対象 = false`、`お気に入り = false`

## 管理対象のパッケージの自動検出

Packagist アカウントから、ユーザーがメンテナンスするパッケージを取得できる場合、その結果を管理対象のパッケージ候補として扱います。実装時期は [`use_cases.md` 優先順位-1](./use_cases.md#優先順位-1) の UC-02を正本とします。認証の設定は UC-16を正本とします。

## 検出結果

プロバイダから取得したパッケージが、`管理対象` であることと、`ダッシュボードに表示する` ことを同一視しません。

発見とプレゼンテーションは、別責務とします。

## お気に入り登録

お気に入り追加時には、対象パッケージがドメイン上有効なパッケージであることを確認します。

## パッケージの重複

同一パッケージ・アイデンティティについて、複数のパッケージ・レコードを作成しません。

`vendor/package` は、ダッシュボード内で一意とします。

## お気に入りの重複

すでにお気に入りであるパッケージを、再度お気に入りにしても、重複の状態を作成しません。操作は、冪等 (べきとう) とします。

## 管理対象の削除

管理対象の状態が解除された場合も、パッケージ自体を自動削除しません。

## お気に入りの削除

お気に入りを解除しても、パッケージ自体を削除する必要はありません。お気に入りは `false` になります。

## パッケージの削除

「ダッシュボードからパッケージを削除する」ことと、「履歴スナップショットを削除する」ことを分離します。

## 履歴データの保全

パッケージをダッシュボードから削除しても、履歴スナップショットを自動削除しないことを基本とします。

## 明示的な履歴削除

履歴スナップショットを削除する場合は、ユーザーによる明示的な削除操作を必要とします。

## プロバイダ

プロバイダは、外部データソースを表します。

初期バージョン:

* Packagist
* GitHub

## プロバイダの独立性

層境界は [`architecture.md`](./architecture.md)、API 実装は各 API 仕様を正本とします。
本仕様は、「ドメイン・モデルが API URL / HTTP メソッド/認証ヘッダーを知らない」ことのみを定めます。

## プロバイダ・データ

「データ転送オブジェクト (DTO) ≠ドメイン」は [`models_spec.md`](./models_spec.md) を正本とします。
本仕様は、「プロバイダ・データを、ドメイン・マッパー経由でドメイン・オブジェクトにしてから扱う」ことのみを定めます。

## カレント・データ

カレント・データとは、「プロバイダから比較的新しい時点で取得された、統計の現在値」とします。

## カレント・データは、スナップショットではない

カレント・データと、履歴スナップショットを同一概念として扱いません。

* カレント・データ: 現在状態
* スナップショット: 過去時点の記録

## スナップショット

スナップショットは、「S2J Package Dashboard が特定時点に取得した統計の記録」とします。不変性、アイデンティティ、重複排除、欠測および0の扱いは、本仕様を正本とします。
永続化は [`storage_spec.md`](./storage_spec.md)、収集の意味は [`statistics_spec.md`](./statistics_spec.md) とします。

## スナップショット不変性

確定済みスナップショットは、原則不変とします。

過去スナップショットを、現在のプロバイダ・データによって上書きしません。

## スナップショット・アイデンティティ

スナップショットは、少なくとも、パッケージ + プロバイダ + `Captured At` によって識別可能とします。永続キーの構成は [`storage_spec.md` スナップショット ID](./storage_spec.md#スナップショット-id) を正本とします。

## 日次スナップショット

初期バージョンでは、同一パッケージ/プロバイダについて、1日1スナップショットを基本とします。

## スナップショットの重複排除

同一日について複数回取得した場合、重複履歴スナップショットを無制限に生成しません。

## スナップショット・タイムスタンプ

スナップショットは、`capturedAt` を必ず持ちます。

## タイムスタンプのセマンティクス

`capturedAt` は、「S2J Package Dashboard がその統計を取得した時点」を表します。プロバイダ側のデータ生成時刻と同一とは限りません。

## UTC

ドメイン上のタイムスタンプは UTC/Instant として扱います。

表示時のタイムゾーン変換は、UI/プレゼンテーション層の責務とします。

## 未来のタイムスタンプ

明らかに不正な、「未来のタイムスタンプ」を、正常な履歴スナップショットとして扱いません。

## 指標

指標は、統計を構成する最小の意味単位とします。

例:

* `downloads`
* `favers`
* `stars`
* `forks`
* `views`
* `clones`

## 指標のアイデンティティ

指標には、`metricName` またはドメイン上で同等のアイデンティティを持たせます。

## 指標値

指標値は、指標の定義に応じた、型を使用します。

計数指標では、原則として、非負の整数とします。

## 負数

下記のような計数は、ドメイン上の有効の状態としません。

* ダウンロード数 = -1
* スター数 = -10
* フォーク数 = -1

## 0値

0は、有効な指標値になり得ます。

`ダウンロード数 = 0` と、`ダウンロード数 = 利用不能` を区別します。

## 可用性

指標には、データの可用性を表現可能とします。

基本状態:

* `Available`
* `Unavailable`
* `NotFetched`
* `NotAuthorized`
* `NotSupported`
* `Stale`

## 利用不能は、0ではない

`利用不能` と値 `0` を明確に区別します。

## NotAuthorized

認証/権限不足の場合、`NotAuthorized` とします。

0に変換しません。

## NotSupported

プロバイダが指標自体を提供していない場合、`NotSupported` とします。

## Stale

取得時点が、一定の鮮度の方針を超えた場合、指標/データを「Stale」として扱えます。

## Stale は、無効ではない

Stale データは、`Invalid` ではありません。ただし、`新鮮` とも扱いません。

## 出典

指標には、出典を明示可能とします。

例:

* Packagist
* GitHub
* 派生

## Raw 指標

プロバイダから直接取得した指標を、Raw 指標とします。

`source = Packagist` または `source = GitHub` 等。

## 派生指標

Raw 指標から計算した指標を、派生指標とします。

例:

* 成長率
* 変更
* 移動平均

## 派生指標ルール

派生指標は、Raw 指標から再計算可能な場合、Raw 指標を「信頼できる情報源 (SoT)」とします。

## 派生指標バージョン

派生指標の計算方法がバージョンによって変わる場合、`calculationVersion` を区別します。

## 統計の比較

統計の比較は、同じ定義の指標同士で行います。

`ダウンロード数 ↔ ダウンロード数` は、比較可能ですが、`ダウンロード数 ↔ スター数` は、直接比較しません。

## 単位

指標には、単位を定義します。

例:

* `count`
* `percentage`
* `ratio`
* `bytes`
* `duration`

## 単位の互換性

異なる単位の指標を、同一指標として扱いません。

## 期間

指標が期間に依存する場合、期間を明示します。

例:

* `daily`
* `monthly`
* `total`

## 期間の互換性

異なる期間を、無条件に比較しません。たとえば、「日次ダウンロード数」と「月次ダウンロード数」は、同一指標ではありません。

## 累積 vs 定期

累積指標と定期指標を、別指標のセマンティクスとして扱います。

累積は、プロバイダが返す生涯カウンタです。日次や月次の単純足し算で、累積を作りません。

GitHub トラフィックの期間合計は、累積ではありません。`count` の内訳だけが単純足し算と一致します。`uniques` は単純足し算しません。レスポンスの形は [`api-github.md`](./api-github.md) を正本とします。

## ダウンロード数

Packagist ダウンロード数については、プロバイダが定義する期間のセマンティクスを尊重します。

S2J 側で 累積/月次/日次等を勝手に同一指標として扱いません。

## Faver 数

Faver 数は Packagist 由来の指標として扱います。

プロバイダから取得できない場合は、Unavailable/NotSupported 等の適切な状態を使用します。

## GitHub スター数

GitHub スター数は、GitHub リポジトリの状態を表す指標とします。

## GitHub フォーク数

GitHub フォーク数は、GitHub リポジトリの状態を表す指標とします。

## GitHub トラフィック

GitHub トラフィックは、GitHub 側の保持期間の制限を持つデータとして扱います。

S2J スナップショットによって長期履歴を形成できます。

## トラフィックのスナップショット・ルール

GitHub トラフィックを取得した場合、スナップショット方針に従って、履歴データを保存可能とします。

## 履歴の真実

履歴スナップショットは、「S2J Package Dashboard がその時点で取得した データ」を記録します。

プロバイダの完全な履歴データベースを表すものではありません。

## 履歴の推測なし

取得できなかった過去データを、現在データから推測して生成しません。

## 欠落スナップショット

ある日のスナップショットを取得できなかった場合、下記のようなギャップを許容します。

* `2026-08-20`
* `2026-08-21`
* `2026-08-23`

## 欠落データは、0ではない

スナップショットが存在しないことを、`指標 = 0` として扱いません。

## スナップショット・ギャップ

欠測を実値として補間しません。チャート上のギャップ表現は [`statistics_spec.md`](./statistics_spec.md) を正本とします。

## 補間

ドメイン上で履歴データを自動補間しません。

## API 失敗

API 失敗は、ドメイン・データ自体の値ではありません。0との区別は [利用不能は、0ではない](#利用不能は0ではない) を正本とします。

## プロバイダの部分失敗

Packagist 取得成功、GitHub 取得失敗のような状態を許容します。

* Packagist: 利用可能
* GitHub: 利用不能

## 部分データ

部分データを理由に、成功したプロバイダのデータまで破棄しません。

## リフレッシュ

リフレッシュは、「カレント・データを再取得する操作」とします。

リフレッシュ自体は、履歴スナップショット生成を必ず意味しません。

## スナップショット・コレクション

スナップショット・コレクションは、リフレッシュとは独立した方針として扱います。

## 冪等 (べきとう) 性

下記の操作は、可能な限り、冪等 (べきとう) とします。

* お気に入り追加
* お気に入り削除
* 管理対象に設定
* 管理対象から解除
* リフレッシュ

## お気に入りコマンド

`favorite(package)` は、すでに「お気に入り」の場合でも、ドメイン状態を壊しません。

## お気に入りの解除コマンド

`unfavorite(package)` は、「お気に入り」でない場合でも、正常に完了可能とします。

## 管理対象コマンド

`markMaintained(package)` は、すでに「管理対象」の場合でも、重複の状態を作成しません。

## 管理対象の解除コマンド

`unmarkMaintained(package)` は、すでに「管理対象」でない場合でも、正常に完了可能とします。

## パッケージ登録

パッケージをダッシュボードに登録する場合、パッケージ・アイデンティティの独自性を保証します。

## パッケージ発見

プロバイダ発見の結果は、ドメイン・パッケージを自動的に重複作成しません。

## パッケージ・マージ

同一パッケージ・アイデンティティが複数ソースから取得された場合、ドメイン上では同一パッケージとして扱います。

## プロバイダ・メタデータ

プロバイダ固有のメタデータは、コア・パッケージ・アイデンティティとは分離します。

## リポジトリの関連付け

パッケージとリポジトリの関連付けは、プロバイダ・データによって更新可能とします。

ただし、パッケージ・アイデンティティ自体を変更してはなりません。

## リポジトリの状態

リポジトリには、必要に応じて、下記の状態を持たせます。

* アクティブ
* アーカイブ
* 利用不能
* 不明

## アーカイブ・リポジトリ

アーカイブ・リポジトリは、統計データを必ずしも削除しません。

## リポジトリ利用不能

リポジトリが取得不能になっても、過去スナップショットを削除しません。

## パッケージの可用性

パッケージについても、下記の状態を、必要に応じて、表現可能とします。

* 利用可能
* 利用不能
* 不明

## プロバイダ失敗とパッケージの状態

一時的な API 失敗だけで、`パッケージ = Deleted` 等の不可逆状態を変更しません。

## 削除の確認

プロバイダからパッケージが取得できなくなった場合、それだけを理由にローカルのパッケージを削除しません。

## 外部の状態 vs ローカルの状態

プロバイダ状態とユーザー設定 (Preference) を明確に分離します。たとえば、「GitHub リポジトリ アーカイブ」と「ユーザーお気に入り」は、独立した状態です。

## アカウント

Packagist アカウント/GitHub アカウントは、ドメイン・パッケージ自体とは異なる概念とします。

## クレデンシャル (資格情報)

クレデンシャルをドメインに載せないことは [`authentication_spec.md`](./authentication_spec.md) / [`security_spec.md`](./security_spec.md) を正本とします。
本仕様は、「パスワード/Token/Secret をドメイン・エンティティの属性としない」ことのみを定めます。

## アカウント・アイデンティティ

アカウント・アイデンティティは、認証層からドメインに必要最小限の情報だけを渡します。

## 認可

認可の状態は、ドメイン・データの指標値に変換しません。

## 権限

権限不足によって取得できない指標は、`NotAuthorized` として表現可能とします。

## ドメイン・エラー

ドメイン・エラーは、プラットフォーム・エラー/HTTP エラーと分離します。

例:

* `InvalidPackageIdentifier`
* `DuplicatePackage`
* `InvalidMetric`
* `InvalidSnapshot`
* `InvalidStateTransition`

## API エラーのマッピング

境界の分類は [`architecture.md`](./architecture.md)、`ApplicationError` は [`models_spec.md`](./models_spec.md) を正本とします。
本仕様は、「HTTP ステータス・コード自体をドメイン・ルールにしない」ことのみを定めます。

## ドメイン・サービス

複数ドメイン・オブジェクトを横断し、単一エンティティに「自然に所属させられない」ドメイン操作には、ドメイン・サービスを利用可能とします。

## ドメイン・サービスの例

例:

* StatisticsComparisonService
* TrendCalculationService
* PackageIdentityResolver

## ドメイン・サービス制限

ドメイン・サービスは、UI/データベース/HTTP クライアントを直接操作しません。

## リポジトリ

リポジトリは、ドメイン・オブジェクトのコレクションとして扱います。

ドメイン層からは、インターフェースのみを参照します。

## リポジトリの独立性

リポジトリ・インターフェースは、下記を知りません。

* SwiftData
* SQLite
* SQLDelight
* Room
* CoreData

## 集約

集約は、ドメイン不変性を守る必要がある範囲で、定義します。

リレーションシップがあるという理由だけで、同一集約にまとめません。

## パッケージ集約

初期バージョンでは、パッケージを主要集約ルート候補とします。

パッケージが、下記の整合性を保持します。

* パッケージ・アイデンティティ
* 管理対象の状態
* お気に入りの状態

## スナップショット集約

統計スナップショットは、下記の理由により、パッケージとは別の集約として扱うことを許容します。

* 履歴データ が大量になる
* Append-oriented である
* パッケージの状態と独立して保存できる
* スナップショットの不変性を保ちやすい

## スナップショット境界

スナップショット内部では、指標の集合として整合性を保証します。

## スナップショットのアトミック性

永続のアトミック・コミットは [`storage_spec.md`](./storage_spec.md) を正本とします。
本仕様は、「スナップショット・メタデータと指標が、一貫した状態で確定する」ことのみを定めます。

## 集約横断型の一貫性

パッケージとスナップショットの間に存在するすべての関係を、単一トランザクションで常に同期させることを、ドメイン・ルールとはしません。

## 最終的な一貫性

プロバイダ・メタデータ等の外部情報については、最終的な一貫性を許容します。

## グローバル・トランザクションなし

Packagist 取得、GitHub 取得、パッケージ更新、スナップショット確定を、単一ドメイン・トランザクションとして必須化しません。

## 信頼できる情報源 (SoT)

パッケージ・アイデンティティは ドメイン・パッケージ、ユーザー設定 (Preference) は ローカル・ユーザーの状態、現在の統計はプロバイダ、履歴 統計は S2J スナップショットを「信頼できる情報源 (SoT)」とします。
詳細は、直後の各節を正本とします。

## 信頼できる情報源 (SoT) としてのプロバイダ

現在 Packagist/GitHub 統計については、各プロバイダを「信頼できる情報源 (SoT)」とします。

## 履歴レコードとしてのスナップショット

履歴スナップショットは、プロバイダの現在の状態を上書きするものではありません。

## ローカルの真実としてのユーザー設定 (Preference)

お気に入り/管理対象は、プロバイダのデータ ではなく、ユーザー設定として扱います。

## 統計の鮮度

鮮度は、指標の有効性とは別概念とします。

* 新鮮
* Stale 

は、

* 有効
* 無効

とは異なります。

## 計算ルール

成長率等の派生指標は、定義されたフォーミュラに従います。

## 成長

基本: `成長率 = (現在値 - 前回値) / 前回値 × 100`

ただし、前回値 = 0の場合は、通常の割合計算を適用しません。

## 0除算

`前回値 = 0` の場合、「成長率」を単純に「無限」として扱いません。

`Undefined`/`NotAvailable` 等のドメイン状態を利用します。

## 指標比較の期間

比較対象の期間が存在しない場合、成長指標を生成しません。

## 傾向

傾向は、下記のドメイン状態として表現可能とします。

* Increasing
* Decreasing
* Stable
* InsufficientData

## 傾向の最小データ

傾向判定には、最低限必要なスナップショット数を定義します。

初期バージョンでは、少なくとも、2つの比較可能なデータポイントを必要とします。

## データの推測なし

スナップショットが1つしか存在しない場合、傾向を推測しません。

## 安定版

安定版判定には、明示的な閾値を使用します。

閾値未定義の場合、安定版と断定しません。

## ヘルス

パッケージ・ヘルス等の複合インジケータを導入する場合、判定ルールを明示します。指標の意味は [`statistics_spec.md`](./statistics_spec.md) を正本とします。
本仕様は、「ダウンロード数傾向 / リリース履歴 / Issue の状態等を合成する場合に、ルールを持つ」ことのみを定めます。

## ヘルスは、派生

ヘルスはプロバイダから直接取得した指標ではなく、S2J が計算する派生ドメイン概念とします。

## ヘルス閾値

閾値は、UI にハードコーディングしません。

ドメインのシステム設定 (Configuration) として管理します。

## システム設定 (Configuration)

下記は、ドメイン・ルールに必要な、システム設定として扱います。

* スナップショット間隔
* 傾向閾値
* ヘルス閾値
* 鮮度の方針

## システム設定 (Configuration) 不変性

Runtime システム設定を変更した場合でも、過去スナップショット自体を変更しません。

## 履歴計算

過去統計の再計算が必要な場合、計算バージョンを明示します。

## データの来歴

派生データは、可能な限り、出典指標とプロバイダを追跡可能とします。

## ドメイン・クロック

現在時刻を、直接グローバル API から取得しません。

必要に応じて、ドメイン・クロックを抽象化します。

`Clock.now()` 等の形を想定します。

## 決定論的テスト

ドメイン・ルールは、固定クロック/固定タイムスタンプを利用して、決定論的テスト可能とします。

## ロケールの独立性

ドメイン・ルールは、ユーザーのロケールに依存しません。

たとえば、`1,234` という表示形式は UI の責務であり、ドメイン値は数値として保持します。

## タイムゾーンの独立性

ドメイン・ルールは、表示タイムゾーンに依存しません。

## 通貨

統計に通貨が必要になった場合も、表示フォーマットとドメイン値を分離します。

## 文字列のフォーマット

パッケージ名/指標値等の表示用のフォーマットは、プレゼンテーション層の責務とします。

## ドメイン・モデルの不変性

値オブジェクト/スナップショット等、変更する必要のないドメイン・オブジェクトは、可能な限り、不変とします。

## 値オブジェクト

下記は、値オブジェクト候補とします。

* `PackageID`
* `RepositoryID`
* `MetricName`
* `MetricUnit`
* `MetricPeriod`
* `ProviderID`

## エンティティ

アイデンティティとライフサイクルを持つものは、エンティティ候補とします。

* パッケージ
* リポジトリ

## 集約ルート

集約ルートは、外部から直接、内部状態を変更できないようにします。

## 不正状態の防止

可能な限り、「不正状態を生成できないモデル」を目指します。

たとえば、`ダウンロード数 = -1` のような状態を、ドメイン・コンストラクタ/Factory で拒否します。

## Factory

複合ドメイン・オブジェクト生成には、Factory を利用可能とします。

## 検証タイミング

ドメイン検証は、ドメイン・オブジェクト生成時および状態変更時に行います。

## データ転送オブジェクト (DTO) 検証

「DTO ≠ドメイン」は [`models_spec.md`](./models_spec.md) を正本とします。
本仕様は、「API スキーマ検証とドメイン検証を分離する」ことのみを定めます。

## 外部データの信頼

プロバイダから取得したデータであっても、ドメイン検証を省略しません。

## 不明指標

未知指標を受信した場合、コア・ドメインを破壊しません。

下記のいずれかを採用可能とします。

* 無視
* 拡張データとして保存
* 非対応とマーク

## 前方互換性

プロバイダ API に新指標が追加されても、既存ドメイン・モデルが無効になりません。

## 後方互換性

ドメイン ・スキーマ変更時には、既存スナップショットを、可能な限り、解釈可能とします。

## ドメイン・バージョン

ドメイン・モデル変更時には、必要に応じて、ドメイン・スキーマ・バージョンを更新します。

## ドメイン・イベント

将来的に必要となった場合、ドメイン・イベントを利用可能とします。

候補:

* PackageAdded
* PackageFavorited
* PackageUnfavorited
* PackageMaintained
* PackageUnmaintained
* SnapshotCaptured
* SnapshotDeleted

## イベントのセマンティクス

ドメイン・イベントは、「ドメイン上で意味のある状態変化が発生した」ことを表します。

UI イベントと同一視しません。

## イベント不変性

発生済みドメイン・イベントは、不変とします。

## イベント・ペイロード

イベント・ペイロードには、必要最小限のドメイン情報のみを含めます。

クレデンシャル (資格情報) を含めません。

## 外部連携

将来的に、ドメイン・イベントを、外部同期/アナリティクス等に利用可能とします。

ただし、初期バージョンでは、外部イベント・バスを必須としません。

## API の独立性

ドメイン・ルールをプロバイダ API の現在仕様に、過度に固定しません。

## Packagist の独立性

Packagist 固有の仕様は、Packagist アダプタ/プロバイダ・モデルに閉じ込めます。

## GitHub の独立性

GitHub 固有の仕様は、GitHub アダプタ/プロバイダ・モデルに閉じ込めます。

## 複数プロバイダ

将来的に、プロバイダを追加しても、コア・ドメイン・ルールを大きく変更しません。

## プロバイダ・ケイパビリティ

プロバイダごとの指標対応差は、ケイパビリティとして表現可能とします。

## ケイパビリティ例

扱う指標は [`statistics_spec.md` Packagist 指標](./statistics_spec.md#packagist-指標) / [`statistics_spec.md` GitHub 指標](./statistics_spec.md#github-指標) を正本とします。
本仕様は、「プロバイダ差をケイパビリティとして表現する」ことのみを定めます。

## ケイパビリティ・ルール

指標がプロバイダ・ケイパビリティに存在しない場合、`NotSupported` として扱います。

## プロバイダ認証

認証の有無は、指標の意味を変更しません。

## 認可依存の指標

認可が必要な指標について、未認証状態を0に変換しません。

## 公開 vs 認可済みデータ

公開データと認可済みデータを、ドメイン上で、必要に応じて、区別します。

## セキュリティ境界

Token をドメインに載せないことは [`security_spec.md`](./security_spec.md) / [`authentication_spec.md`](./authentication_spec.md) を正本とします。
本仕様は、「ドメイン・モデルにパスワード/ API Token/Secret を渡さない」ことのみを定めます。

## クレデンシャル (資格情報) 永続化なし

ドメイン・オブジェクトは、クレデンシャル (資格情報) を永続化しません。

## オフライン・ルール

オフラインであること自体は、ドメイン・オブジェクトの無効の状態ではありません。

## オフライン・カレント・データ

オフライン時には、最終確認データを利用可能とします。

そのデータが Stale である場合は、「Stale」の状態を保持します。

## オフライン・スナップショット

プロバイダ・データを取得していないため、オフライン時に新しいスナップショットを作成してはなりません。

## スナップショット真正性

スナップショットは、実際に取得したプロバイダ・データにもとづく場合のみ生成します。

## 合成スナップショットなし

オフライン時に、前回値から新規スナップショットを合成して、通常の履歴スナップショットとして保存しません。

## タイムスタンプのリフレッシュ

リフレッシュ開始時刻とスナップショット収録時刻を混同しません。

## フェッチに成功

スナップショットを作成するには、対象指標の取得が成功している必要があります。

部分プロバイダ・データについては、部分スナップショットルールを適用します。

## 部分スナップショット

一部指標のみ取得成功した場合、指標単位の可用性を保持可能とします。

完全/部分の表現は [スナップショットの完全性](#スナップショットの完全性) を正本とします。
欠落指標を0に変換しないことは [利用不能は、0ではない](#利用不能は0ではない) を正本とします。
本節は、「一部指標が取得できなかった場合を、部分とする」ことのみを定めます。

## スナップショットの完全性

スナップショットには、必要に応じて、下記を表現可能とします。

* 完全
* 部分

## 完全なスナップショット

プロバイダから必要な対象指標がすべて取得できた場合を、「完全」とします。

## スナップショット比較

スナップショット同士を比較する場合、比較可能な指標だけを比較します。

## 欠落指標の比較

片方にしか存在しない指標について、「成長」を計算しません。

## 履歴の削除

履歴スナップショット削除は、ドメイン上の不可逆操作として扱います。

## スナップショット復元

バックアップ/インポートから、スナップショットを復元する場合も、ドメイン検証します。

## インポートされたデータ

外部インポートデータを、無条件に「信頼済み」ドメイン状態として扱いません。

## インポート検証

インポートの処理順は [`storage_spec.md` インポート](./storage_spec.md#インポート) を正本とします。
本仕様は、「スキーマ検証のあとに、ドメイン検証と重複解決を行い、無条件に信頼済みとしない」ことのみを定めます。

## 重複スナップショットのインポート

既存スナップショットとアイデンティティが一致する場合、重複スナップショットを作成しません。

## コンフリクト解決

インポート/同期でコンフリクトが発生した場合、ドメイン・ルールとして勝手に「Last Writer Wins」を適用しません。

コンフリクトの方針を別途定義します。

## デバイス横断型同期

デバイス横断型同期は、初期バージョンでは、ドメイン要件としません。

将来的に導入する場合、お気に入り/管理対象/スナップショット等のコンフリクト・ルールを別途定義します。

## プラットフォームの独立性

ドメイン・ルールは、下記のいずれでも、同一のセマンティクスを持ちます。

* iOS
* iPadOS
* Android

## Kotlin Multiplatform (KMP) の互換性

KMP の HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とします。
本仕様は、「ドメイン層が、共有コードに移行可能な構造である」ことのみを定めます。

## Kotlin Multiplatform (KMP) 移行の境界

共有対象と優先順位は [`architecture.md`](./architecture.md) を正本とします。
本仕様は、「ドメイン・ルールを、共有ロジック側に置く」ことのみを定めます。

## Swift 実装

初期実装の言語は [`architecture.md`](./architecture.md) を正本とします。
本仕様は、「ドメイン・ルールが SwiftUI/SwiftData/iOS 固有 API に依存しない」ことのみを定めます。

## Kotlin 移行

共有に移す順序は [`architecture.md`](./architecture.md) を正本とします。
本仕様は、「不変を移植対象の中心とする」ことのみを定めます。

## UI の独立性

ドメイン・ルールは、SwiftUI/Compose のレンダリング・ロジックに直接埋め込みません。

## 永続化の独立性

ドメイン・ルールは、SwiftData/SQLite/SQLDelight/Room 等の永続化技術に依存しません。

## API の独立性

ドメイン・ルールは、HTTP クライアントや API レスポンス・データ転送オブジェクト (DTO) に依存しません。

## ドメイン・テスト

検証の種類は [`testing_spec.md`](./testing_spec.md) を正本とします。
本仕様は、「ドメイン・ルールを UI テストではなく、ユニットテストで検証する」ことのみを定めます。

## 不変性テスト

検証項目は [`testing_spec.md`](./testing_spec.md) を正本とします。
本仕様は、「パッケージ ID/指標/スナップショット/お気に入り/管理対象の不変条件をテスト可能である」ことのみを定めます。

## 統計テスト

指標の意味は [`statistics_spec.md`](./statistics_spec.md)、検証の種類は [`testing_spec.md`](./testing_spec.md) を正本とします。
本仕様は、「成長/傾向/0/欠落/部分/Stale のドメイン判定をテスト可能である」ことのみを定めます。

## プロパティ・ベースのテスト

将来的に、可能なドメイン・ルールについて、プロパティ・ベースのテストを導入可能とします。

## 決定論

同一インプットに対して、同一ドメイン・ルールは、同一結果を返します。

現在時刻等の外部の状態は、抽象化します。

## ドメイン・ルールの優先順位

ルールが競合した場合、下記を優先します。

1. ドメインの不変性
2. データの整合性
3. ユーザー・インテント
4. プロバイダ・データ
5. プレゼンテーションの利便性

## プロバイダ・データは、ユーザーの状態をオーバーライドしない

プロバイダから取得したデータによって、お気に入り/管理対象を、勝手に変更しません。

## UI は、ドメイン・ルールをオーバーライドしない

UI からの操作であっても、ドメイン・ルールを無視した状態変更を許可しません。

## ストレージは、ドメイン・ルールを定義しない

データベース・スキーマによって、ドメインのセマンティクスを決定しません。

## API は、ドメイン・モデルを定義しない

プロバイダ API レスポンスを、そのままドメイン・モデルとして扱いません。

## 信頼できるセマンティック情報源としてのドメイン

アプリケーション内部の意味については、「ドメイン・モデル + ドメイン・ルール」を意味的な「信頼できる情報源 (SoT)」とします。

## ドメイン・ルール変更

ドメイン・ルールを変更する場合、下記を記録します。

* 変更理由
* 旧ルール
* 新ルール
* 影響するモデル
* 影響する統計
* 移行要件
* テスト

## ルールの後方互換性

過去スナップショットの意味を変えてしまうドメイン・ルール変更には、注意します。

## 履歴のセマンティクス

過去スナップショットを再解釈する場合、旧計算バージョン/スキーマ・バージョンを参照可能とします。

## ルールのバージョン管理

将来的に、ルール・バージョンが必要となった場合、`domainRuleVersion` を利用可能とします。

## セマンティックのサイレント変更なし

ドメイン・ルール変更によって履歴データの意味が変わる場合、サイレント移行しません。

## ドメイン・ドキュメント

ドメイン・ルール変更時には、関連する専門仕様を確認します。ファイル名簿は [`specs.md`](./specs.md) を正本とします。
