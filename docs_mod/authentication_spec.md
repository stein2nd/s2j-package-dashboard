# S2J Package Dashboard - 認証/クレデンシャル (資格情報) 仕様

## 概要

本ドキュメントは、S2J Package Dashboard の初期設計における、認証/クレデンシャル (資格情報) 管理を定義します。

Packagist/GitHub の認証の仕様変更、プラットフォーム・セキュリティ API の変更、Kotlin Multiplatform (KMP) 移行、セキュリティ・レビュー等に応じて更新します。

外部プロバイダ固有の認証仕様については、Packagist および GitHub の公式ドキュメントを正本とします。

認証方式を追加する場合は、下記への影響を確認します。

* 最小権限の原則
* クレデンシャル (資格情報) ストレージ
* クレデンシャル (資格情報) ライフサイクル
* 無効化
* バックアップ/移行
* ロギング
* プラットフォーム境界

## 目的

本ドキュメントでは、認証およびクレデンシャル (資格情報) の取り扱いを定義します。Packagist/GitHub 認証、Token、ストレージ、ライフサイクル、認証状態、接続解除、移行、バックアップ、ロギング、エラー処理を対象とします。

外部プロバイダ固有の認証仕様については、Packagist および GitHub の公式ドキュメントを正本とします。

## 非目的

本仕様は、外部サービス固有の API エンドポイント詳細を定義しません。パスワードを保存する認証を目的としません。

## 責務

認証方針、クレデンシャルの境界、最小権限、ライフサイクル、プラットフォーム Secure ストレージへの委譲を正本とします。

## 非責務

Packagist API は [`api-packagist.md`](./api-packagist.md)、GitHub API は [`api-github.md`](./api-github.md)、横断セキュリティは [`security_spec.md`](./security_spec.md)、Keychain/Keystore 実装差分は [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md)、横断 UI 振る舞いは [`ui.md`](./ui.md)、Settings 画面構成は [`screen_spec.md`](./screen_spec.md)、共有対象は [`architecture.md`](./architecture.md)、KMP の HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とします。

## 基本原則

S2J Package Dashboard では、下記を認証の基本原則とします。

1. 認証を必要としない操作では、認証を要求しない
2. パスワードを保存しない
3. 権限は、「最小権限の原則」とする
4. クレデンシャル (資格情報) は、必要最小限とする
5. クレデンシャルを、アプリケーション・データから分離する
6. クレデンシャルを、OS 提供の Secure ストレージに保存する
7. クレデンシャルを、ログ/アナリティクスに出力しない
8. クレデンシャルを、ソースコードに埋め込まない
9. クレデンシャル失効時に、安全に回復できること
10. サービスごとの認証境界を維持する

基本構造: 公開データは匿名アクセス、保護対象データだけ認証し、権限は最小限、クレデンシャルは Secure ストレージに置く。

## 認証境界

認証は、外部サービスごとに独立させます。

* Packagist クレデンシャル (資格情報) を GitHub 認証に使用しない
* GitHub クレデンシャル (資格情報) を Packagist 認証に使用しない

## 認証 vs アプリケーション・アカウント

S2J Package Dashboard 自体のアカウントと、Packagist/GitHub アカウントを区別します。

初期バージョンでは、「S2J Package Dashboard アカウント」を必須としません。ユーザーは、S2J Package Dashboard 専用アカウントを作成せず、公開情報を利用できることを基本とします。したがって、アプリケーション・ログイン、Packagist 認証、GitHub 認証は互いに異なる概念とします。

## 「匿名」ファーストの原則

認証を必要としない API については、匿名アクセスを優先します。認証済みであることを理由に、すべてのリクエストにクレデンシャル (資格情報) を付与しません。必要なリクエストだけ認証済みとします。

## クレデンシャル (資格情報) の分類

下記にクレデンシャル (資格情報) を分類します。それぞれのセキュリティ要件を区別します。

* パスワード
* API Token
* アクセス Token
* リフレッシュ Token
* クライアント識別子
* クライアント Secret

## パスワードの方針

S2J Package Dashboard では、Packagist および GitHub のアカウント・パスワードを保存しません。パスワードによる直接 API 認証を実装しません。認証プロバイダが提供する「Token/認可フロー」を利用します。

## クレデンシャル (資格情報) の機密性

クレデンシャル (資格情報) は、下記のように分類します。

| クレデンシャル (資格情報) | Secret | 永続ストレージ |
| --- | --- | --- |
| ユーザー名 | No/低 | 許可 |
| アカウント ID | No/低 | 許可 |
| API Token | Yes | Secure ストレージのみ |
| アクセス Token | Yes | Secure ストレージのみ |
| リフレッシュ Token | Yes | Secure ストレージのみ |
| クライアント ID | Usually No | 許可 |
| クライアント Secret | Yes | ネイティブ・アプリケーションに埋め込まない |
| パスワード | Yes | 保存しない |

## Packagist 認証

Packagist API については、可能な限り匿名アクセスを利用します。公開 API は匿名、認証済み API は API Token とします。

### Packagist クレデンシャル (資格情報)

Packagist 認証が必要な場合は、Packagist API Token を利用します。パスワードは、利用しません。

クレデンシャル (資格情報): `username` / `token` / `tokenType`。`tokenType` は `SAFE` または `MAIN` とします。

### Packagist `SAFE` Token

可能な限り `SAFE` Token を使用します。`MAIN` Token を必要とする機能は、初期バージョンでは原則として実装対象外とします。

### Packagist `MAIN` Token

`MAIN` Token は、高権限クレデンシャル (資格情報) として扱います。将来、`MAIN` Token を必要とする機能を追加する場合は、セキュリティ・レビューを必須とします。

初期バージョンでは、`MAIN` Token は未対応とします。

### Packagist Bearer 認証

認証済みリクエストでは、「Bearer 認証」を優先します。

概念:

`Authorization: Bearer <credential>`

クレデンシャル (資格情報) を、URL クエリー・パラメータに含めません。URL への Secret 禁止とログ露出は [`security_spec.md`](./security_spec.md) を正本とします。実際のヘッダー・フォーマットは、Packagist API 仕様を正本とします。

## GitHub 認証

GitHub API についても、公開リポジトリ情報は、可能な限り匿名アクセスを利用します。保護対象データのみ認証済みとします。

### GitHub 認証ユースケース

下記は、認証を必要とする、代表的なユースケースです。認証なしでも利用できる機能については、認証を必須としません。

* リポジトリ・トラフィック
* 非公開リポジトリ
* ユーザー固有データ
* API リミットの引き上げ

### GitHub 認証方法

下記は、GitHub 認証候補です。一般ユーザー向けアプリケーション認証では、GitHub アプリケーションを第一候補とします。個人用アクセス Token は、開発/個人利用等の限定用途として扱います。候補は GitHub アプリケーション / OAuth / 個人用アクセス Token とします。

### GitHub アプリケーション

一般ユーザー向け認証を実装する場合、下記の理由から、GitHub アプリケーションを推奨方式とします。

* きめ細かな権限
* リポジトリ選択
* 無効化
* 短期間有効な Token
* GitHub 側での権限管理

概念: S2J Package Dashboard → GitHub 認可 → ユーザー承認 → GitHub アプリケーション → アクセス Token。

## OAuth/PKCE

ネイティブ・アプリケーションでは、クライアント Secret を安全に保持できないことを前提とします。そのため、OAuth 系認可フローを採用する場合は、PKCE を利用可能な方式を優先します。クライアント Secret をアプリケーション・バンドルに埋め込みません。流れは、認可リクエスト → PKCE → ブラウザー/認証セッション → GitHub → 認可コード → Token とします。

## 個人用アクセス Token

個人用アクセス Token をサポートする場合、きめ細かな個人用アクセス Token を優先します。Classic 個人用アクセス Token は、互換性等の明確な理由がある場合のみ利用します。ユーザーに Token 作成を要求する方式は、一般ユーザー向けの主認証フローとしません。

## 最小権限の原則

クレデンシャル (資格情報) には、必要最小限の権限のみ要求します。「将来使う可能性がある」という理由だけで、権限を要求しません。求められる機能 → 求められる API → 求められる権限 → クレデンシャル、の順で決めます。

## リポジトリ選択

GitHub アプリケーション等でリポジトリ単位のアクセス制御が可能な場合、ユーザーが必要なリポジトリだけ選択できることを優先します。「すべてのリポジトリ」へのアクセスを、初期値として要求しません。

## 認証ケイパビリティ

認証状態と、実際に利用可能な「ケイパビリティ」を区別します。たとえば、GitHub 認証済みでも、リポジトリ・トラフィック権限がなければトラフィックは、取得できません。

「認証済み ≠ すべての機能が利用可能」

## ケイパビリティ・モデル

概念的に下記を管理します。UI は、単純なログイン中/ログアウト中だけでなく、必要に応じて「ケイパビリティ」を参照します。フィールド: `publicRead` / `repositoryRead` / `trafficRead` / `privateRepositoryRead` / `accountRead`。

## 認証状態

下記のように、認証状態を定義します。

* `Unknown`
* `Unauthenticated`
* `Authenticating`
* `Authenticated`
* `Expired`
* `Revoked`
* `InsufficientPermission`
* `Error`

## サービス認証状態

認証状態は、下記のように、サービスごとに保持します。

* Packagist: 認証済み
* GitHub: 未認証

この状態を正常な状態として扱います。すべてのサービスへの認証を要求しません。

## クレデンシャル (資格情報) ストレージ

クレデンシャル (資格情報) は、通常のアプリケーション・ストレージに保存しません。クレデンシャル (資格情報) 専用 Secure ストレージを使用します。

下記は、クレデンシャル保存が禁止されているストレージ例です。

* `UserDefaults`
* `JSON`
* `plist`
* `SQLite`
* `SwiftData`
* `Room`
* プレーンファイル

## Apple プラットフォーム・ストレージ

iOS/iPadOS は Keychain を使用します。実装差分 (Item、Accessibility、生体) は [`ios_spec.md`](./ios_spec.md) を正本とします。

## Android ストレージ

Android は Keystore 系の Secure ストレージを使用します。実装差分は [`android_spec.md`](./android_spec.md) を正本とします。

## Kotlin Multiplatform (KMP) クレデンシャル (資格情報) 境界

KMP に移行した場合でも、クレデンシャル (資格情報) ストレージそのものを共通コードに実装しません。モジュール配置は [`kmp_spec.md`](./kmp_spec.md)、Keychain / Keystore の実装は [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md) を正本とします。ドメイン/アプリケーション層は、`CredentialStore` インターフェースのみを認識します。

### クレデンシャル (資格情報) データの分離

クレデンシャル (資格情報) と通常のアカウント・メタデータを分離します。

例: アカウントの `provider` / `username` / `displayName` / `accountID` はアプリケーション・ストレージに保存可能とします。一方、`accessToken` / `refreshToken` / `apiToken` は Secure ストレージのみに保存します。

### クレデンシャル (資格情報) レファレンス

アプリケーション・データから、クレデンシャル (資格情報) を直接保持しません。たとえば、データベース・レコードに Token 文字列を保存しません。アカウントは `CredentialReference` のみを持ち、実体は Secure クレデンシャル・ストアに置きます。

### クレデンシャル (資格情報) 有効期限

クレデンシャル (資格情報) について、下記を管理します。

* `issuedAt`
* `expiresAt`
* `refreshable`
* `revoked`

プロバイダから取得可能な情報のみ、保持します。

有効期限を持たない Token について、架空の有効期限を生成しません。

## アクセス Token 有効期限

アクセス Token に 有効期限が存在する場合、有効 / まもなく期限切れ / 期限切れ を区別します。有効期限が切れた Token を、API に無条件に送信し続けません。

## リフレッシュ Token

リフレッシュ Token を利用する認証方式では、アクセス Token とは別クレデンシャル (資格情報) として扱います。リフレッシュ Token をアプリケーション・ログに出力しません。ログ禁止は [`security_spec.md`](./security_spec.md) を正本とします。本節は、リフレッシュ Token を Secure ストレージに置くことだけを定めます。

## Token 更新

Token 更新が利用可能な場合、アクセス Token が期限切れ/期限間近ならリフレッシュ Token で更新し、新アクセス Token を得ます。成功時は、旧クレデンシャル (資格情報) を安全に置換します。

## クレデンシャル (資格情報) ローテーション

プロバイダまたはユーザーによって Token がローテーションされた場合、新クレデンシャル (資格情報) に安全に置換できること。

新 Token の保存に失敗した場合、不用意に旧 Token を削除しません。順序は、新 Token 検証済み → 新 Token を保存 → 旧 Token を削除、とします。

## クレデンシャル (資格情報) 検証

クレデンシャル (資格情報) 入力時には、可能であれば保存前または保存直後に検証します。妥当ならストア、妥当でなければ拒否します。ただしオフライン時には、プロバイダ仕様に応じた適切に処理されます。

## 認証不具合

認証不具合を下記に分類します。これらを単一の、ログイン失敗として扱いません。

* `InvalidCredential`
* `ExpiredCredential`
* `RevokedCredential`
* `InsufficientPermission`
* `NetworkFailure`
* `ProviderUnavailable`
* `UserCancelled`
* `Unknown`

## `401` vs `403`

HTTP 認証エラーについて、`401` と `403` を同一視しません。プロバイダ固有の意味は、各 API 仕様を正本とします。

下記は、概念です。

* `401` → クレデンシャル (資格情報) 無効/欠落
* `403` → 認証済みだが、操作が許可されていない

## 再認証

クレデンシャル (資格情報) が期限切れ/失効となった場合、ユーザーに再認証を要求します。無限リトライを行いません。API の認証不具合の後にクレデンシャル状態を更新し、再認証が必要であることを示します。

## 接続解除

ユーザーは、各サービスとの接続を個別に解除できます。

例:

* Packagist を接続解除
* GitHub を接続解除

接続解除時には、下記を実施します。

1. ローカル・クレデンシャル (資格情報) を削除
2. 認証状態を更新
3. クレデンシャル (資格情報) キャッシュを削除
4. 認証済みデータの扱いを決定

## ログアウト vs 接続解除

S2J Package Dashboard では、サービスとの関係について、ログアウトより接続解除という概念を優先します。ユーザーは S2J Package Dashboard そのものからログアウトするのではなく、外部サービスとの接続を解除するためです。

## リモート無効化

プロバイダが Token 無効化 API を提供し、現在の認証方式で利用可能な場合は、接続解除時にリモート無効化を検討します。リモート無効化に失敗しても、ローカル・クレデンシャル (資格情報) 削除を妨げません。順序は、接続解除 → リモート無効化 → ローカル削除、とします。

## 認証 UI

UI に出してよい状態は `## UI 状態` を正本とする。Settings の画面構成は [`screen_spec.md`](./screen_spec.md) を正本とする。本節は、設定等にサービス単位の接続状態 (アカウント名、未接続) を出すことだけを定める。

## 権限 UI

追加権限が必要になった場合、必要な理由をユーザーに説明します。

例:

`リポジトリ・トラフィックを表示するには、選択したリポジトリへの追加アクセスが必要です。`

権限要求を、機能利用前に無差別に行いません。

## Progressive 認可

権限は、必要になった時点で要求します。これを漸進的認可の基本方針とします。公開 Dashboard は認証なし、トラフィック選択時に GitHub 認証、非公開リポジトリ選択時に追加権限とします。

## クレデンシャル (資格情報) ロギング

ログに Secret を出さないことは [`security_spec.md`](./security_spec.md) を正本とします。本仕様は、認証フローがパスワード / Token / 認可ヘッダー / 認可コード / クライアント Secret をログに載せないことだけを定めます。

## HTTP ロギング

認可ヘッダーの Redact は [`security_spec.md`](./security_spec.md) を正本とします。本仕様は、デバッグ・ビルドの HTTP ログでも認証情報を Redact することだけを定めます。

## エラー・レポート

クラッシュ・レポートへの Secret 禁止は [`security_spec.md`](./security_spec.md) を正本とします。本仕様は、エラー・オブジェクトに HTTP リクエストを添付する場合に認可情報を除去することだけを定めます。

## クリップボード

クリップボード方針は [`security_spec.md`](./security_spec.md) を正本とします。本仕様は、認証 UI が Token を自動コピーせず、入力後にクリップボード内容を保持しないことだけを定めます。

## スクリーンショット/画面収録

Token のマスク表示は [`security_spec.md`](./security_spec.md) を正本とします。本仕様は、UI に出してよい状態が `## UI 状態` であることだけを定めます。

## アナリティクス

アナリティクス導入時には、[`security_spec.md`](./security_spec.md) を正本とします。本仕様は、認証イベントに Token / 認可ヘッダー / クレデンシャル識別子を含めないことだけを定めます。

## バックアップ

クレデンシャル (資格情報) バックアップについては、プラットフォームの Secure ストレージの方針を尊重します。

アプリケーション独自の通常バックアップ・データに、クレデンシャル (資格情報) を含めません。バックアップ対象のプライバシーは [`security_spec.md`](./security_spec.md) を正本とします。本節は、お気に入り / 設定 / 統計 / キャッシュをバックアップしてもクレデンシャルは Secure ストレージの方針に従うことだけを定めます。

## デバイス移行

デバイス移行時にクレデンシャル (資格情報) が利用可能かどうかを、アプリケーションが保証しません。プラットフォーム Secure ストレージの移行の方針に従います。クレデンシャル (資格情報) が移行されなかった場合、アプリケーション・データはリストア済みでも再認証を正常な回復フローとして扱います。

## クレデンシャル (資格情報) and 統計バックアップ

クレデンシャル (資格情報) と統計データを独立して扱います。統計バックアップ/リストアが成功したからといって、クレデンシャル (資格情報) が存在すると仮定しません。クレデンシャルは Secure ストレージ、統計はアプリケーション・ストレージとします。

## MDM/デバイス・バックアップ

MDM、デバイス・バックアップ、デバイス移行等によるアプリケーション・データの移行時にも、クレデンシャル (資格情報) とアプリケーション・データを別カテゴリーとして扱います。

クレデンシャル (資格情報) 移行の可否は、プラットフォーム・セキュリティの方針に従います。

## 同期

初期バージョンでは、クレデンシャル (資格情報) を S2J Package Dashboard 独自サーバーに同期しません。独自サーバーへクレデンシャルを送るアーキテクチャーを採用しません。

## クラウド・クレデンシャル (資格情報) ストレージ

* Packagist Token
* GitHub Token
* パスワード

S2J Package Dashboard 独自バックエンドに、上記を保存しないことを初期方針とします。これにより、下記を避けます。

* サーバーサイド・クレデンシャル (資格情報) 漏洩
* クレデンシャル (資格情報) データベース操作
* クレデンシャル (資格情報) 暗号化キー管理
* サーバー侵害の影響

## マルチ・デバイスの方針

クレデンシャル (資格情報) のマルチ・デバイス共有を、S2J Package Dashboard 独自機能として実装しません。各デバイスで認証が必要になった場合は、プロバイダ認証フローを利用します。通常のアプリケーション・データ同期とは分離します。

## iCloud/プラットフォーム同期

プラットフォーム Secure ストレージがクレデンシャル (資格情報) 同期機能を提供する場合でも、利用するか否かは明示的に決定します。

「ローカル限定」クレデンシャル (資格情報) vs「同期可能」クレデンシャル (資格情報) をアーキテクチャー決定として扱います。

初期実装では、「ローカル限定」を安全側のデフォルトとします。

## 生体認証の保護

必要に応じて、クレデンシャル (資格情報) アクセスに、下記による追加保護を検討します。

* Face ID
* Touch ID
* デバイス・クレデンシャル (資格情報)

ただし、API リクエストごとに生体認証を要求するなど、過度に UX を損なう設計は避けます。

## メモリ内のクレデンシャル (資格情報)

クレデンシャル (資格情報) は、API リクエスト生成に必要な期間だけメモリ上で保持します。可能な限り、下記に長期間保持しません。

* グローバル・シングルトン
* 静的変数
* アプリケーション状態
* UI 状態

## UI 状態

SwiftUI/Jetpack Compose の状態に、生の Token を保持することを避けます。

たとえば、下記にクレデンシャル (資格情報) そのものを公開しません。

* `@State`
* `Observable`
* `StateFlow`

UI に公開するのは、下記の状態とします。

* `Connected`
* `Disconnected`
* `Expired`
* `AccountName`
* `Capability`

## ドメイン境界

ドメイン・モデルに、クレデンシャル (資格情報) を持ち込みません。クレデンシャル (資格情報) は、インフラストラクチャー/認証境界で管理します。

禁止例:

`Package { githubToken }`

## 認証アーキテクチャー

基本構造: プレゼンテーション → 認証ユースケース → 認証リポジトリ → プロバイダ・アダプタ。アダプタは Packagist / GitHub / クレデンシャル・ストアに分かれ、ストアはプラットフォーム Secure ストレージを使う。層の依存方向は [`architecture.md`](./architecture.md) を正本とします。本節は、認証境界をこの経路に閉じることだけを定めます。

## プロバイダ・アダプタ

プロバイダ固有の認証処理を、アダプタに閉じ込めます。`AuthenticationProvider` の実装は `PackagistAuthenticationProvider` と `GitHubAuthenticationProvider` とします。ドメイン/アプリケーション層から、Bearer ヘッダー等のプロバイダ固有詳細を分離します。

## クレデンシャル (資格情報) 注入

API クライアントは、必要なリクエストにのみクレデンシャル (資格情報) を付与します。不要な付与の禁止は `## 「匿名」ファーストの原則` を正本とします。本節は、認証が必要なリクエストだけクレデンシャル・プロバイダ経由で認可ヘッダーを付けることだけを定めます。

## クレデンシャル (資格情報) 漏洩防止

リダイレクト等によって、認可ヘッダーを意図しないホストに送信しません。ホスト規制は [`security_spec.md`](./security_spec.md) を正本とします。本仕様は、GitHub クレデンシャルを `github.com` / `api.github.com` に限定するなど、対象プロバイダの許可ホストにのみ送ることだけを定めます。プロバイダ固有のホストの方針は、API 仕様で定義します。

## 暗号化通信の規格 (TLS)

HTTPS 必須は [`security_spec.md`](./security_spec.md) を正本とします。本仕様は、クレデンシャルを送信する通信で HTTP を拒否することだけを定めます。開発環境で例外を設ける場合は、本番ビルドに含めません。

## 認証テスト

最低限下記をテストします。

* 匿名アクセス
* 認証成功
* 無効なクレデンシャル (資格情報)
* 期限切れクレデンシャル (資格情報)
* 無効化されたクレデンシャル (資格情報)
* 権限不足
* クレデンシャル (資格情報) ストレージ
* クレデンシャル (資格情報) 削除
* Token 更新
* 接続解除
* 再認証

## Secure ストレージ・テスト

Secure ストレージについて、下記を確認します。実 Token をテスト「フィクスチャ」に保存しません。

* 保存
* ロード
* 更新
* 削除
* 欠落クレデンシャル (資格情報)
* 破損クレデンシャル (資格情報)
* デバイス移行シナリオ

## 「フィクスチャ」の方針

認証テストでは、ダミー・クレデンシャル (資格情報) を使用します。実際の Packagist/GitHub クレデンシャル (資格情報) を、リポジトリにコミットしません。

例:

* `test-token`
* `expired-test-token`
* `invalid-test-token`

## CI

CI 環境で実 API 認証テストが必要な場合、CI Secret ストアを利用します。クレデンシャル (資格情報) を、下記に保存しません。CI ログにクレデンシャル (資格情報) を出力しません。

* ソースコード
* リポジトリ
* フィクスチャ
* 設定ファイル

## Secret スキャン

Secret スキャンと誤 Commit 時の無効化 / Rotation は [`security_spec.md`](./security_spec.md) / [`cicd.md`](./cicd.md) を正本とします。本仕様は、実クレデンシャルがリポジトリに入った場合にプロバイダ側で無効化することだけを定めます。

## 認証エラー UX

クレデンシャル (資格情報) エラー発生時には、技術的な HTTP ステータスだけでなく、`GitHub への接続が無効になっています。再接続してください。` のように表示します。必要に応じて、「再接続アクション」を提供します。

## 権限エラー UX

権限不足の場合、「認証失敗」とは表示せず、`GitHub には接続されていますが、このリポジトリのトラフィックを取得する権限がありません。` のように、認証と認可を区別します。

## セキュリティ不具合の原則

認証エラーによってアプリケーション全体を利用不能にしません。部分障害の方針は [`security_spec.md`](./security_spec.md) を正本とします。本節は、GitHub 認証失敗でも Packagist 公開データを利用可能とすることだけを定めます。

## 初期認証スコープ

v1では、下記を基本とします。

### 匿名

* Packagist 公開 API
* GitHub 公開 API

### Packagist

* `SAFE` Token → 必要性が確認された機能のみ

### GitHub

* 認証済み GitHub API → トラフィック等、明確な必要性がある機能

### 未対応

* Packagist パスワード
* GitHub パスワード
* Packagist `MAIN` Token
* 共有された平文クレデンシャル (資格情報)

## 将来のスコープ

将来的に、下記を検討します。これらを追加する場合は、本仕様および [`security_spec.md`](./security_spec.md) を再評価します。

* GitHub アプリケーション
* 非公開リポジトリ
* 組織アカウント
* デバイス間データ同期
* サーバーサイド統計の収集

## 認証決定の概要

初期方針:

| プロバイダ/データ | 認証 |
| --- | --- |
| Packagist 公開データ | 匿名 |
| Packagist 統計 | 匿名 |
| Packagist セキュリティ告知 | 匿名 |
| Packagist 認証済み操作 | 可能な場合は `SAFE` |
| Packagist パスワード | 不可 |
| Packagist `MAIN` Token | 初期段階では未対応 |
| GitHub 公開リポジトリ | 匿名 |
| GitHub 公開統計 | 利用可能な場合は匿名 |
| GitHub トラフィック | 認証済み |
| GitHub 非公開リポジトリ | 将来 |
| GitHub パスワード | 不可 |
| GitHub 一般ユーザー認証 | GitHub アプリケーション推奨 |
| クレデンシャル (資格情報) ストレージ | プラットフォーム Secure ストレージ |
