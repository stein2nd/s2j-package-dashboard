# S2J Package Dashboard - Swift アプリケーションにおける仕様書構成・細分化方針 — ベター・プラクティス

## 概要

本ドキュメントは、S2J Package Dashboard の初期設計における、仕様書の構成および責務分担を定義します。

プロジェクトの規模、実装経験、Kotlin Multiplatform (KMP) への移行検証等に応じて、仕様書の構成を変更することがあります。

仕様書の分割自体を目的とせず、各仕様書の責務、可読性、変更容易性およびアーキテクチャーとの対応関係を優先します。

## 目的

本ドキュメントでは、仕様書の構成、責務、細分化方針および仕様書間の依存関係を定義します。適切な粒度に分割し、責務を明確にし、変更の影響範囲を限定することを目的とします。

## 非目的

仕様書の分割自体を目的としません。アプリケーション構成や個別機能の正本になることを目的としません。

## 責務

どの関心事をどの**種類**のファイルに置くか、分割基準、命名を定義します。

## 非責務

現行ファイルの名簿は [`specs.md`](./specs.md)、統合の見取り図は [`spec.md`](./spec.md)、各関心事の本文と「責務」節は各専門仕様を正本とします。

## 基本方針

仕様書は、単に「機能ごと」に分割するのではなく、**責務・変更理由・依存関係が異なるものを分離する** ことを基本とします。

たとえば、「パッケージ」という単一の概念について、下記を一つの仕様書にまとめません。

* パッケージ・モデル
* パッケージ API
* パッケージ UI
* パッケージ・ストレージ
* パッケージ統計

それぞれ、下記として責務を分離します。

* [`models_spec.md`](./models_spec.md)
* [`api-packagist.md`](./api-packagist.md)
* [`design_spec.md`](./design_spec.md)
* [`storage_spec.md`](./storage_spec.md)
* [`statistics_spec.md`](./statistics_spec.md)

## 仕様の層分類

仕様書は、下記の層に分類します。仕様構成 / プロジェクト / アーキテクチャー / ドメイン / 外部連携 / アプリケーション / プレゼンテーション / 永続化 / 統計 / 認証・セキュリティ / プラットフォーム / テスト / 運用。現行ファイルの割り当ては [`specs.md`](./specs.md) の「関連仕様」を正本とする。

## 層とファイルの対応

現行ファイルの名簿は [`specs.md`](./specs.md) を正本とする。各ファイルの責務・非責務は、そのファイル自身を正本とする。本節は「どの層に何を置くか」だけを定義し、ファイルごとの記載内容を再掲しない。

| 層 | 置くもの | 置かないもの |
| --- | --- | --- |
| 仕様構成 | 分割方針、統合の優先、入口の目次 | 個別関心事の本文 |
| プロジェクト | 何を作るか、対象ユーザー、非目標 | API、画面、スキーマの詳細 |
| アーキテクチャー | 層、依存方向、共有ロジックの対象 | KMP の source set / 移行手順 |
| ドメイン | 型と層境界、不変条件 | DTO スキーマ、TTL、チャート |
| 外部連携 | エンドポイント、DTO、レート制限 | ドメイン型、キャッシュ TTL |
| アプリケーション | ユースケース、保持する状態、遷移 | 画面 Layout、Route の実装、統合見取り図 |
| プレゼンテーション | 経路、ナビゲーション、画面、コンポーネント、横断 UI、Viewport、視覚 | ドメイン判定、永続スキーマ |
| 永続化 | 端末内保存、スナップショット行、プラットフォーム差分 | 不変条件の再定義、TTL |
| 統計 | 指標の意味、収集、可視化 | 型スキーマ、不変条件 |
| 認証 / セキュリティ | 認証ライフサイクル、脅威・権限・ログ | Keychain / Keystore の API 詳細 |
| プラットフォーム (KMP) | 実施時のモジュール配置と移行段階 | アーキ方針の上書き |
| テスト / 運用 | 何をテストするか、CI、Release 条件 | 機能の再定義 |

たとえば、「パッケージ」は機能で1ファイルにまとめず、モデル / API / UI / ストレージ / 統計へ分ける (基本方針を参照)。

## 仕様の依存関係

仕様書間の依存関係を明確にします。

基本方向: 概要 → アーキテクチャー → モデル → ドメイン・ルール → アプリケーション → プレゼンテーション。外部連携 (`api-packagist` / `api-github` / ストレージ) はアプリケーション/ドメインに依存する。プレゼンテーションは 経路 → ナビゲーション → 画面 → コンポーネント → 横断 UI → Viewport → 視覚。テストはすべての仕様から testing_spec へ向かう。現行ファイルの名簿およびカテゴリー内の並びは [`specs.md`](./specs.md) を正本とする。本節は依存の向きだけを定める。

## 仕様の依存関係ルール

上位仕様から下位仕様への依存を、基本とします。

ただし、仕様書間の循環依存を作りません。循環する場合は、共通概念を上位仕様に抽出します。

A → B → C → A のような循環依存は、禁止例です。

## 仕様の粒度

仕様書は、下記の条件のいずれかを満たす場合に分割します。

### 1. 責務

異なる責務を持ちます。

### 2. 変更頻度

変更頻度が大きく異なります。

### 3. 所有権

異なる層/チーム/コンポーネントが管理します。

### 4. 依存関係

依存関係が異なります。

### 5. サイズ

一つの文書が過度に大きくなった。

## 焦って分割しないこと

仕様書を、過度に細分化しません。

たとえば、下記のようにドメイン・モデルごとにファイルを作る必要はありません。これらが同じドメイン責務に属する場合、[`models_spec.md`](./models_spec.md) にまとめます。

* `package_name_spec.md`
* `package_version_spec.md`
* `dependency_spec.md`
* `repository_spec.md`

## 分割基準

下記を目安とします。最初から最大粒度に分割しません。小は既存仕様へ、中はセクション、大/独立は独立仕様とする。

## 単一の責務

一つの仕様書は、一つの主要な質問に答えられることを基本とします。各ファイルが答える問いは、そのファイルの「概要」「責務」および [`specs.md`](./specs.md) の分類を正本とする。本節は、1ファイルに複数の主質問を載せないことだけを定める。

## 実装漏れを防ぐ

仕様書では、実装詳細を必要以上に固定しません。

たとえば、下記のような技術選択は、ストレージ仕様に記載します。

* SwiftData
* Core Data
* SQLite
* Room

ドメイン仕様では、下記の概念を定義します。

* `Package`
* `StatisticsSnapshot`
* `Favorite`

## API 実装漏れ

API 仕様でも、HTTP クライアントの実装方法を、ドメイン仕様に持ち込みません。

たとえば、下記は、API アダプタ/インフラストラクチャーの実装詳細です。

* URLSession
* Alamofire
* Ktor

ドメイン・モデルは、これらに依存しません。

## UI 実装漏れ

画面仕様では、下記の SwiftUI 具体コンポーネントを、必須仕様として固定しません。

* VStack
* HStack
* LazyVStack
* NavigationSplitView

Android でも同じ情報設計を実現できるよう、下記を中心に定義します。

* 情報
* ナビゲーション
* インタラクション
* レイアウトの意図

具体的なウィジェット選択は、プラットフォーム実装に委ねます。

## ネイティブ UI 原則

S2J Package Dashboard では、UI をプラットフォームごとにネイティブ実装します。共用ロジックと Native UI の分離は [`architecture.md`](./architecture.md) を正本とする。本節は、仕様書を UI 実装方式の正本にしないことだけを定める。

iOS/iPadOS では SwiftUI、Android では Jetpack Compose を基本とします。これは、プラットフォーム間で UI コードを無理に共有することよりも、各プラットフォームの UX の尊重を優先するためです。

Kotlin Multiplatform (KMP) でも、「共用ビジネス・ロジック + ネイティブ UI」という構成が公式テンプレートとして提供されています。([Kotlin Multiplatform Wizard - JetBrains](https://kmp.jetbrains.com/templates/))

## 仕様と Kotlin Multiplatform (KMP)

KMP 移植を容易にするため、仕様書にもプラットフォーム境界を反映します。共用対象は [`architecture.md`](./architecture.md)、KMP の HOW は [`kmp_spec.md`](./kmp_spec.md) を正本とする。本節は、仕様を共用仕様とプラットフォーム仕様に分けることだけを定める。

## 共用仕様

ドメイン、ユースケース、API 契約、永続方針、認証方針など、プラットフォームに依存しない関心事は共用仕様とする。実装差が出る場合だけ、プラットフォーム仕様に差分を書く。現行のどのファイルが該当するかは [`specs.md`](./specs.md) のカテゴリーを正本とする。

## プラットフォーム仕様

ストレージの OS 差分は `ios_spec.md` / `android_spec.md` とする。`kmp_spec.md` は移行時の実装境界であり、アーキ方針の正本ではない。名簿は [`specs.md`](./specs.md) とする。

## 対ファイル

見出しをそろえた対は、同じ関心の HOW をプラットフォームまたはプロバイダごとに切ったものである。現行の対は下記とする。

* [`ios_spec.md`](./ios_spec.md) / [`android_spec.md`](./android_spec.md)
* [`api-packagist.md`](./api-packagist.md) / [`api-github.md`](./api-github.md)

上流の不変条件 (ドメイン正しさ、TTL / Freshness、スナップショット行、型、認証方針など) を対の本文に写さない。追加・変更するなら正本へ書き、対ファイルは参照だけにする。正本は関心事ごとに [`specs.md`](./specs.md) の名簿と、各ファイルの「非責務」を見る。

対ファイルに書いてよいのは、その側だけの HOW である。例: SwiftData Record と Room Entity、Packagist の `If-Modified-Since` と GitHub の14日窓。

## 汎用 UI vs プラットフォーム固有 UI

UI については、「汎用 UX」と「プラットフォーム UI」を分離します。

汎用 UI:

* 情報の階層構造
* ナビゲーションの意図
* ユーザーのワークフロー
* アクセシビリティの要件
* Viewport の要件

プラットフォーム固有 UI:

* SwiftUI ビュー
* Jetpack Compose コンポーザブル
* ナビゲーション API
* プラットフォーム固有のジェスチャ
* プラットフォーム固有のシステム連携

## 決定記録

仕様上の重要な選択については、仕様書本文に長大な議論を記載しません。下記のような決定は、ADR (アーキテクチャー決定記録) として管理します。仕様書には「決定の結果」を記載し、詳細な議論は ADR に分離します。

## 変更管理

仕様変更時には、変更対象の仕様書だけでなく、依存する仕様書への影響を確認します。

たとえば、ドメイン・モデルを変更する場合、ドメイン・ルール、API マッピング、ストレージ、統計、UI、テストへの影響を確認します。各関心事の正本はそれぞれの専門仕様、名簿は [`specs.md`](./specs.md) とする。

## バージョン管理

仕様書バージョンは、原則としてプロジェクト・バージョンとは独立して管理します。

重大な破壊的変更が発生した場合は、Git 履歴および ADR (アーキテクチャー決定記録) によって変更理由を追跡可能とします。

## フラット構造の方針

仕様書が少ない段階では、ディレクトリを細分化しません。

理由:

* ファイルを探しやすい
* GitHub 上で一覧性が高い
* Link が単純
* 小規模プロジェクトでは、過剰な階層を避けられる

下記を目安とします。これは厳密な制限ではなく、プロジェクトの規模に応じて判断します。10～15件はフラット、15～30件はディレクトリによるグループ化を検討、30件以上はドメイン/API/UI/プラットフォーム等に分類。

## アンチパターン

下記のような「仕様書構成」を避けます。

### 「神」仕様

すべての仕様を、一つの巨大なファイルに集約しません。

### 「API + ドメイン」の混在

API 応答とドメイン・モデルを、同一仕様書に混在させません。

### 「UI + ビジネス・ロジック」の混在

ビジネス・ルールを UI 仕様書に記載しません。

### 「プラットフォーム + ドメイン」の混在

ドメイン・モデルに、プラットフォーム固有仕様を持ち込みません。

### 「対ファイル」への上流ルールの写し

`## 対ファイル` の対に、上流の不変条件の本文を再掲しません。見出しがそろっているため、写すと対の間でフォークします。追加するなら正本へ書き、対は参照だけにします。

* SwiftData の使用
* URLSession の使用
* NavigationStack の使用
